# BUG 实测：参考旋律提取「并发闸门形同虚设」+「重试上限永久封死」（P1-12）

- **日期**：2026-09-10
- **发现**：`local/唱歌模块全链路拷问报告-2026-09-10.md`（P1-12 / 2-C，7 路审计交叉）
- **范围**：`services/python/app/sing/jobs.py`（`_drain_queue`、`_resume_or_create`、`run_job_sync`）
- **影响**：① 多首积压时 **8 个 pyin 同时跑**（配置的并发上限 2 被架空）——CPU 打满、ffmpeg/内存峰值叠加，uvicorn 单 worker 下 SSE 心跳与评分请求一起排队；② 提取器换代（或失败原因随换代修好）后，**撞过重试上限的歌永远不会再被重建**，`pitch_ref_status` 永久 missing（跟唱入口 40905），只能人工改库——BUG-2 之后 3 首 demo 的真实处境。

---

## 1. 复现

### 1.1 并发闸门失效（无需真实音频）

库里有 5 个 `queued` 提取任务时执行一次排空（`jobs._drain_queue()`），统计同时进入 `run_job_sync` 的任务数：

- 修复前：**并发 5**（批大小）——配置 `pitch_extract_concurrency=2` 完全没起作用；
- 修复后：**并发 2**。

自动化证据（回退修复后重跑）：

```
tests/test_pitch_jobs.py::test_drain_queue_caps_concurrency_to_setting
E  AssertionError: 并发应被信号量限到 2，实测 5
E  assert 5 == 2
```

### 1.2 重试上限永久封死（BUG-2 的真实后续）

1. pyin-v1 的 upsert 缺陷（BUG-2）让 3 首 demo 的提取任务反复失败 → `attempts=3`；
2. 修好缺陷并升到 pyin-v2（`EXTRACTOR_VERSION` 变更，`_refs_ready` 判旧世代 → 走重建路径）；
3. 扫描看到"最近一条 failed 且 `attempts >= 3`" → `return False` **永久跳过** → refs 永远 missing。

自动化证据：

```
tests/test_pitch_jobs.py::test_scan_revives_capped_job_after_extractor_generation_change
E  AssertionError: 换代后应重建（修复前 attempts=3 撞上限 → 永久跳过）
E  assert 0 == 1                       # scan_due_jobs() 返回 0

tests/test_pitch_jobs.py::test_scan_probes_legacy_capped_job_only_once
E  AssertionError: 世代不明的历史失败行应放行一次探针（修复前永久跳过）
E  assert 0 == 1
```

## 2. 根因

1. **信号量包在 `gather` 外层**：`async with _sem(): await asyncio.gather(*(to_thread(run_job_sync, j.id) for j in jobs))` —— 整批只取 1 个许可，`_sem()`（`Semaphore(pitch_extract_concurrency)`）约束的是"批次数"而不是"并发任务数"；批大小是 8（`_drain_queue` 的 `limit(8)`），于是实际并发上限是 **8**。
2. **重试上限不带世代维度**：`if last_failed.attempts >= settings.pitch_extract_max_attempts: return False` —— 只看次数，不看"这次失败属于哪个世代"；失败 payload 也没记 `extractor_version`，事后无法判断是否换代。

## 3. 修复

1. **逐任务取信号量**（`_drain_queue` + 新增 `_run_one_job`）：
   `await asyncio.gather(*(_run_one_job(j.id, max_attempts) for j in jobs))`，其中 `_run_one_job` 内 `async with _sem(): await asyncio.to_thread(run_job_sync, ...)` → 并发上限真正等于 `pitch_extract_concurrency`；批大小 8 仍保留为"每轮排空的任务数上限"。
2. **重试预算随世代复位**（新增 `retry_decision()`，`_resume_or_create` 按决策处理）：
   - `RETRY_RESET`：payload 的 `extractor_version` != 当前 `EXTRACTOR_VERSION`（换代）**或** 行上 `revision` != 当前 LRC 世代 → 重建并 `attempts = 0`，给新世代完整预算；
   - `RETRY_PROBE`：历史失败行 payload 无版本快照（世代不明）→ 放行**一次**探针，**不**清零（失败即刻回到上限）——一次性自愈历史卡死，又不取消重试上限；
   - `RETRY_SKIP`：世代未变且达上限 → 仍跳过（保留 failed 证据）；
   - `RETRY_REQUEUE`：同世代未达上限 → 常规重试（`attempts` 不清零，语义同修复前）。
   失败快照新增 `payload.extractor_version`（`run_job_sync` 失败分支写），下一轮判定据此比较世代。

## 5. 踩坑

1. **「信号量包 gather」是这类批处理的通病**：`async with sem: await gather(...)` 读起来像"限流"，实际只限流的**入口次数**。只要被包住的协程多于许可数，闸门就是纸糊的。判定口诀：许可获取必须在**每个并发单元内部**（`_run_one_job`），批处理外壳只管取批。
2. **`retry_decision` 的返回值语义别复用**：第一版把"未达上限的常规重试"也返回 `RESET`，调用方顺手把 `attempts` 清零 → 既有测试（第 2 轮断言 `attempts == 2`）立刻变红。四态拆开后（`requeue`/`reset`/`probe`/`skip`）才既保上限又保换代复位。
3. **探针分支要考虑"无版本快照"的历史数据**：修复前落库的失败 payload 里没有 `extractor_version`，判"没换代"会继续永久卡死（等于没修），判"换代"等于废掉重试上限。折中是放行一次且不清零——失败后该行就带上了当前版本，自动回到上限约束（用测试固定住这个"只探一次"的行为）。
4. **LRC 换代其实多半不需要 revision 分支**：LRC 整首重写会 CASCADE 删掉旧 job（新 job 从 attempts=0 开始）；`revision` 分支实际兜住的是"就地追加 LRC 行"这类 max(id) 变化但 job 存活的场景——仍保留，判据便宜且可测。
