# BUG 实测：容器内 Python→Java 内部委托全部失效（APP_JAVA_BASE_URL 缺省 localhost）

- **日期**：2026-09-10（唱歌模块全方面复测发现）
- **范围**：`docker-compose.yml`（python-api 环境变量）、`.env.example` 注释
- **影响**：容器内 Python 对 Java 的**三个内部委托全部 Connection refused**：
  1. `POST /internal/song/{id}/pitch-status` —— 参考旋律就绪门禁翻转（唱歌链路关键路径）；
  2. `POST /internal/level` —— 入学测试档位回写；
  3. `POST /internal/checkin` —— 每日打卡卡物化。
  其中 ① 会让**新环境首次提取 / LRC 重写 / 提取器换代**之后，歌曲永远停在 `missing`/`building` → 用户建跟唱会话恒 **40905「参考旋律未就绪」**；② ③ 静默降级（只写日志），看板/打卡长期缺数据。

---

## 1. 复现（真容器）

1. 容器起来后，把某首歌的 refs 世代降级（模拟提取器换代）或把门禁置 missing：
   ```bash
   docker compose exec -T postgres psql -U vocalverse -d vocalverse -c \
     "update song_pitch_refs set version='pyin-v1' where lrc_id in (select id from lrc where song_id=3)"
   ```
2. 等一个扫描周期（`APP_PITCH_EXTRACT_SCAN_INTERVAL_S=60`）→ 任务被重建、提取成功、refs 写回 pyin-v2；
3. `songs.pitch_ref_status` **纹丝不动**（仍 missing/building），`python-api` 日志：
   ```
   pitch status 委托失败 job=7 song=3（补偿重发兜底）: [Errno 111] Connection refused
   pitch status 补偿委托失败 song=2: [Errno 111] Connection refused
   ```
4. 逐层验证：
   ```bash
   docker compose exec -T python-api sh -c "getent hosts java-api"     # 172.18.0.5 java-api（DNS 正常）
   # 但 settings.java_base_url 默认 = http://localhost:8080 ← 容器内的 localhost 是它自己
   ```

## 2. 根因

`app/core/config.py:43` 的默认值是 `java_base_url = "http://localhost:8080"`（对**裸跑**正确），
而 `docker-compose.yml` 的 `python-api` 段**从未**设置 `APP_JAVA_BASE_URL`（`git log -S` 证实历史上也没设过），
`.env` 里也没有 → 容器内指向自己 → `httpx.post` 直接 `Connection refused`（连不上本容器的 8080）。

> 为什么演示"看起来没问题"：`songs.pitch_ref_status` 早已是 `ready`（历史某次由 host 裸跑或手工内部 REST 翻转），
> 而扫描的补偿分支对 `building` 状态**主动跳过**（"worker 会推进，keep building"）→ 一旦真的进入重建路径就锁死。

## 3. 修复

`docker-compose.yml` python-api 环境显式钉死容器网络地址（不受 `.env` 影响）：

```yaml
      APP_JAVA_BASE_URL: http://java-api:8080
```

`.env.example` 同步补注释：`.env` 里的 `localhost` 只对裸跑生效，compose 已覆盖为服务名。
（首次尝试顺带给 python-api 加 `depends_on: java-api` → compose 报 **依赖环**（java-api 已依赖 python-api），已回退；委托失败本身已被代码降级+补偿兜底，无需启动序约束。）

## 4. 验证（真容器）

修复前后同一实验对比（song 3：refs 降级 pyin-v1 + 门禁置 missing）：

| | 修复前 | 修复后 |
|---|---|---|
| 提取任务 | done | done |
| refs 版本 | 回到 pyin-v2 | 回到 pyin-v2 |
| `songs.pitch_ref_status` | **missing（锁死，需人工改库）** | **ready（自动翻转）** |
| 日志 | `委托失败 … Connection refused` | 无失败日志 |

另核验：`docker compose exec python-api uv run python -c ...` 打印 `java_base_url = http://java-api:8080`；
`docker compose config` / `yaml.safe_load` 解析通过（AGENTS.md 要求）。

## 5. 踩坑

1. **配置默认值分"裸跑/容器"两套语境**：`localhost` 在容器里永远指容器自己。凡"服务间调用地址"必须在 compose 里显式钉死服务名，不能依赖代码默认值——这类缺陷在裸跑联调时 100% 看不出来。
2. **静默降级让缺陷藏得住**：委托失败按设计只记日志（不阻塞主流程）+ 补偿分支兜底，于是"提取成功但门禁没翻"看起来像"还没到扫描周期"。复测时必须**主动造一次重建**（降 refs 世代）才能暴露。
3. **补偿分支有合理的跳过条件，别把它当兜底万能**：`status == building` 时补偿分支主动 `continue`，所以"卡在 building"这种最危险的形态**不会**被补偿修好——修复前它是永久态。
4. **加 `depends_on` 前先看全图**：java-api 已 `depends_on: python-api`（seeder/健康依赖），再反向加就成环；compose 会直接报错（不是静默），本地 `docker compose config` 一圈即可发现。
