# BUG：审核队列升级件消失 + 看板「新建」口径错位 + 处置备注文案与拍板相反

- **发现**：2026-09-22 · 审核自动送审接入前的链路通读（Java 审核域 + `apps/admin` 审核工作台）+ 新回归用例复现。
- **修复**：2026-09-22 · 执行人：LHRCarrier（AI 代工）· 设计 `docs/58 §5`。
- **影响面**：管理端审核队列（升级件可见性）、审计看板趋势图口径、审核决定弹窗文案、举报处理请求体；不含 C 端与数据库结构。

## 复现

1. **升级件消失**：造一张待审单（发一条被判定违规的帖子）→ 在控制台点「升级」→ 刷新默认队列
   （`GET /api/v1/console/moderation/cases?status=pending`）→ **该单不在列表里**；顶部「已升级」计数却 +1，点不进去。
   升级后单子状态是 `escalated`，而默认筛选是等值 `pending`。
2. **看板口径错位**：`GET /moderation/stats` 的 `trend[i]` 同时返回 `created`（当日新建）与 `pending`
   （当日结束时仍未决定的积压）。前端「新建」折线接的是 `p.pending` —— 图例说新建，画的是积压。
3. **文案与拍板相反**：决定弹窗写「给作者的说明（作者本人会看到这段文字）」，而 `docs/51 B-4` 已拍板
   `decision_note` **不下发作者**（避免审核员身份/内部理由外泄）；作者侧只下发固定原因码标签（P6）。
4. **举报处理双键 hack**：`ReportsView.callHandle` 同时发 `{decision, action}` 并用 `as unknown as` 断言，
   注释称「Java `action` 是 `@NotNull`」——实际 Java `ReportHandle.effective()` 以 `decision` 优先、`action` 可空。

## 根因

1. **状态机语义与查询面不一致**：`ModerationCaseRepository.decide` 的条件 UPDATE 特意用
   `status not in (终态)` 而非 `= 'pending'`，就是为了让 **escalated 仍可处置**；但列表 `search` 只支持单值等值筛选，
   前端默认 `pending` → 升级后的单从「待办视图」里消失了。**「还能处置」与「看得到」是两件事，当时只做了前者。**
2. **同一份数据两个口径，展示层没有区分**：`trend` 里 `created`（新建）与 `pending`（积压）名字都像"量"，
   前端顺手接了后者；服务端注释写得很清楚，前端没人读到。
3. **拍板变更没有扫执行面**：`docs/50 §6.2 硬点 3` 的旧文案与 `docs/51 B-4` 冲突，前端照旧版实现且无人对账。
4. **注释代替验证**：把「对方接口应该是什么样」的假设写进注释，并据此加了一层类型逃逸来"兜住"，
   掩盖了本来可以直接对账的契约（`ReportHandle` 是 public record，一眼可查）。

## 修复

| # | 修复 | 位置 |
|---|---|---|
| 1 | `search` 支持聚合筛选 `status='open'`（= `pending + escalated`）；控制器 `@Pattern` 加 `open`；`/moderation/contract` 增 `caseStatusFilters`；队列默认筛选改 `open` | `ModerationCaseRepository.search`、`ModerationController.listCases/contract`、`QueueView.vue`、`moderationMeta.CASE_STATUS_FILTER_OPTIONS` |
| 2 | 新增 `trendSeries()` 纯函数统一映射：新建=`created`、已处置=`approved`、驳回=`rejected`；补单测防回潮 | `moderationMeta.trendSeries`、`QueueView.vue`、`dto/moderation.ts` |

## 踩坑

1. **「还能处理」≠「看得到」**：状态机的可处置集合改了（escalated 纳入），查询面的筛选集合必须同步扩，
   否则功能"还在"但人"找不到"——这类缺口在纯接口测试里完全测不出来，必须在**列表视图**级写断言。
2. **同名不同义的指标最危险**：`created` 与 `pending` 都像"来了多少单"，实际一个是新建、一个是积压下界。
   修法不是改注释，而是把映射收敛到一个纯函数并配测试（`trendSeries`），让口径只有一处。
3. **拍板文档冲突要在 UI 上落地才算落地**：`docs/51 B-4` 拍板了"不下发作者"，但 UI 继续写"作者会看到"——
   审核员会按错误预期写备注。**文档拍板变更后必须扫一遍执行面（代码 + 文案 + 测试）。**
4. **接入外部判定链路时，AFTER_COMMIT 的默认事务传播是陷阱**：`afterCommit` 回调里旧事务资源仍绑定，
   默认 `REQUIRED` 的"新事务"会加入一个已提交事务，写入在收尾时被丢弃 —— 必须 `REQUIRES_NEW`
   （或用独立线程）。本仓后续任何"提交后动作"都应沿用这条。
