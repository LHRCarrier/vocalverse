# BUG：单写方探针正则笔误 → `db.add(` 完全不检测（M-2 门禁假绿）

- **发现**：2026-09-10 · 修唱歌 BUG-2 时核对"哪些写法会被探针拦"，手工复现探针规则发现命中为空。
- **修复**：2026-09-10 · 执行人：AI 代签（正式署名待组长确认）。
- **影响面**：`services/python/tests/test_single_writer.py`（探针 + 元测试）；
  连带暴露清单误列（`ScenarioMessage`）与未豁免种子写（`app/db/seed_recommend.py`）。

## 复现

1. 在任意 Python 文件写 `db.add(User(username="x"))`（User 为 Java 拥有表）——**探针不报**；
2. 手工复现探针规则：`app/sing/jobs.py` 明明含 `db.add(`，但

```python
PAT = r'(?:db|session|uow|sess)\.add_all?\('   # 原 WRITE_PATTERNS 第一条
re.search(PAT, "db.add(PitchExtractJob(...))")  # → None
```

## 根因

`\.add_all?\(` 中的 `?` 只作用于**紧邻字符 `l`**，等价于 `add_al` 或 `add_all`——
**不匹配最常见的 `db.add(`**（M-2 守护对"新增行"这一写形态完全失效，只剩
`db.delete/update/execute-DML` 形态被拦）。因此：

- `test_single_writer` 常绿是**假绿**：`db.add(Java 拥有表)` 一律漏网；
- 连带没人发现两类存量问题（因守护看不见 add）：
  1. **清单误列**：`ScenarioMessage` 被列入 Java 拥有表，但 docs/10 §4.3 明确
     「练习域（全部 Python 写）」/ docs/10 §3 写方矩阵中 `scenario_messages` 属 Python 写方
     （与 2026-09-09 修正过的 `SongPitchRef` 同类误列）；
  2. **真写 Java 拥有表**：`app/db/seed_recommend.py:121 session.add(Scenario(...))`，
     该种子文件不在 M-3 豁免名单（原名单只有 `app/db/seed.py`）。

## 修复（组长拍板 A：按目标表名精确检测）

1. 正则修正为 `\.add(_all)?\(` 语形，并**按写入目标模型名判定**：
   - 显式模型名（`db.add(X(`、`db.add_all([X(`、`db.delete(X`、`db.update(X`、`db.bulk_*(X`、
     `db.execute(insert|update|delete(X)）→ 仅当 X ∈ JAVA_OWNED_MODELS 才违规
     （`jobs.py` 写 `SongPitchRef` 合法通过——精确化后**不再需要文件级豁免**）；
   - 实例变量形式（`db.add(attempt)` / `db.delete(obj)`）→ 静态不可判定表 → **不判违规**
     （文件级粗粒度守护的已知边界，docs/20 §4.4；选择"不判"而非"保守判违规"是因为后者会
     把 `db.add(attempt)` 这类合法常见写法全部误报）；
   - Core DML 无模型名 / 裸 SQL（`db.execute(text("DELETE FROM songs"))`）→ **保守判违规**。
2. 扫描逻辑抽成纯函数 `find_violations(text)` → 元测试 7 组正反例锁定（含"`db.add(` 必须被抓"
   防笔误复发、"写 SongPitchRef 不误报"、"ScenarioMessage 属 Python 写方"）；
3. 清单修正：`ScenarioMessage` 移出 Java 拥有清单（依据 docs/10 §4.3/§3）；
4. 豁免扩充（组长 2026-09-10 拍板 A）：`app/db/seed_recommend.py` 与 `seed.py` 同列 M-3 豁免
   ——同为仓库内种子初始器（只增不改、非运行时写路径），理由写入探针注释。

## 验证

- `pytest tests/test_single_writer.py`：全仓扫描用例 + 元测试全绿（修复前元测试项不存在）；
- 存量审计：修正后全仓命中归零（仅剩两个已豁免种子文件的合法写）；
- 反向确认：把 `db.add(User(...))` 临时加入任一文件 → 探针**立即报红**（修复前静默通过）。

## 踩坑

1. **门禁的"绿"要能自证**：探针是安全网里最不该出错的组件，却因一个 `?` 位置失效数月；
   教训：**解析型工具必须配正反例元测试**（本次补上），否则"没报错"≠"没问题"。
2. 修好守网会**先翻出存量**（本次一次暴露清单误列 + 未豁免种子写）——修复顺序应为：
   先修规则 → 全仓审计 → 逐条归类（真违例/清单错/需豁免）→ 再落地，避免"修好探针即 CI 变红"的返工。
3. 精确化的代价是**放弃一部分覆盖**（变量形式不再判）——这是刻意的取舍：把守护做准，
   比做宽但满是误报（最终被集体无视）更有价值；边界已写进探针 docstring。
