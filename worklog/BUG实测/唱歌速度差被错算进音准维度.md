# BUG：整体速度差被错算进音准维度——句窗口只平移不缩放 + 局部 DTW 按短侧截断

- **发现**：2026-09-10 · 唱歌模块容器端到端功能测试（素材：整体低 3 半音 + **慢 18.9%**）。
- **修复**：2026-09-10 · 执行人：AI 代签（正式署名待组长确认）。
- **影响面**：`app/audio/sing.py::PyinSingScorer.score_sync`（句窗口映射）、`local_align`（DTW 截断）。
  影响一切"演唱速度与参考有明显差异（≳10%）"的跟唱评分：音准被系统性低估。

## 复现

1. 生成测试素材：参考旋律低 3 半音 + 慢 18.9%（采样率变换，瞬态保留）+ 微底噪；
2. 走容器全链路评分（`local/sing_e2e_test.py`）；
3. 结果：`transpose_semitones=-3`（移调补偿正确）、`medfilt_kernel=5`、`ref_coverage=1.0`，
   但 **`pitch=78.33`**（同等条件下正常速度的素材为 95）；**`rhythm=95`** 完全不受影响。

## 根因（两层，缺一不可）

**第一层：句窗口只做整体平移**
```python
win_start = a["start_ms"] + offset_ms          # offset 只是全局中位平移（≈2272ms）
win_end   = a["end_ms"]   + offset_ms          # 窗口长度 = 参考句长，未按速度缩放
```
用户慢 18.9% → 实际句长 ≈1.19×参考句长 → **句尾 19% 落在窗口外**（从未进入评分）。

**第二层：局部 DTW 按短侧截断**
```python
n = min(len(user_win_f0), len(ref_win_f0))     # 旧实现
u, r = user_win_f0[:n], ref_win_f0[:n]
```
即使把窗口放大到够长，这里仍会把用户序列尾部对齐到参考序列尾部之前的位置——
**参考句末帧永远拿不到对应用户帧**，句尾音高信息既没进 DTW 也没进 cent 统计。

→ 速度问题渗进音准维度：与 docs/06 §9.4「音准测音高、节奏测时间」的分工不一致
（v2 起 `bpm_ratio` 被定为"信息性字段"，**却没人消费它**——白算）。

## 修复（组长拍板 A：句窗口按 bpm_ratio 缩放）

1. `score_sync`：
```python
scale = 1.0 / float(tempo["bpm_ratio"] or 1.0)          # ratio<1（用户慢）→ scale>1（窗口更长）
win_end = win_start + max(1.0, (a["end_ms"] - a["start_ms"]) * scale)
```
   `bpm_ratio` 不可用时为时长截断比（同为"用户相对参考的速度比"，已 clamp [0.5,2.0]）——
   item7 的产出在这里被**消费**（此前只写进 alignment 展示）。
2. `local_align`：去掉短侧截断，用完整两侧序列建成本矩阵（句级 155×185 ≈ 2.9 万格，可承受）；
   守卫由 `n < 3` 改为「任一序列 < 3 → 空路径」。

## 验证

- 新增单测 `tests/test_sing_scorer.py::test_local_align_not_truncated_to_shorter_side`
  （**修复前必失败**）：用户句 35 帧 vs 参考 30 帧 → 断言路径覆盖到**参考末帧**
  （`max(j for _, j in path) == len(ref)-1`）且对齐后 cent < 30；
- 容器 e2e 复测：同一素材 `pitch` 由 78.33 提升（见主线日志）；
- 既有 408 用例全绿（含 v2/v3 全部回归）。

## 踩坑

1. **"信息性字段"= 没人消费的产出**：v2 把 `bpm_ratio` 从节奏分里摘出来后只用于展示，
   而"用户整体快慢"这一真实信息就再没进入任何计算——直到本次端到端才暴露。
   教训：凡是算出来的量，要么被消费，要么在文档里明确"仅展示"，别留中间态。
2. **测试素材必须自检物理真实性**：本轮素材先后错了两次——① 用"乘系数"冒充移调（实为幅度缩放）；
   ② 用相位声码器（pitch_shift/time_stretch）导致**起音瞬态被抹平**（用户侧 onset 只检出 2 个，
   真实人声不会）；③ 采样率变换方向写反（想让音高降 3 半音，实际升了 3 半音）。
   三次都是脚本内置的**FFT 主峰自检**（打印比值 vs 期望比值）当场抓出来的——
   素材脚本从此必须带数值自检，不能"看着差不多就上传"。
3. 端到端 vs 单测的分工再次被验证：本次第二层缺陷（短侧截断）单测里"看不出问题"——
   因为单测喂的两条序列等长；只有真实链路（用户句被速度差拉长）才会触发。
