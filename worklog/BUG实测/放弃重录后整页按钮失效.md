# BUG：唱吧「放弃重录」后整页按钮失效（录音态不复位 · 两个同源缺陷）

- **发现**：2026-09-10 · 组长真机/网页实测 `/m/sing`：进入跟唱面板录音后点**「放弃重录」，整个页面的功能都失效卡住了**（截图：录音中 · 放弃重录/停止并评分 · 实时音准线仍在）。
- **修复**：2026-09-10 · 执行人：AI 代签（正式署名待组长确认）。
- **影响面**：`/m/sing`（真形态）与 `/preview/singing`（同一 `useSingPlay` 组合式）；缺陷 1 影响**所有跟唱用户**（放弃一次即整面板失效），缺陷 2 影响「录音中直接关面板」的用户（麦克风泄漏 + 旧音频按新歌评分）。后端/契约无涉（纯前端状态机）。

## 复现

```
进入 /m/sing → 点某首歌 → 「开始跟唱（≤3 分钟）」→（录音中）点「放弃重录」
```
实际：录音态 UI 不消失——「录音中…」按钮一直禁用、「放弃重录」「停止并评分」点了没反应、实时音准线读数冻结在最后一帧。除面板右上角「关闭」外，面板内所有控件都失效（用户感知为「整页卡死」）。

第二个（同源，分析时发现）：
```
录音中点面板右上角「关闭」→ 重新进同一首歌 → 点「开始跟唱」
```
实际：界面毫无反应（不进入录音态）；且那段被遗弃的录音到 ≤180s 自动停止后，会带着**新歌**的 `detail` 上传评分。

## 根因

**缺陷 1（主因）**：`useSingPlay` 的 recorder 状态回调**丢掉了非录音态**。

```ts
// 修复前（apps/web/src/composables/sing.ts）
recorder.onStateChange = (s) => {
  if (s === 'error') phase.value = 'failed'
  if (s === 'recording') phase.value = 'recording'   // ← idle / stopped 无人处理
}
```
`cancel()`（放弃重录）的真实链路是 `recorder.stop() → onstop(cancelled 分支) → setState('idle')`（`audio/recorder.ts:105-109`），这个 `idle` 被丢弃 → `phase` 永远停在 `'recording'`：
- **主按钮**（`:disabled="recording || processing"`）永久禁用，文案停在「录音中…」；
- **「停止并评分」** → `recorder.stop()` 被 `if (this.state !== 'recording') return` 挡成空操作；
- **「放弃重录」** → `cancel()` 再次走同一分支、再发一个被忽略的 `idle` → 也是空操作；
- **实时音准线** → `:active="recording"` 恒真、`phase` 无响应式变化 → 父组件不重渲染 → `getLiveStream()`（非响应式字段）不会把 `null` 传下去 → 子组件 `live.stop()` 不触发，60ms 间隔 + rAF 一直跑（读数冻结、白耗电）。

> 全仓约定本来是对的：`audio/__tests__/recorder.test.ts` 的装配注释写着「与三个 View 一致：**非 recording 即复位按钮**」，MobileSpeakingView / PracticeView / PlacementView / DefenseView / MobileFreeChatView 五处都是 `if (state !== 'recording') recording = false`——**只有 `useSingPlay` 这一处漏了**。

**缺陷 2（同源）**：`reset()`（关闭面板 / 预览页「再来一遍」）只清状态，**不 `recorder.cancel()`**（而 `onUnmounted` 里有）→ 面板关闭后录音被遗弃：麦克风继续采集到 ≤180s 自动停（已无 UI 可停），且 `recorder.state` 仍是 `'recording'` → 之后 `start()` 被同态守卫 `if (this.state === 'recording') return` **静默早退**（界面毫无反应）；到点后 `onStop` 触发上传，此时 `detail` 已是新歌 → 旧音频按新歌评分。

## 修复（组长 2026-09-10 拍板：方案 A + A′）

1. **`onStateChange` 补非录音态复位**（3 行，对齐既有五处约定）：
```ts
if (s === 'error') phase.value = 'failed'
else if (s === 'recording') phase.value = 'recording'
else if (phase.value === 'recording') phase.value = 'idle'   // idle/stopped → 复位
```
   正常停止路径不受影响：`stopped` 复位后，紧随其后的 `onStop → submitAudio` 在**同一同步块**内把 phase 置为 `'uploading'`，不会闪回（已加测试锁定）。
2. **`reset()` / `retry()` 补 `recorder.cancel()`**：关闭面板、错误态复位都真正释放麦克风与 recorder，杜绝「上一次录音还活着」。

## 踩坑

1. **「回调只处理关心的状态」是本类缺陷的温床**：状态机回调必须显式声明**穷尽**语义（`else` 分支复位），否则新增一条 recorder 状态路径就会静默卡死 UI；全仓五处正确、一处漏写，说明**约定要靠测试钉住**（本轮补的就是 sing 这条路径）。
2. **非响应式数据在渲染期读取 = 更新丢失**：模板里 `:stream="play.getLiveStream()"` 读的是 recorder 的普通字段，父组件不重渲染时这个 prop 永远不会变成 `null`，子组件的 `watch` 也就不会停检测——「状态没变 → 不渲染 → 清理逻辑不执行」的隐蔽链条（缺陷 1 的次生影响）。
3. **停止/取消的守卫要成对**：`start()` 有同态守卫、`stop()`/`reset()` 就必须保证状态一定被复位（本次缺陷 2 的教训）；否则守卫会把「无效调用」和「真实用户操作」一起吞掉。
4. **探测顺序**：先用假 recorder 写探针复现（`phase after cancel = recording`）再改代码，比直接改完再看现象更快锁定唯一根因。
