# BUG：提取器世代升级重提取必失败——refs 只 INSERT 不 UPSERT，撞 `uq_song_pitch_refs_lrc_id`

- **发现**：2026-09-10 · 唱歌模块容器端到端功能测试（`EXTRACTOR_VERSION` 由 pyin-v1 升 pyin-v2 时暴露）。
- **修复**：2026-09-10 · 执行人：AI 代签（正式署名待组长确认）。
- **影响面**：`app/sing/jobs.py::_run_job_inner`（写 refs 段）。
  **影响一切"同 LRC 世代重提取"**：提取器/参数升级、失败重试、参考音频替换——不只是本次的 pyin-v2。

## 复现

1. 将 `EXTRACTOR_VERSION` 由 `pyin-v1` 改为 `pyin-v2`（pitch_ref 增 `onsets_ms`）；
2. 重建 python-api 容器（旧 refs 仍在库：14 行 `version=pyin-v1`）；
3. 等 lifespan 扫描（60s 周期）或手动调 `scan_due_jobs()`：3 首 published 歌各建一 job（行为正确：`_refs_ready` 判定"世代旧"）；
4. worker 执行 → 3 个 job 全部 `failed`（attempts=1），`songs.pitch_ref_status` 仍 ready 但 refs 仍 pyin-v1；
5. 每轮扫描把 failed 重置为 queued 再失败一次，attempts 累到上限（3）后**永久放弃**。

## 根因

`_run_job_inner` 写 refs 只有 `db.add(SongPitchRef(...))`（纯 INSERT），其隐含假设是
「refs 只随 LRC 整首重写而重建——LRC 行删除时 `ON DELETE CASCADE` 已把旧 refs 清空」。

而**世代升级重提取**时 LRC 未变、旧 refs 仍在 → 同一 `lrc_id` 撞唯一约束：

```
(psycopg.errors.UniqueViolation) duplicate key value violates unique constraint "uq_song_pitch_refs_lrc_id"
DETAIL:  Key (lrc_id)=(1) already exists.
[SQL: INSERT INTO song_pitch_refs (lrc_id, start_ms, end_ms, pitch_ref, extractor, version) ...]
```

整事务回滚 → 该 job failed（错误快照写入 `payload.error`，不伪造数据——这一点是对的）。

**为什么一直没暴露**：v1→v2 是本仓第一次走到"世代升级"路径（提取管线落地时只有"新 LRC → CASCADE → 全新建"这一条路），
单测也只覆盖"refs 不存在 → 新建"，没有"refs 已存在 → 重提取"用例。

## 修复（组长拍板 A：幂等 upsert，纯 ORM）

```python
ref = db.execute(select(SongPitchRef).where(SongPitchRef.lrc_id == int(line.id))).scalar_one_or_none()
if ref is None:
    db.add(SongPitchRef(lrc_id=..., ..., version=EXTRACTOR_VERSION))
else:
    ref.start_ms, ref.end_ms, ref.pitch_ref = ..., ..., pitch_ref
    ref.extractor, ref.version = "pyin", EXTRACTOR_VERSION
```

- 纯 ORM 属性赋值（`app/models/*` 之外不出现 Core UPDATE/DELETE）→ 与单写方探针口径一致；
- SQLite（单测/CI）与 PG（生产）双兼容，不依赖 `ON CONFLICT`。

## 验证

- 新增单测 `tests/test_pitch_jobs.py::test_scan_rebuilds_refs_when_extractor_generation_is_old`：
  预置 `version="pyin-v1"` 的 refs → `scan_due_jobs()==1`（世代旧必重建）；配合既有
  `test_run_job_writes_refs_and_delegates_camelcase`（断言 refs 为当前世代 + `pitch_ref` 含 `onsets_ms`）
  → **修复前**：重建路径 `db.add` 撞唯一键；**修复后**：就地更新为 pyin-v2。
- 容器实测：重建后 3 首自动重提取成功，`song_pitch_refs` 全部 `pyin-v2` 且含 `onsets_ms`。

## 踩坑

1. **"重跑幂等"是被假设的，不是被验证的**：`song_pitch_refs` 的唯一约束与 `db.add` 直接冲突，
   但只有当"同世代重提取"第一次真实发生才炸；此前所有验证都是"从零提取"。
2. 失败重试机制（attempts 上限）把问题**累积成永久失败**而不是反复报错——排障时先看
   `pitch_extract_jobs.payload.error`（错误快照设计在这里救了排查）。
3. 世代升级的触发依赖 `_refs_ready` 的版本比对——扫描逻辑本身正确，**坏的是写入侧**；
   排查时"日志说建了 job、job 却 failed"这个组合是定位关键。
