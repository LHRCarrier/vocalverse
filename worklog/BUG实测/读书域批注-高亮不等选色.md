# 读书域批注 · 点「高亮这句」不等选色就落默认色

> 归档日期：2026-09-09 · 发现人：组长手机实测（`worklog/BUG记录/读书域系列BUG9-09/高亮句子问题/新建 文本文档.txt`）· 模块：`apps/web` `MobileWordCard` / `MobileReaderView` / `MobileAnnotationSheet`
> 修复 commit：见本条目所在 PR（`fix(reading)`）

## 复现

1. 进阅读器，点任意词 → 弹出查词卡；
2. 点卡片底部「高亮这句」；
3. **句子立刻被高亮成黄色**（色板首色 `#fde68a`），用户没有机会选色。

## 根因

`MobileWordCard.vue` 的「高亮这句」按钮 emit `sentence-highlight`（无 payload）→
`MobileReaderView.vue` 的 `@sentence-highlight="runSentenceAction('highlight')"` →
`runSentenceAction` 的默认参数 `color = '#fde68a'`（`MobileReaderView.vue:152`）→
`:163-167` 立即 `createAnnotation` 落库。

即：**「没传色」被当成「用默认色」**，而不是「还没选色」。

## 修复

把「高亮」拆成两条语义：

- **不传色** → `chooseColorForSentence(idx)`：打开 `MobileAnnotationSheet mode="highlight"` 面板
  （只列 4 色 + 取消/高亮），`color` 初值 `null`、未选色时「高亮」按钮**禁用**，选色后才落库；
- **显式传色** → `highlightSentence(idx, color)`：动作条色点直出（色点本身即选色动作，不弹层，
  保持 2026-09-10 组长拍板的既有交互）。

顺带把 `mode="create"` 也改为必须选色（此前会静默落色板首色，用户没点过任何色块）——
两种模式共用 `canSave = color !== null`。

## 验证

`apps/web/src/views/mobile/__tests__/MobileReaderView.test.ts`：

```
✓ 查词卡底部「高亮这句」→ 先出选色面板，未选色不能保存（修复前直接落默认黄，用户没得选）
     1) 点「高亮这句」后 createAnnotation 调用次数 = 0（修复前 = 1）
     2) 面板标题「选择高亮颜色」，「高亮」按钮 disabled=true，点击不落库
     3) 点蓝色块 → 点「高亮」→ createAnnotation 收到 color='#bfdbfe'、整句范围、sentence_idx=0
✓ 动作条点色点 → 直接整句高亮（既有行为不变，color='#bbf7d0'）
```

**注意**：该用例的前身断言的是缺陷行为（`expect(payload.color).toBe('#fde68a')`），
修复时一并改写 —— 这类「测试把 bug 锁成契约」的情况，必须在归档里写明改了哪条断言及原因。

修复前必红（HEAD 63fcaee 实测）。修复后 `pnpm lint` / `typecheck` / `test:run`（178 passed）全绿。

## 踩坑

1. **默认参数是隐蔽的「静默决策」**：`function f(color = '#fde68a')` 让「调用方忘了传」与
   「调用方要黄色」不可区分。默认值只能用于「无副作用」的参数；有副作用（写库）的路径必须
   用 `undefined` 显式分支。
2. **旧测试锁定了 bug**：`MobileReaderView.test.ts` 原有用例把「点高亮这句 → 立刻落默认黄」
   断言成期望行为，直接改代码会让它红。改断言时要在 commit message 与归档里说明
   「该断言描述的是缺陷，不是契约」，否则后人会以为是在迁就实现。
3. **动作条色点是有意的直出**：色点按钮本身就是「选色 + 高亮」二合一（2026-09-10 组长拍板
   「免开弹层」），不要一并改成弹层 —— 用「是否显式传色」区分两条路径即可。
