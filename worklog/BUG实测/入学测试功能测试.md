## BUG-001-R 复审整改：`startSeq` 补丁在三条边界路径上仍是破的（含原 P1 卡死复发）

- **复审/整改时间**：2026-09-01
- **负责人**：LHRCarrier（复审）· 承接 Faust-sudo 的 BUG-001 修复
- **严重级别**：P1（原「按键永久卡死」经另一条路径复发）

### 复审方法

按 `apps/web/src/audio/recorder.ts` 复刻 `MediaRecorder` 状态机（含「对 inactive 实例再 `stop()` 抛 `InvalidStateError`」这一规范行为），把 BUG-001 的 `startRecord`/`stopRecord` 原样跑在假件上，驱动四条路径。主路径（录音中点 ■ → 停止并上传）**验证通过**；另三条不通过，已固化为 `src/audio/__tests__/recorder.test.ts` 的回归用例（对整改前的代码 10 条挂 7 条）。

### 三个残留缺陷

1. **P1 · 权限提示期间点 ■ 再点「拒绝」→ 按钮永久卡死（原 bug 复发）**
   `catch` 里的复位被 `if (seq === startSeq)` 守着，而 `stopRecord()` 恰好把 `startSeq` 改掉了 → 整块跳过，`recording` 永远停在 `true`；再点只会反复触发一个空转的 `stopRecord()`。**「乐观置位」的复位分支上不能加任何条件守卫**——这正是踩坑记录 2 自己写下的教训，却在新代码里被守卫抵消了。
2. **P2 · 权限提示期间点 ■ 再点「允许」→ 被取消的录音照样上传，静默吃掉一道题**
   `if (seq !== startSeq) { recorder.stop() }` 里的 `stop()` 会正常触发 `onstop → onStop → upload()`，上传约 0ms 音频后 `index += 1`。服务端 `placement.py` 无最短时长校验，照收并消耗 ASR/ISE 限流额度。（缓解：`finalize` 的 `scored` 过滤会剔除空分 attempt，综合分不被拉低；但用户少答一题且本页无重录入口。）
3. **P2 · 连点两下 ■ → `@click` 处理器抛未捕获 `InvalidStateError`**
   `MediaRecorder.stop()` 后 `onstop` 要到下一个宏任务才派发，这个间隙里 `VoiceRecorder.state` 仍是 `'recording'`，守卫放行 → 对已 `inactive` 的实例二次 `stop()`。且 `stopRecord()` 的调用点在 `try` 块**外面**。
   > 顺带修正 BUG-001 的一处判断：「同一任务内复位…Vue 批量渲染无中间态」不成立，这是真实的宏任务间隙，不是渲染批次。

### 整改思路：把生命周期收回 recorder，删掉视图层的序号账本

根因是 `recording` 被视图与 `onStateChange` 双重持有，而 `RecorderState` 里的 `'error'` 档**从定义起就没被 `setState` 过**——启动失败时没有任何信号能通知视图复位。整改后：

- `recorder.ts`：`start()` 失败 `setState('error')` 并释放已拿到的轨道；`stop()` 改守 `MediaRecorder` 自身的 `state` → **幂等**；新增 `cancel()`（停采集、放麦克风、**不触发 `onStop`**）与内部世代号 `startGen`，用于作废「仍卡在权限提示上的 `start()`」；新增 `micErrorMessage()` 把 `NotAllowedError` 等译成中文；新增 `MIN_RECORD_MS = 800`。
- `PlacementView.vue`：删除 `startSeq`（竞态改由录音机内部处理），`catch` 无条件复位；`stopRecord()` 按 `recorder.state` 二选一——录音中 `stop()`（上传），启动窗口 `cancel()`（不上传）；`onStop` 增加最短时长判定，避免手滑吃题；`track()` 改 `void` 不阻塞开录（少一个 RTT，也少一个竞态窗口）。

**顺带收益**：`setState('error')` 是三个视图共用的复位信号，因此 `PracticeView` / `DefenseView` 的「权限被拒后按钮卡死」**未改动这两个文件即被一并修复**；它们各自的「停止键失效」仍需按 BUG-001 踩坑记录 3 单独排期。

### 踩坑记录（复审补充）

5. **给竞态打补丁前，先问这个状态该由谁持有**：`startSeq` 是在视图层给「录音机内部竞态」记账，账本和真实状态各走各的，于是漏掉了「取消发生在拒绝之前」这类组合。把世代号挪进 `VoiceRecorder` 后，视图层从 30 行降到 12 行，三条边界路径一起消失——**补丁打在状态的所有者身上，而不是观察者身上**。
6. **异步 API 的「状态」有两份，别信自己镜像的那份**：`VoiceRecorder.state` 是 `MediaRecorder.state` 的镜像，两者在 `stop()` 到 `onstop` 之间必然不一致。凡是包装浏览器异步对象，**幂等守卫要守被包装者的真实状态**。
7. **枚举里定义了却从未被赋过的状态就是 bug 的藏身处**：`RecorderState` 有 `'error'` 却无人 `setState('error')`，三个页面的「失败复位」因此全部失灵。定义了状态就要有人进入它，否则删掉它。
8. **修好「停止」会解锁「过早停止」**：原代码停不下来，所以录音时长恒等于 15s；把停止修好之后，200ms 的误触录音第一次成为可能，而上传即推进题目且不可重录——**新增能力要顺带补上它放开的输入域**（`MIN_RECORD_MS`）。

## BUG-001 入学测试：开录音后点击结束键无法停止录音，按键一直停留在录音状态

- **发现/修复时间**：2026-09-01
- **负责人**：Faust-sudo
- **严重级别**：P1（录音无法手动结束，只能等 15s 自动停止；麦克风权限被拒时按键会**永久卡死**，核心交互不可用）

### 复现过程（报告人：Faust-sudo，2026-09-01 实测提供）

1. 进入「入学测试」页面（`/placement`），加载出朗读题；
2. 点击 🎙 按钮开始录音，按钮变为红色 ■ 并提示「录音中…（≤15s）」；
3. 录音过程中点击 ■（结束键），期望提前结束本次录音；
4. **实际结果**：录音不停止，■ 按键一直停留在录音状态中，只能干等到 15s 自动停止；
5. **附加场景**：若浏览器拒绝麦克风权限（`getUserMedia` 抛错），按钮将**永久**停留在录音状态，无法恢复、无法继续答题。

### 根因分析

`PlacementView.vue` 的录音按钮是「单键」设计，但只实现了启动、没实现停止：

1. 录音中按钮显示 ■（停止图标），点击事件绑定的却仍是 `startRecord()`；
2. `startRecord()` 首行 `if (recording.value) return` 直接早退——**录音中点击 ■ 什么都不执行**，整个页面不存在任何 `recorder.stop()` 调用路径；
3. `recording` 状态是**乐观置位**（点击后立刻 `= true`），而 `recorder.start(15_000)` 失败（权限被拒 / 无麦克风 / 无可用 mime）时**没有 try/catch 复位** → `onStateChange` 永不触发 → 按钮永久卡死。

一句话：**UI 画了停止键，却没有接线停止逻辑；启动失败也没有状态复位。**

### 修复过程（2026-09-01 · Faust-sudo）

修改 `apps/web/src/views/PlacementView.vue`（`<script setup>` 录音逻辑）：

1. **`startRecord()` 改为「切换」语义**：录音中点击 → 调用新增的 `stopRecord()`（内部 `recorder.stop()`，停止后经既有 `onStop → upload()` 正常上传已录片段，与 15s 自动停止同一条链路）；
2. **新增启动序号 `startSeq`**：停止键在任意时刻点击都会作废「尚未完成的启动」（覆盖权限提示/埋点等待窗口），避免 `start()` 完成之后才收到停止导致停止键无效；
3. **`recorder.start()` 包 try/catch**：`getUserMedia` 被拒 / 无麦克风等失败时复位 `recording` 并展示错误提示，**按键不再永久卡死**；
4. 按钮提示文案同步为「录音中…（≤15s 自动停止，点击 ■ 立即停止）」。

> 说明：`track('recording_start')` 内部已静默容错（`@/api/events.ts` 自带 try/catch），不会抛错，故保持「先埋点、后启动」顺序不变。

### 踩坑记录

1. **UI 画了停止键，却没接停止逻辑**：录音中按钮变 ■ 只是「视觉状态」，点击事件仍绑 `startRecord()` 且首行早退——**任何「图标切换」都必须对应真实行为切换，否则就是假按钮**。排查此类 BUG 先看点击事件绑的是哪个函数、代码里有没有 `recorder.stop()` 调用路径。
2. **乐观置位必须配套失败复位**：`recording = true` 在 `getUserMedia` 之前就置位，一旦 `start()` 抛错，`onStateChange` 永远不触发 → 状态卡死。**凡是「先置 UI 状态、后等异步结果」的代码，catch 里必须复位 UI 状态**——权限被拒是真实用户场景，不是理论问题。
3. **同类隐患（本轮未修，建议跟进）**：`PracticeView.vue`（录音中点击 ■ 走 `recorder.start()`，被内部 `state === 'recording'` 守卫吞掉，同样无法手动停止）与 `DefenseView.vue`（`startAnswer()` 首行 `if (recording.value) return`，同样早退）存在同一「停止键无效」模式。本轮按报告范围只修入学测试，另两处建议排期统一修复。
4. **手动停止应复用自动停止的上传链路**：手动停止走 `recorder.onStop → upload()`，与 15s 自动停止完全同一条链路，`uploading` 顺带禁用按钮，不会出现「停完立刻能重录同题」的竞态——修 BUG 优先复用既有回调，不要另开上传分支。
