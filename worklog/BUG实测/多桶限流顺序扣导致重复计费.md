# BUG 实测：多桶限流「顺序扣 + 不回滚」导致重复计费与额度空转（P1-13）

- **日期**：2026-09-10
- **发现**：`local/唱歌模块全链路拷问报告-2026-09-10.md`（P1-13）
- **范围**：`services/python`（`app/core/ratelimit.py` 新增 `consume_all`；`app/sing/service.py`、`app/api/routes/{practice,placement,free_chat}.py` 换用）
- **影响**：一次请求要消耗多个桶时逐桶顺序扣、**任一桶超限不回滚**：
  - 用户重试被**重复计费**（跟唱：`sing` 已扣、`ise` 429 → 重试再扣一次 `sing`；`sing` 只有 5 次/时，两三次重试就再也唱不了）；
  - 某桶耗尽期间**其他桶被空转烧干**（`ise` 用尽后每次重试白扣 `sing`，用户始终拿不到结果）；
  - Redis 路径 429 时**仍然 INCR**：被拒请求不断抬高计数，"越拒越多"。

---

## 1. 复现

真机/接口序列（修复前）：

1. 用户 ISE 桶已用尽（30/h），sing 桶还有余额；
2. `POST /api/v1/sessions/{id}/audio`（跟唱整首上传）→ 429；
3. 重新上传同一会话 → 又 429，且 **sing 桶计数继续 +1**（每次重试都白扣）——`sing` 5/h 很快见底，之后连"能算的请求"也进不来。

自动化证据（回退调用点后重跑，`assert` 打在真实内存计数上）：

```
tests/test_sing_service.py::test_submit_does_not_charge_sing_when_ise_bucket_is_full
E  AssertionError: ISE 超限时 sing 必须回滚（修复前为 1）
E  assert 1 == 0
```

计数层面（`tests/test_ratelimit.py`）另有：`consume_all` 成功后各桶 +1；任一桶超限时**所有桶（含超限桶自身那次 +1）**回到 0；单桶达限后拒绝请求不再放大计数。

## 2. 根因

`submit_song_audio`（以及 practice/placement/free_chat 的同类写法）：

```python
await consume("sing", settings.sing_rate_per_hour, user_id)   # ← 先扣
await consume("ise", settings.ise_rate_per_hour, user_id)     # ← 后扣，抛 429 时上一行已生效
```

`consume` 是"扣 1 再判限"，**没有回滚概念**；调用方顺序扣多桶时，异常点之后的桶不会被检查，异常点之前的桶已经计入。Redis 路径更严重：`pipe.incr()` 无条件执行，超限时计数仍 +1。

## 3. 修复

新增 `core/ratelimit.consume_all(buckets, user_id)`，语义 = **全有或全无**：

1. 逐桶调 `_redis_consume`（扣 1 并返回是否超限），记录**第一个**超限桶（`Retry-After` 归它）；
2. 若无超限 → 结束（成功路径与旧逐桶扣完全等价）；
3. 若有超限 → 对**全部桶**执行 `_release`（`-1`，内存/Redis 双后端；Redis 回滚后计数为负则归零）→ 抛 429（`Retry-After` 指向超限桶）。

`consume(bucket, limit, user_id)` 保留为 `consume_all` 的单桶特例（调用点无需区分）；`_memory_consume` 的"先判后扣"改为"先扣后判"，与 Redis 路径同构——否则无法区分"是否已扣"，回滚就会把没扣过的桶减成负数（负计数会放行超额请求）。
调用点换用 `consume_all`：跟唱 `sing`+`ise`（本项主目标）、回合 `asr`+`ise`+`llm`、入学测试 `asr`+`ise`、自由对话 `asr?`+`llm`（同类缺陷一并收口）。

## 4. 验证

- 新增 6 个测试：
  - `tests/test_ratelimit.py`（5）：成功后全桶各计 1 / 任一桶超限全量回滚（含超限桶自身）/ 用尽后再次请求不放大计数 / 单桶语义与上限不变 / 回滚不为负；
  - `tests/test_sing_service.py::test_submit_does_not_charge_sing_when_ise_bucket_is_full`（**修复前必失败** `assert 1 == 0`）：ISE 额度 0 → 提交 429 且 `sing` 计数为 0；额度恢复后重试成功且 `sing` 恰好计 1（证明失败那次没被计费）。
- 既有回归：`tests/test_m2_core.py::test_rate_limit_429` / `test_turn_rate_limit_buckets_by_action`（patch `_redis_consume`）不变通过——桶顺序仍为 asr→ise→llm。
- 门禁：`ruff check` 绿、`ruff format --check` 159 files、`pytest -q` **474 passed**。
- 文档：docs/21 §1.3 增「多桶一起扣」规则（禁止逐桶顺序扣 + 被拒请求不改计数），§3.6 错误码行同步。

## 5. 踩坑

1. **`_memory_consume` 的"先判后扣"和 Redis 的"先扣后判"原本就不一致**：这次要做回滚才暴露——内存路径超限时**没有** +1，Redis 路径**已经** +1。若按内存语义实现回滚，就会把没扣过的桶减成负数（`TRACE` 里出现 -1 → 后续请求被放行）。统一成"先扣后判 + 回滚"后两条路径才同构，`_memory_bump` 再做 `max(0, count+delta)` 兜底。
2. **测试里 patch 的目标名跟着改名走**：`app.sing.service` 由 `from ... import consume` 换成 `consume_all` 后，7 处 `monkeypatch.setattr("app.sing.service.consume", …)` 直接 `AttributeError`（模块里已无该名）；`app.core.ratelimit.consume` 同理。改测试时用带引号的精确替换（`"app.sing.service.consume"`）并断言替换条数，避免误伤 `consume_all` 前缀。
3. **回滚要连超限桶一起回**：只看"没超的桶要回滚"是不够的——超限桶那次 +1 也是本请求造成的，不回滚会让"被拒请求"持续抬高计数（尤其用户在额度耗尽后反复点重试）。
