## 4. 复测新发现：**F1 句窗口起点未按速度弯折 → 偏慢演唱整首失去「节奏」维度**

### 4.1 现象（容器实测）

用「句间插 300ms 静音」的跟唱素材（参考旋律降 3 半音 + 慢 18.9%，素材 37s）跑真容器：

```
status=done  计分句=0/6  rhythm=None  overall=46.45   （alignment: bpm_ratio=0.8261, offset_ms=2976, bpm_source=onset-arbitrated）
```

即：**素材里明明有 5 处 ≥372ms 换气静音**，6 句仍全部 `reason='no_onset'`（节奏不计分、`overall` 退化为 `(0.5·音准+0.3·发音)/0.8`）。
更关键的是历史数据：PG 里 **26 条 attempt 中只有 14 条有 `rhythm_score`**，且 `bpm_ratio < 1`（用户偏慢）的那批**全部**没有节奏分（0.826 组：attempt 17/19/25/27/28），而 `bpm_ratio > 1`（用户偏快）的那批有（1.407→74.25、1.652→95.0）。

### 4.2 根因

`app/audio/sing.py:1137-1139`（句窗映射）：

```python
scale = window_scale(tempo["bpm_ratio"])          # 1/bpm_ratio（clamp [0.67,1.5]）
win_start = a["start_ms"] + offset_ms              # ← 起点只加“全局中位偏移”，**没按速度缩放**
win_end = win_start + max(1.0, (a["end_ms"] - a["start_ms"]) * scale)
```

- `offset_ms` 来自 `align_frames` = DTW 路径 `i-j` 的**中位数**。对速度比 r 的演唱，真实映射是**时间弯折** `user_ms ≈ offset₀ + ref_ms / r`，而中位数偏移只是"整段折中值"：起点处偏大、结尾处偏小。
- 于是**偏慢**（r<1）时后续句窗口起点落到**上一句句腹**（无前置静音）→ `onset_is_continuation` 只能判"延续" → `reason='no_onset'` → 整首节奏不可用；
- **偏快**（r>1）时窗口起点反而落到**前一句之前的静音里** → 首帧无声 → 走 `detect_onset_ms` 正常定位 → 节奏有分。这就是历史数据里"偏快有、偏慢没有"的方向性差异。
- 与 `BUG-4`（句长按比例缩放）同源：当时只补了**长度**，**起点**没补。

证据脚本（只读，可复跑）：`local/window_mapping_probe.py`（帧长按文件真实采样率换算）——

```
音频 37.02s @ 22050Hz，检出 ≥150ms 静音段 5 处：5851~6223ms 12074~12446ms 18321~18692ms 24543~24915ms 30766~31138ms
句 参考窗(ms)      A 现状窗(ms)      A 判定            C 真值弯折窗(ms)  C 判定
1  0~4940       2976~8956        ❌ 延续（前置有声 5/6 帧）  0~5874      ❌ 起点在文件头部（无前置静音，素材特性）
2  4940~9880    7916~13896       ❌ 延续（前置有声 6/6 帧）  5874~11747  ✅ 新起唱（落在 5851~6223 静音内）
3  9880~14820   12856~18836      ❌ 延续              11747~17621 ❌（差 327ms：本素材每插一个换气段还会顺移）
```

> 判据 `onset_is_continuation` 本身设计合理（首帧有声且前 150ms 也有声 = 延续；首帧无声则交给 `detect_onset_ms` 找静音→有声跳变）。**问题只在窗口落点**。

### 4.3 影响面

- 用户在跟唱时报"整首没有节奏分"（报告三分项缺一，`overall` 静默按 0.5/0.3 权重重算）；
- **演示素材正好命中**：仓库自带 `local/sing_test_user.wav` 与容器历史 attempt 均为 `bpm_ratio=0.826`（偏慢 18.9%）→ 演示链路里「节奏」维度长期为 `None`，而 `docs/06 §9.4` 明确节奏占 **0.2** 权重；
- 偏快的演唱不受影响（掩盖了问题：之前 v4 验证用的素材正好是偏快/同步的）。

### 4.4 修复结果（组长拍板**方案 A** → 已落地为口径 v6）

| 方案 | 状态 |
|---|---|
| **A 时间弯折 + 截距拟合** | ✅ **已实施**（升 `SCORING_VERSION='v6'`）：`TimeWarp(offset + stretch × ref)`，stretch 取 onset 仲裁 `bpm_ratio` 且与路径拟合斜率互证；偏差对期望位置计算 |
| B 只补起点缩放 | 未采用（实测不足以解决） |
| C 只加兜底 | 未采用（会让错位窗口把下一句起唱算给本句） |
| D 文档化不改 | 未采用 |

**实施中还发现 F1 的①号主因**（比 §4.2 的窗口分析更关键）：起唱判据用 `f0 > 0` 判"有声"，而 `librosa.pyin`
对**数字静音也大量判浊**（37s 换气素材 1119 帧中仅 39 帧清音），叠加 160ms 中值滤波后一次 372ms 真实换气
只剩 ~150-190ms —— 恰好卡在 150ms 门槛上，判据近乎**恒判"延续"**（历史上"偏快有分"只是窗口偏早撞进静音）。
故 v6 同时换用**能量口径**的 `onset_voiced_mask`（RMS 为主、f0 为辅），并在外扩 400ms 的检测窗内搜索
"换气→再起唱"跳变。

**真容器同素材对比（41/41 PASS）**：

| 素材 | v5 | v6 |
|---|---|---|
| 连奏跟唱（`bpm_ratio=0.826`） | pitch 74.01 / rhythm **None** / overall 54.72 | pitch **84.67** / rhythm **79.42** / overall **62.83** |
| 句间 372ms 换气 | pitch 57.06 / rhythm **None（0/6 句）** / overall 46.45 | pitch **81.92** / rhythm **42.61（6/6 句）** / overall **52.84** |

归档：`worklog/BUG实测/偏慢跟唱无节奏分-起唱判据与句窗弯折.md`；口径入 docs/06 §9.4（v6 小节）。

**已知边界（未根治）**：整首 DTW 仍是 ±10% Sakoe-Chiba 带，"偏慢 20% + 每句换气"（实测总时长 +39%）这类
累积形变远超带宽 → 窗口放置仍会漂（v6 借 onset 比值缓解）；后续可按 onset 比值**预拉伸**用户序列后再对齐（另案）。

补充建议（仍有效）：把 `local/sing_test_user.wav` 换成**带换气间隔**的素材（生成方式见 `scripts/sing_container_test.py:gapped_fixture`），否则演示链路测不到"节奏分档"的真实形态。

## 5. 其他观察（非缺陷，登记备查）

### 5.0 F2（复测发现并已修复）：容器内 Python→Java 内部委托全部失效

- **现象**：容器内把某歌 refs 降级/门禁置 missing 后，提取任务重建成功但 `songs.pitch_ref_status` **翻不回来**，
  日志 `pitch status 委托失败 … Connection refused`；新环境首次提取 / LRC 重写 / 提取器换代后歌曲永久 40905。
- **根因**：`config.py` 默认 `java_base_url=http://localhost:8080`（裸跑正确），但 `docker-compose.yml`
  **从未**给 python-api 设 `APP_JAVA_BASE_URL` → 容器内 localhost 指自己 → 三个内部委托（pitch-status / level / checkin）全断。
- **修复**：compose python-api 显式 `APP_JAVA_BASE_URL: http://java-api:8080`（+ `.env.example` 注释说明两套语境）。
- **验证**：同一实验（song 3 refs→pyin-v1 + 门禁 missing）修复前停在 missing、修复后 90s 内自动翻 `ready` 且无失败日志。
- **归档**：`worklog/BUG实测/容器内内部委托地址错-参考旋律门禁翻不了.md`。
