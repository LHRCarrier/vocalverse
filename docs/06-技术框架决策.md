## 1. 总体架构与调用拓扑（已拍板）

```
┌──────────── Browser (Vue3 + TS) ────────────┐
│  ① 业务/登录 API ——→ Java:8000（管理端+JWT签发）│
│  ② 语音/LLM/推荐热路径 ——→ Python:8000（直连）   │
└─────────────────────────────────────────────┘
        Java ←—— 内部 REST（service-token）——→ Python
                │                    │
        PostgreSQL（Alembic 唯一 schema 真源）  Redis（会话/缓存/限流）
```

| 服务 | 职责 | 明确不做 |
|---|---|---|
| Python (FastAPI) | ASR / TTS / 发音评分 / 唱歌评分 / LLM 场景扮演 Agent / 推荐 / 水平预测 / 埋点落库 | 不做管理端 CRUD、不做 JWT 签发 |
| Java (Spring Boot) | 用户管理、场景/歌曲/LRC 库 CRUD、工单、评价看板（可选）、JWT 签发 | **严禁进入语音/SSE/LLM 热路径**；不做 DDL（`ddl-auto=none`） |
| 前端 (Vue3+TS) | 页面、录音、SSE 消费、音频队列播放、埋点上报、报表可视化 | 不做 App（PWA/响应式覆盖移动端） |

关键点：
- 语音热路径（录音→ASR→评分→LLM→TTS→SSE）**前端直连 Python**，少一跳；
- 内部鉴权：Java 签发 HS256 access JWT（共享 secret），Python 验签；Java↔Python 内部调用加 `X-Service-Token` 头；
- 内部通信纯同步 REST（超时 3s），不上消息队列；异步用 Redis 任务状态轮询。

## 7. API 契约（契约真源 = `docs/api/`）

- 统一 envelope：`{code:int, message:string, data:object|null}`，成功 `code=0`；HTTP 状态码管传输错误、code 管业务语义；错误码表见 `docs/api/error-codes.md`。
- **不做运行时 codegen（杜绝 DTO 双写）**：契约真源 = Python `/openapi.json` + Java `/v3/api-docs` + `docs/api/`（envelope/错误码）。前端 client 基类（请求封装/错误码解析）手写保留；**DTO 及请求/响应的 TS 类型由 `openapi-typescript` 在构建期从 OpenAPI 生成**（2026-08-31 已落地：`apps/web` 的 `pnpm gen:api` 命令 + 契约快照 `src/api/specs/python-openapi.json` → 生成文件 `src/api/generated/python-api.d.ts` 入库；后端改契约后重跑生成即可暴露断点）——解决"改后端契约→手工同步前端类型"的跨语言维护痛点。**CI 双关卡**：python-ci 校验「快照 == 后端 `app.openapi()`」、frontend-ci 校验「生成文件 == 快照（`pnpm gen:api` 后 `git diff` 为空）」；开发侧一步刷新 = `scripts/refresh-openapi.ps1`（导出快照 + 重新生成）。Java 侧 DTO 仍手写（Swagger 契约保障）。
- 鉴权：access JWT **15min**（`Authorization: Bearer`）+ refresh JWT **7d**（httpOnly + SameSite=Lax + Secure cookie，`/api/auth/refresh`）；Java 签发，Python 共享 secret 验签。
- CORS：白名单 `http://localhost:5173`；限流（Redis）：登录 5 次/分/IP、LLM/评分 30 次/用户/时、ASR/TTS 60 次/用户/时（429 + Retry-After）。

## 8. 音频与流式（关键决策）

| 项 | 决策 |
|---|---|
| 录音 | `audio/webm;codecs=opus`（MediaRecorder，失败回退其他 mime）；**v0 录完整段再上传（非流式分片）** |
| 限制 | 单次语音 ≤60s、唱歌 ≤180s、体积 ≤20MB（超限 413） |
| 下行流 | **SSE**（服务端→前端单向），不做 WebSocket（本期无双工/打断需求） |
| 转写 | **faster-whisper small + int8 + CPU** + Silero VAD；medium 仅离线/有 GPU 时用 |
| TTS | `TTSClient` 接口：默认 **edge-tts**，`AZURE_TTS_KEY` 存在时切 Azure；CI 不调真 TTS；**demo 保底 = 常用台词预合成离线 mp3** |
| 排队播放 | 以**音频为时间轴权威、文本降级为字幕**：LLM 按句切分 → 逐句 TTS → SSE 推 `text_delta` + `audio_chunk`，前端队列顺序播放（`preload=auto`），字幕跟随当前音频段 |
| 音频存储 | demo 用本地卷 `./data/audio`（多容器共享）；生产预留 S3/MinIO 接口抽象，本期不引入 |
| 模型缓存 | **HF 模型缓存挂卷**（`hf-cache:/root/.cache/huggingface`），避免容器重建重复下载 ~500MB；`lifespan` 启动预热 whisper 模型（防首个请求卡 30s；预热失败仅告警不阻塞启动） |
| 并发与线程模型 | ① **>10ms 的 CPU 工作必须进 `anyio.to_thread`/线程池**（torch/librosa/pyin 直接放 async 处理器会阻塞整个事件循环；SSE 心跳都会断）；② uvicorn **`--workers 1` 显式声明**（whisper 内部自带 C++ 线程池，多 worker 每进程各载 ~500MB 模型，且并发收益为负）；③ 模型侧信号量（whisper 并发 **2**，与讯飞 ISE 一致），多请求排队不雪崩；④ 容器内存 **≥2GB**（compose 中声明）；⑤ 唱歌/长音频评分走「Redis 任务状态轮询」异步化（M3 必项，不许退化为同步等待） |
| 延迟口径 | 按场景分层（docs/09 P0-#2 修正）：**对话短轮次（≤15s 语音）目标 3~5s 反馈**（上传 1~2 + ASR≈2 + 评分≈1 + LLM 首 token 1~2 + TTS 1~2）；**≤30s 演示录音目标 5~8s**；全程 ≈7~10s。M2 第 1 周做 **ASR 基准试验**（15s/60s 实测 RTF 写入本表并校准）；演示话术「录音后 3~5 秒内反馈（短句）/ 5~8 秒（长录音）」 |

## 9. 功能口径决策（需求官 63 问的定稿）

### 9.1 四项检查点指标（独立统计，01 的「三项」为笔误）

| 指标 | 定义 |
|---|---|
| 点击率 CTR | 推荐内容被点击会话数（去重）/ 推荐内容曝光会话数；窗口 = 曝光后 30min |
| 完成率 | 口语 = 单次对话达 **5 轮或 2min** 以上；唱歌 = 整首逐句评分结束；完成率 = 完成单元数 / 发起单元数（会话级去重） |
| 互动率 | 会话内互动率 = 用户主动发消息轮数 / 会话分配轮数；另列功能互动（点示范/纠错/二次录制）作补充 |
| 跳出率 | 进入场景/歌曲页后 **30s 内无任何有效事件**（录音开始/播放/点击）记 1 跳；跳出率 = 跳出会话 / 进入会话 |

埋点事件（服务端落库 + 会话去重 + 维度：年龄组/水平档/场景/歌曲/渠道/时间）：`page_view / scene_start / recording_start / recording_complete / score_event / recommend_impression / recommend_click / practice_complete / fun_action`。

### 9.2 水平分级与入学测试

- **4 档 L1~L4**；综合分 `S = 0.4·发音 + 0.3·语法 + 0.3·流利度`；`S≥85→L4`、`70~84→L3`、`55~69→L2`、`<55→L1`（写入配置可调）。
- 入学测试 = **5 条固定朗读句 + 1 轮 QA**（admin 题库预置，保证可复现）；判定 = 综合分公式。
- 年龄组**只驱动 TTS 语速/音色/默认难度档**（3 语速档 × 3 音色，默认按年龄预选、设置页可改）；内容只按「难度档」组织（4 档，非 age×level 全正交）。
- 「交互数字人」= **2D 形象 + 说话动画 + TTS 实时语音**；明确放弃 3D/口型驱动（SadTalker/Wav2Lip），答辩口径「交互+语音+可见形象」。

### 9.3 评分口径

- 发音/流利度取讯飞 ISE（16k wav、并发信号量 2、整句批量；免费额度监控）；语法由 **DeepSeek/LLM 对转写文本判定**（0-100 + 错误类型 + 改法），进报告「语法/表达」子项（拍板为「暂定」，若演示不稳定回退为「砍语法项、口径改发音/流利度/完整度」并在全文档同步）。
- 错误定位默认**单词级**，重难点词给音素级提示 + 正确示范（TTS）。
- 场景内容相关度**不进量化总分**；LLM 只做引导与润色反馈。

### 9.4 唱歌评分（自研，M3 做深）

- 音准 = 逐句基频与**离线预提取的参考旋律音高序列**偏差（cent）映射（≤50→90+ / ≤100→70~90 / ≤200→50~65 / >300→<40）；节奏 = onset/beat 与 LRC 时间戳的**相对** DTW 偏差映射（≤150ms→90+ / ≤300→75~90 / ≤600→55~75 / >1000→<50）；发音 = **复用口语评分引擎**。
- 综合 = `0.5·音准 + 0.2·节奏 + 0.3·发音`。
- 对齐：先按整体 BPM 倍率粗对齐 → Sakoe-Chiba window（≤10%）+ 局部斜率约束子序列 DTW 精对齐；音高轮廓先归一化。
- F0：librosa **pyin**（说话 75~300Hz、唱歌 65~800Hz；frame 2048/hop 512；清浊门限过滤静音）；**不引 crepe/TensorFlow**（若需更高精度，隔离独立 venv）。
- 人工抽检：5 首 × 每首 5 句，2 人打 0-100，与算法相关 **r≥0.7**，出具验证报告进答辩材料。

### 9.5 推荐与水平预测（M3 演示化）

- item 候选池 = 场景 + 歌曲 + 听力素材（均带难度/类型/兴趣标签）。
- 冷启动 = 入学测试档 + 兴趣标签 + 内容相似；**在线协同过滤用预置模拟行为矩阵驱动（明确标注 demo 验证，不做真实在线学习）**。
- 水平预测模型：特征 = 练习行为 + 近期综合分，目标 = **预估/未来水平**（≠入学测试档，避免循环），用于进步趋势展示；用 sklearn 合成数据训练，走接口。
- **训练一次、启动加载**（docs/09 3.2-4）：推荐/预测模型训练完成后 `joblib.dump` 持久化，服务启动时加载；**严禁每请求重训**（否则推荐接口数秒级延迟）。
- 推荐「生效」验收：3 画像用户（成年中级-场景 / 青少年初级-歌曲 / 老年高级-新闻慢速）top-3 互异 + 命中兴趣标签 ≥60%。

### 9.6 场景、社区、Java 管理端

- 场景：**4~5 个**（生活：咖啡馆、机场；工作：面试；学习：图书馆），每个含角色设定/开场白/目标语料/难度分级；会话默认 **5~8 轮、目标 2~3min**，超 8 轮 LLM 自动收尾（总结+评分）。
- 社区最小版 = **打卡（单日 ≥1 次口语练习）+ 成绩卡片（canvas 生成图片下载 + Web Share）+ 只读打卡动态流 + 点赞**；**不做双人实时对练**；答辩口径「分享+激励」。
- Java 管理端最小集 = 用户管理（列表/查询/禁用启用/档案）+ 场景/歌曲库 CRUD（含上下架）+ **工单**（用户提交反馈/报错/纠误 → 新建/处理中/已解决/关闭）+（P2 可选）评价看板；权限 = 简单 admin/user 角色。
- 海量资源：场景模板 + 歌曲库作为可扩展内容库模型 + **1 个听力素材示例**（含 ASR 字幕），答辩解释为「架构能力」而非真海量。
- 移动端：不做原生 App，PWA/响应式覆盖；答辩话术「移动端 Web/PWA 优先，原生 App 列为扩展」。

### 9.7 合规与数据

- **只存评分/转写/元数据**；原始音频默认 24h 过期清理（临时/内存处理），demo 不采真实用户数据。
- 未成年人：产品范围声明「面向成年学习者演示；儿童/青少年为目标人群，未成年场景需监护人同意，本期不采集真实未成年人数据」。
- 公开仓库红线扩充：API Key、密码、真实用户数据、训练集原始文件、模型权重、原始音频、**商用音乐**均禁提交；PR 模板加检查项。

## 10. 数据库与 Redis

- 表：`users`、`user_profiles`（level、goal、tags、voice_pref）、`placements`、`scenarios`、`scenario_messages`、`sessions`、`attempts`（transcript、overall/pron/gram/flu jsonb）、`scores`（音素级明细）、`songs`、`lrc`（offset_ms/text/seq）、`sing_attempts`（逐句音准/节奏/发音）、`events`（埋点）、`reports`、`tickets`（工单）、`refresh_tokens`。
- **Alembic 唯一 schema 真源**；Java `ddl-auto=none`（只映射）；约束/FK/索引**只建在 Alembic**（JPA 纯映射，防漂移）；CI 加一致性探针（当前为单头断言，`alembic check` 待 M2 接 PG 后启用）。
- **SQLite 单测 vs PG JSONB 兼容**（docs/09 4.3）：字段一律用 `sa.JSON().with_variant(postgresql.JSONB, "postgresql")` 声明，避免 M2 建表后 SQLite 测试炸掉；现在就把该声明写入模型基类约定。
- Redis：会话（`session:{id}` TTL 30min）、缓存（场景/歌曲列表、推荐结果 TTL 5min）、限流计数、评分任务状态、SSE 缓冲（可选）；**不存业务主数据**；compose 固定必含，Python 侧提供内存 fallback（启动参数）。
- **Redis 不可用时的行为**（修正 docs/09 P1-#7）：**不拒绝启动**——会话/缓存切内存 TTL 实现；限流退化为宽松模式（按进程内计数）；`/readyz` 的 `data.status` 报 `degraded` 并附 `redis:false`；评分任务状态走进程内字典。演示主路径「省 Redis 也能起」的 ADR 语义保持不变。

### 10.1 讨论记录：为何不用 Prisma（2026-08-31 组长提问，拍板维持本方案）

- **提问**：数据库管理用 Prisma 怎样（参考 ai4u 项目的经验）。
- **结论**：**维持 SQLAlchemy 2 + Alembic**，不引入 Prisma。理由：
  1. **语言契合**：本项目 DB 消费方是 Python（FastAPI 语音/评分/推荐）与 Java（Spring Boot 管理端）；Prisma 官方客户端仅支持 TS/JS（及 Go/Rust），Python 只有社区版 `prisma-client-py`（非官方、需额外 codegen + Rust 引擎二进制，Windows/CI 有额外坑），**Java 没有任何 Prisma 客户端**——引入后「真源」仍是两套映射，DX 收益被抵消。
  2. **代价**：迁移需重写 M1 已合入且 CI 全绿的数据层（Alembic 骨架、测试、Dockerfile、CI 一致性探针），两套 ORM（Python 社区客户端 + Java JPA）并存更复杂。
  3. **收益重合**：Prisma Migrate 的「单文件 schema + 自动迁移」，Alembic `autogenerate` 已等价提供，且原生融入 Python 生态。
- **答辩口径**：若被问「为什么不用 X」——「统一 schema 迁移由 Alembic 承担；Prisma 官方不支持 Python，Java 无客户端，为避免双语言双 ORM 不一致风险，本架构选择原生融入栈的 SQLAlchemy+Alembic；若未来引入 Node 服务可再评估」。
