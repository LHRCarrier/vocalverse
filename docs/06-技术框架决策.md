## 1. 总体架构与调用拓扑（已拍板）

```
┌──────────── Browser (Vue3 + TS) ────────────┐
│  ① 业务/登录 API ——→ Java:8000（管理端+JWT签发）│
│  ② 语音/LLM/推荐热路径 ——→ Python:8000（直连）   │
└─────────────────────────────────────────────┘
        Java ←—— 内部 REST（service-token）——→ Python
                │                    │
        PostgreSQL（Alembic 唯一 schema 真源）  Redis（会话/缓存/限流）
```

| 服务 | 职责 | 明确不做 |
|---|---|---|
| Python (FastAPI) | ASR / TTS / 发音评分 / 唱歌评分 / LLM 场景扮演 Agent / 推荐 / 水平预测 / 埋点落库 | 不做管理端 CRUD、不做 JWT 签发 |
| Java (Spring Boot) | 用户管理、场景/歌曲/LRC 库 CRUD、工单、评价看板（可选）、JWT 签发、**社区内容 C 端（feed/发帖/评论/互动 5 表写方，2026-09-06 登记 · docs/37）** | **严禁进入语音/SSE/LLM 热路径**；不做 DDL（`ddl-auto=none`） |
| 前端 (Vue3+TS) | 页面、录音、SSE 消费、音频队列播放、埋点上报、报表可视化 | 不做 App（PWA/响应式覆盖移动端） |

关键点：
- 语音热路径（录音→ASR→评分→LLM→TTS→SSE）**前端直连 Python**，少一跳；
- 内部鉴权：Java 签发 HS256 access JWT（共享 secret），Python 验签；Java↔Python 内部调用加 `X-Service-Token` 头；
- 内部通信纯同步 REST（超时 3s），不上消息队列；异步用 Redis 任务状态轮询。

## 7. API 契约（契约真源 = `docs/api/`）

- 统一 envelope：`{code:int, message:string, data:object|null}`，成功 `code=0`；HTTP 状态码管传输错误、code 管业务语义；错误码表见 `docs/api/error-codes.md`。
- **不做运行时 codegen（杜绝 DTO 双写）**：契约真源 = Python `/openapi.json` + Java `/v3/api-docs` + `docs/api/`（envelope/错误码）。前端 client 基类（请求封装/错误码解析）手写保留；**DTO 及请求/响应的 TS 类型由 `openapi-typescript` 在构建期从 OpenAPI 生成**（2026-08-31 已落地：`apps/web` 的 `pnpm gen:api` 命令 + 契约快照 `src/api/specs/python-openapi.json`、`java-openapi.json` → 生成文件 `src/api/generated/python-api.d.ts`、`java-api.d.ts` 入库；后端改契约后重跑生成即可暴露断点）——解决"改后端契约→手工同步前端类型"的跨语言维护痛点。**CI 三关卡**：python-ci 校验「Python 快照 == 后端 `app.openapi()`」、java-ci 校验「Java 快照 == springdoc 实时渲染」（`ContractSnapshotTest`，跑在 `mvn verify`）、frontend-ci 校验「生成文件 == 快照（`pnpm gen:api` 后 `git diff` 为空）」；开发侧一步刷新 = `scripts/refresh-openapi.ps1`（导出双快照 + 重新生成；Java 快照亦可 `CONTRACT_SNAPSHOT_GENERATE=1` 由测试重写，仅限本地）。Java 侧 DTO 仍手写（Swagger 契约保障）。
- 鉴权：access JWT **15min**（`Authorization: Bearer`）+ refresh JWT **7d**（httpOnly + SameSite=Lax + Secure cookie，`/api/auth/refresh`）；Java 签发，Python 共享 secret 验签。
- CORS：白名单 `http://localhost:5173`；限流（Redis）：登录 5 次/分/IP、LLM/评分 30 次/用户/时、ASR/TTS/ISE 60 次/用户/时（429 + Retry-After）。**2026-09-09 唱歌 P0 拍板（D3 + R-16 闭合）**：ISE 桶对齐 ADR 口径改为 **30/h**；另新增子资源桶 **`sing`：5 次/用户/时**（整首跟唱评分计 1，与 asr/ise/llm 独立计数）。

## 8. 音频与流式（关键决策）

| 项 | 决策 |
|---|---|
| 录音 | `audio/webm;codecs=opus`（MediaRecorder，失败回退其他 mime）；**v0 录完整段再上传（非流式分片）** |
| 限制 | 单次语音 ≤60s、唱歌 ≤180s、体积 ≤20MB（超限 413） |
| 下行流 | **SSE**（服务端→前端单向），不做 WebSocket（本期无双工/打断需求） |
| 转写 | **faster-whisper small + int8 + CPU** + Silero VAD；medium 仅离线/有 GPU 时用 |
| TTS | `TTSClient` 接口：默认 **edge-tts**，`AZURE_TTS_KEY` 存在时切 Azure；CI 不调真 TTS；**demo 保底 = 常用台词预合成离线 mp3** |
| 排队播放 | 以**音频为时间轴权威、文本降级为字幕**：LLM 按句切分 → 逐句 TTS → SSE 推 `text_delta` + `audio_chunk`，前端队列顺序播放（`preload=auto`），字幕跟随当前音频段 |
| 音频存储 | demo 用本地卷 `./data/audio`（多容器共享）；生产预留 S3/MinIO 接口抽象，本期不引入。**2026-09-10 修正（BUG-5）**：用户录音文件名扩展名按**魔数嗅探**决定（浏览器 MediaRecorder 实为 `audio/webm;codecs=opus`，历史实现一律存 `.mp3` → 回放 `Content-Type: audio/mpeg` 与内容不符，严格客户端可能拒播）；`GET /api/v1/audio/{name}` 回放时**嗅探优先于扩展名**（老文件零迁移）；实现 `app/audio/upload.py:sniff_audio_ext/resolve_media_type`。**2026-09-10 增（P0-6 · 上传体量双层护栏）**：FastAPI 在**解析 body 之后**才求解依赖（`request.form()` 早于 `solve_dependencies`），Starlette 对 >1MB 的 multipart part 落盘且无总量上限 → 匿名大 body 可打爆容器。故：**应用层** `BodySizeLimitMiddleware`（`app/core/body_limit.py`，注册于 `main.py`）按 `Content-Length` 预检 + `receive` 计数护栏，超 `max_upload_bytes + 1MB` 立即返回 **41301** envelope（**不读 body**）；**边缘层** `apps/web/nginx.conf` `client_max_body_size 21m`（留 multipart 封装余量）+ `error_page 413` 回 JSON envelope。20MB 仍由 `sing/service.py` 的业务校验兜底（`validate_audio_bytes`） |
| 模型缓存 | **HF 模型缓存挂卷**（`hf-cache:/root/.cache/huggingface`），避免容器重建重复下载 ~500MB；`lifespan` 启动预热 whisper 模型（防首个请求卡 30s；预热失败仅告警不阻塞启动） |
| 并发与线程模型 | ① **>10ms 的 CPU 工作必须进 `anyio.to_thread`/线程池**（torch/librosa/pyin 直接放 async 处理器会阻塞整个事件循环；SSE 心跳都会断）；② uvicorn **`--workers 1` 显式声明**（whisper 内部自带 C++ 线程池，多 worker 每进程各载 ~500MB 模型，且并发收益为负）；③ 模型侧信号量（whisper 并发 **2**，与讯飞 ISE 一致），多请求排队不雪崩；④ 容器内存 **≥2GB**（compose 中声明）；⑤ 唱歌/长音频评分走「Redis 任务状态轮询」异步化（M3 必项，不许退化为同步等待） |
| 延迟口径 | 按场景分层（docs/09 P0-#2 修正）：**对话短轮次（≤15s 语音）目标 3~5s 反馈**（上传 1~2 + ASR≈2 + 评分≈1 + LLM 首 token 1~2 + TTS 1~2）；**≤30s 演示录音目标 5~8s**；全程 ≈7~10s。M2 第 1 周做 **ASR 基准试验**（15s/60s 实测 RTF 写入本表并校准）；演示话术「录音后 3~5 秒内反馈（短句）/ 5~8 秒（长录音）」。**2026-09-01 实测修正（POC-1=docs/18 §1-P1）**：edge-tts 单句合成网络往返 mean **1.34s**（10 次，en-US-JennyNeural）、3 句串行 4.12s（均摊 1.37s/句）→ 首声预算按「逐句 TTS + 并发预热 + 开场/常用句预合成」重估为 **流式首声 3~6s**；**2026-09-09 落地「开场/常用句预合成」**——`warm_tts_cache` 启动 + 建会话双触发（已知文本：published 场景开场白 + target_corpus 短语 + 影子逐句示范；并发 4 限速、去重、失败仅日志），命中即 0ms 出声（开场白/示范/重听），LLM 流式回复正文无法预知仍走 P0-5 边生成边合成；`score_delta` 迟到 ≤3s 后显示"未评测"（docs/14 §3.2）。**POC-3=ASR 基准试验已实跑（2026-09-01，scripts/poc/whisper_rtf.py，edge-tts 合成语音，small/int8/CPU）**：mean RTF **0.328**（短音频）/ **0.258**（长音频），均 ≤0.6 → **演示话术「录音后 3~5 秒内反馈」成立**；whisper 模型加载 ≈45s（含下载；生产预热见本表"模型缓存"行）。**POC-2（DeepSeek 流式 META）待密钥实跑**。

## 9. 功能口径决策（需求官 63 问的定稿）

### 9.1 四项检查点指标（独立统计，01 的「三项」为笔误）

| 指标 | 定义 |
|---|---|
| 点击率 CTR | 推荐内容被点击会话数（去重）/ 推荐内容曝光会话数；窗口 = 曝光后 30min |
| 完成率 | 口语 = 单次对话达 **5 轮或 2min** 以上；唱歌 = 整首逐句评分结束；**答辩（2026-09-01 M2 登记）= 答满设定题数（sessions.assigned_turns 快照）或 ≥2min**；完成率 = 完成单元数 / 发起单元数（会话级去重） |
| 互动率 | 会话内互动率 = 用户主动发消息轮数 / 会话分配轮数；**救援轮（hint/自动示范/AI 代说）同时从分子+分母剔除**（2026-09-01 M2 修正），另计"功能互动/困难度"（含 trigger_by user/system）作补充；**答辩会话通用互动率 = N/A**，专属「回答率」= 有效作答轮次 / 提问轮次 |
| 跳出率 | 进入场景/歌曲页后 **30s 内无任何有效事件**（录音开始/播放/点击）记 1 跳；跳出率 = 跳出会话 / 进入会话 |

埋点事件（服务端落库 + 会话去重 + 维度：年龄组/水平档/场景/歌曲/渠道/时间）：`page_view / scene_start / recording_start / recording_complete / score_event / recommend_impression / recommend_click / practice_complete / fun_action / corpus_hit`（**2026-09-01 M2：9→10 类**）；`fun_action` payload 的 action 枚举含 `demo/hint/retry` 并带 `trigger_by`。**2026-09-05 自由对话（docs/14 §12）追加 2 类：`free_chat_open / free_chat_turn`（payload `{audio: bool}`）→ 10→12 类；功能行再追加 3 类：`free_chat_switch{to}` / `free_chat_reset` / `free_chat_rate{rate}` → 12→15 类（其中 `free_chat_reset` 随功能行改版（2026-09-05 晚：新对话按钮恢复）重新触发；`free_chat_rate` 因语速取消仍为预留白名单条目）**。

### 9.2 水平分级与入学测试

- **4 档 L1~L4**；综合分 `S = 0.4·发音 + 0.3·语法 + 0.3·流利度`；`S≥85→L4`、`70~84→L3`、`55~69→L2`、`<55→L1`（写入配置可调）。
- 入学测试 = **5 条固定朗读句 + 1 轮 QA**（admin 题库预置，保证可复现）；判定 = 综合分公式。
- 年龄组**只驱动 TTS 语速/音色/默认难度档**（3 语速档 × 3 音色，默认按年龄预选、设置页可改）；内容只按「难度档」组织（4 档，非 age×level 全正交）。

### 9.3 评分口径

- 发音/流利度取讯飞 ISE（16k wav、并发信号量 2、整句批量；免费额度监控）；语法由 **DeepSeek/LLM 对转写文本判定**（0-100 + 错误类型 + 改法），进报告「语法/表达」子项（拍板为「暂定」，若演示不稳定回退为「砍语法项、口径改发音/流利度/完整度」并在全文档同步）。
- **流利度时间戳特征（辅助，2026-09-04 定）**：faster-whisper 开 `word_timestamps=True` → 词级时间戳 → `app/audio/fluency.py` 纯函数出辅助特征（不另起一套流利度，ISE fluency 仍为权威分，docs/07 Q30）：`wpm`（词数/有效说话段分钟，排除录音首尾静默）、`articulation_rate`（去除停顿后的纯发音速率）、停顿统计（相邻词间隙 ≥0.5s 计一次，≥1.0s 计长停顿；仅词间、不含首尾静默）、`pause_ratio`（停顿总时长/说话段）；落 `attempts.wpm` + `attempts.details.fluency`，报告经 `metrics.attempts[].wpm/fluency_features` 透出；为影子跟读三维（语速/停顿/连读，local/28）与 META 内容子分提供特征源。
- **影子跟读评分（2026-09-04 DoD ④ 定）**：素材 = `shadow_materials`（Java 写、Python 读；`text_content` 按行分句、`wpm` 原声语速）；会话 `kind=shadow` 逐句跟读：出句（TTS 示范）→ 跟读录音 → ASR 特征 + **ISE 以题卡句为参考**（ISE 主场，`category=read_sentence`）→ 三维分 `0.4·发音 + 0.3·语速匹配 + 0.3·停顿密度`（素材缺 wpm → 语速匹配维缺省并按剩余权重归一；重音落点/连读识别留待 M3 前端韵律引擎，登记 P2 不伪造）；分段阈值：语速匹配 = |user−ref|/ref ≤10%→95 / ≤20%→85 / ≤35%→70 / ≤50%→55 / 其余 40；停顿密度 = pause_ratio ≤5%→95 / ≤10%→85 / ≤20%→70 / ≤35%→55 / 其余 40；落 `attempts`（kind=shadow_speech，details.shadow 三维明细）+ 报告透出；LLM 不参与（规则教练笔记）。
- **META 语义子分（③，2026-09-04 定）**：`[-META-]` 契约增量 `content:{score,note}`（内容相关度/充实度）+ `vocab:{score,note}`（词汇多样性），LLM 判定（主流与补偿流同口径）；进 SSE meta_block、`scenario_messages.meta` 与报告 `metrics.semantic`（聚合均分+轮次）；**不进量化总分**（docs/07 Q38 拍板 C 落地：S=0.4·发音+0.3·语法+0.3·流利度 不变），纯展示口径；防御：模型输出裸数字/字符串 → 该子分置 None 不伪造。
- 错误定位默认**单词级**，重难点词给音素级提示 + 正确示范（TTS）。
- 场景内容相关度**不进量化总分**；LLM 只做引导与润色反馈。

### 9.4 唱歌评分（自研，M3 做深）

- 音准 = 逐句基频与**离线预提取的参考旋律音高序列**偏差（cent）映射（≤50→90+ / ≤100→70~90 / ≤200→50~65 / >300→<40）；节奏 = onset/beat 与 LRC 时间戳的**相对** DTW 偏差映射（≤150ms→90+ / ≤300→75~90 / ≤600→55~75 / >1000→<50）；发音 = **复用口语评分引擎**。
- 综合 = `0.5·音准 + 0.2·节奏 + 0.3·发音`。
- 对齐：先按整体 BPM 倍率粗对齐 → Sakoe-Chiba window（≤10%）+ 局部斜率约束子序列 DTW 精对齐；音高轮廓先归一化。
  - **整首粗对齐的规模护栏（P1-11，2026-09-10 修复）**：成本矩阵与累积矩阵各占 `n²×8B`，带内 DP 是纯 Python 双层循环（`≈2·w·n` 次，`w = 10%×n`）——180s@32ms = **5625 帧 → 实测 48.3s / 506MB**（`sing_concurrency=2` 时两首并发近 1GB，容器 2GB 还要装 whisper，有 OOM 风险）。旧护栏 `n > 6000 → step=2` 是**死代码**（5625 < 6000 永不触发，"允许的最长歌"100% 走最坏路径）。现按目标帧数自适应：`n ≤ 4000` 全分辨率；否则 `step = ceil(n / 3000)` → 180s 取 **step=2（2813 帧：127MB / 8.7s，5.6× 提速、4× 省内存）**。代价 = offset 量化到 `hop×step = 64ms`（远小于节奏分档阈值 150/300/600ms）；**只降采样整首粗对齐这一层**，逐句局部 DTW 与起唱检测仍是全分辨率。
  - 后续可选治本项（未做，需拍板）：带内 DP 改**反斜对角向量化** + 成本按需计算 → 全分辨率下预估 1~2s / ~10MB（属核心对齐原语重写，必须与现实现对拍等价）。
- F0：librosa **pyin**（说话 75~300Hz、唱歌 65~800Hz；frame 2048/hop 512；清浊门限过滤静音）；**不引 crepe/TensorFlow**（若需更高精度，隔离独立 venv）。
- 人工抽检：5 首 × 每首 5 句，2 人打 0-100，与算法相关 **r≥0.7**，出具验证报告进答辩材料。
  - **抽检口径升级（2026-09-09 · FF 模糊化，P1 落地）**：评委从「打 0~100 点值」升级为「打区间分 [lo,hi]」——区间宽度即犹豫度（点值 = lo==hi）；区间 → Fermatean 模糊数 FFN(μ,ν)（`μ=s(1−h)`、`ν=(1−s)(1−h)`，μ³+ν³≤1 恒成立），得分函数 S=μ³−ν³ 仅作**对照列**（评审主口径 = 透明的区间中点）；一致性判定 = **区间引导 r 置信区间下界 ≥0.7**（每句在 [lo,hi] 均匀采样 ×500，2.5/97.5 分位）——回答「r≥0.7 对评委犹豫是否稳健」（点值口径没有这一问）；辅以模糊同意率（算法分 ∈ 专家区间）与评委内部分歧。判定三档 pass/weak/fail（n<5 → insufficient）。实现：`services/python/app/audio/review.py`（纯函数，零依赖、零 API 影响）+ `scripts/sing_review.py`（CLI 报告生成，评审数据 JSON 见脚本 docstring，实盘数据放 `local/`）。参考：Zhao & Huang, *Sci Rep* (2026) s41598-026-46791-5（FFS 编码专家犹豫思想；其 CRITIC/MAIRCA 面向多候选排序，与本场景不匹配故不引入）。

| R2 音准（音符命中率） | 只有"偏差多大"（cent 映射）；逐句 DTW + 移调 + 八度折叠能把**随机音高轨迹**贴靠到阶梯参考 → 乱唱也得 50~65 分（命中率 0% 却给 60.5） | 新增**音符命中率**（参考切音符 → 句级 DTW 路径映射 → 该音符区间内 ≥30% 帧命中 ±100 cent，**经移调补偿+八度折叠**）→ `pitch = cent映射分 × (0.6 + 0.4×命中率)`（**乘性衰减**，命中 0 → ×0.6、命中 1 → ×1.0）；命中率逐句落库 + 整首汇总。**不做硬阈值判罚**——实测命中率与"轮廓相关性"都无法区分"跑调真唱"（11~47%）与"乱唱"（14~50%），硬阈值会把跑调用户直接判"没唱" |
| R3 覆盖率置信度 | 2/6 有效句仍给综合分（仅文案提示） | `有效句/期望句` 三段线性：≥80% 全额 / 40~80% 线性 0.6→1.0 / **<40% → 不给综合分**（overall=None + `coverage_note`） |

留痕：`scoring_version='v4'`、`lines[i].note_hit_rate`、`alignment` 增 `note_hit_rate/user_coverage/coverage_conf/coverage_note`（docs/10 §4.3 同步）；旧 v2/v3 分不作废。效果对照：真机乱唱 52.92 → **综合 None**；跑调真唱 58.33 → 25.17（仍有分）；准唱 95 → 74（命中率衰减 17%）。详见 `worklog/BUG实测/乱唱也拿高分-评分鲁棒性缺陷.md`。

**口径 v5（2026-09-10 · P0 修复：R1 判据由整轨下沉为逐句）**——v4 的 R1 闸门可被绕过：`has_breath_structure` 只要全轨**任意一处** ≥150ms 静音即为真（手机录音起始那 1s 静音几乎必然满足），而 `_first_new_run` 对「窗口第 0 帧已有声」直接 `return 0` → `onset_dev=0` → `rhythm_score_from_dev(0)=95`：**乱唱/完全不跟拍恒得节奏 95**（v4 想修的真机 52.9 事件在常见录音形态下复活，见 `local/唱歌模块全链路拷问报告-2026-09-10.md` §1 Top 3）。

**口径 v6（2026-09-10 · 复测 F1 修复：句窗时间弯折 + 起唱判据换能量口径）**——容器全链路复测实测：**用户唱得比参考慢（`bpm_ratio<1`）时整首拿不到节奏分**（`reason='no_onset'` 6/6 句，`overall` 静默按 0.5/0.3 重算）；PG 历史 26 条 attempt 中 `ratio<1` 的**全部**无 `rhythm_score`，`ratio>1` 的都有。两个叠加根因：

| # | 根因 | v6 修复 |
|---|---|---|
| ①「有声」判定失效（**主因**） | 逐句起唱判据用 `f0 > 0` 判"有声"；而 librosa.pyin 在本配置（frame 2048=128ms + `fill_na=0`）下对**数字静音也大量判浊**（37s 换气素材 1119 帧中仅 39 帧为清音），再经 160ms 中值滤波后一次 372ms 真实换气只剩 ~150-190ms → 恰好卡在 150ms 门槛上：判据近乎**恒判"延续"** → 节奏维度要么恒 None，要么靠"窗口首帧恰好落在少数 0 帧"撞运气 | 新增 `onset_voiced_mask(f0, rms)`：**能量（RMS）为主**（`rms ≥ max(0.005, 0.12 × 75 分位)`）+ `f0>0` 为辅；无 rms（Fake/单测）时保持 `f0>0` 旧语义。能量不受中值滤波影响、对换气（≥15dB 衰减）敏感 |
| ②句窗起点未按速度弯折 | `win_start = ref_start + offset`（只有句长乘 `scale`）：`offset` 是 DTW 路径 delta 的**中位数**，偏慢时曲首偏大、曲尾偏小 → 后续句窗口落到**上一句句腹**（无前置静音）→ 判"延续" | 新增 `TimeWarp`（`offset + stretch × ref`）：stretch 取 **onset 仲裁的 `bpm_ratio`**（`window_scale`，独立于 DTW 带宽）但与**路径拟合斜率互证**（相差 >0.20 视为 onset 不可信 → 取路径拟合值，防纯音素材把窗口推出曲外）；截距 = 按该 stretch 的残差中位数 |

配套：起唱检测在**外扩 `TIME_WARP_WINDOW_PAD_MS=400ms` 的检测窗**内**向内扫**"换气→再起唱"跳变（v5 只看窗口首帧，窗口一旦被速度模型挪进句腹就永远判不出）；偏差对**期望位置**（`win_start`）计算而非窗口起点（否则外扩会把偏差人为归零 = 自证式打分）；`alignment` 增 `time_warp_stretch` + `windows_ms`（逐句用户时间轴窗口，发音抽样/图表/排障共用一份映射，杜绝口径分叉）。

## 10. 数据库与 Redis

- 表：`users`、`user_profiles`（level、goal、tags、voice_pref、**handle/tint 社区展示列 2026-09-06**）、`placements`、`scenarios`、`scenario_messages`、`sessions`、`attempts`（transcript、overall/pron/gram/flu jsonb）、`scores`（音素级明细）、`songs`、`lrc`（offset_ms/text/seq）、`sing_attempts`（逐句音准/节奏/发音）、`events`（埋点）、`reports`、`tickets`（工单）、`refresh_tokens`、**`posts`/`post_comments`/`post_interactions`/`follows`（社区内容 4 表 + `post_likes` 键改造 · Java 写 · 2026-09-06，docs/37 §3 明细）**。
- **Alembic 唯一 schema 真源**；Java `ddl-auto=none`（只映射）；约束/FK/索引**只建在 Alembic**（JPA 纯映射，防漂移）；CI 加一致性探针。**2026-09-01 M2 启用 `alembic check`（真 PG，零 diff 通过）**——因 SQLAlchemy 2.0.52 对 PG16 identity 列反射与 alembic `_user_compare_server_default` 上游不兼容（`'Identity' object has no attribute 'arg'`，1.18/1.19 均复现），env.py 以 `compare_server_default=False` 规避并登记（docs/11 Q-A06 自定义比较器待上游修复后恢复）；补偿门禁 = offline PG 渲染测试（JSONB/IDENTITY/表达式索引断言）+ 本轮真 PG 零 diff 实测。
- **SQLite 单测 vs PG JSONB 兼容**（docs/09 4.3）：字段一律用 `sa.JSON().with_variant(postgresql.JSONB, "postgresql")` 声明，避免 M2 建表后 SQLite 测试炸掉；现在就把该声明写入模型基类约定。
- Redis：会话（`session:{id}` TTL 30min）、缓存（场景/歌曲列表、推荐结果 TTL 5min）、限流计数、评分任务状态、SSE 缓冲（可选）；**不存业务主数据**；compose 固定必含，Python 侧提供内存 fallback（启动参数）。
- **Redis 不可用时的行为**（修正 docs/09 P1-#7）：**不拒绝启动**——会话/缓存切内存 TTL 实现；限流退化为宽松模式（按进程内计数）；`/readyz` 的 `data.status` 报 `degraded` 并附 `redis:false`；评分任务状态走进程内字典。演示主路径「省 Redis 也能起」的 ADR 语义保持不变。

### 10.1 讨论记录：为何不用 Prisma（2026-08-31 组长提问，拍板维持本方案）

- **提问**：数据库管理用 Prisma 怎样（参考 ai4u 项目的经验）。
- **结论**：**维持 SQLAlchemy 2 + Alembic**，不引入 Prisma。理由：
  1. **语言契合**：本项目 DB 消费方是 Python（FastAPI 语音/评分/推荐）与 Java（Spring Boot 管理端）；Prisma 官方客户端仅支持 TS/JS（及 Go/Rust），Python 只有社区版 `prisma-client-py`（非官方、需额外 codegen + Rust 引擎二进制，Windows/CI 有额外坑），**Java 没有任何 Prisma 客户端**——引入后「真源」仍是两套映射，DX 收益被抵消。
  2. **代价**：迁移需重写 M1 已合入且 CI 全绿的数据层（Alembic 骨架、测试、Dockerfile、CI 一致性探针），两套 ORM（Python 社区客户端 + Java JPA）并存更复杂。
  3. **收益重合**：Prisma Migrate 的「单文件 schema + 自动迁移」，Alembic `autogenerate` 已等价提供，且原生融入 Python 生态。
- **答辩口径**：若被问「为什么不用 X」——「统一 schema 迁移由 Alembic 承担；Prisma 官方不支持 Python，Java 无客户端，为避免双语言双 ORM 不一致风险，本架构选择原生融入栈的 SQLAlchemy+Alembic；若未来引入 Node 服务可再评估」。
