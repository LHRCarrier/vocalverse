## 第一部分 · 最致命的 5 个问题

1. **M3 的排期是假的**：3 人 2 周要做「唱歌评分 + 推荐 + 报表 + 埋点」四件事，还要叠加算法人（唯一的语音算法人力）在**同一时段**去租 GPU 做 wav2vec2 微调，且唱歌评分本身就是算法人自己做——数学上不成立，必须砍，但「砍谁」现在是悬而未决的重大决策。
2. **「语法」评分在当前技术栈里没有任何实现载体**：案例要求「指出发音、语法、流利度问题」，但 03 的讯飞评测只产出「发音/流利度/完整度」，没有任何工具提供「语法分」——这是整个报告中唯一真正的**虚构承诺**，答辩第一问就会被击穿。
3. **「三项指标」数出来是四个**，而四个指标（点击率/完成率/互动率/跳出率）**全部没有事件定义、没有分子分母、没有时间窗、没有维度**——检查点口径直接悬空，而这恰恰是案例明确要「量化」的部分。
4. **案例把「学习社区/社交互动」列为基础功能，但 02 把它标成 P2「可砍」**：砍到「打卡 + 成绩卡片」后没有任何用户间互动，「互相练习口语」一项是完全未兑现的基础功能缺口，答辩合规存在塌方风险。
5. **「入学测试 → 水平分级 → 场景难度 / 推荐 / 水平预测」这条数据依赖链的根节点是空的**：没有任何文档给出测试内容、判定方式、分数到档位的映射刻度——而这四件事全都同时读这个「水平档」。

## 第二部分 · 分维度问题清单

### 维度 1 · 范围与优先级

#### Q1｜P0/P1/P2 的判定依据是什么？谁定的？
- 为什么重要/矛盾点：02 把「推荐、报表、埋点、唱歌」全标 P1，却让 M3 两周做完唱歌+推荐+报表+埋点；P 级没有判定原则（对案例覆盖？对检查点不可缺？对 demo 说服力？），导致「优先级」与「排期」自相矛盾。
- 候选答案 A/B/C：A 按「案例必须 + 创新必验」；B 按「demo 可演示闭环」；C 按「三人工作量均衡」倒排。
- 推荐答案（含默认值/数字）：A+B 混合——P0=案例基础功能的口语闭环 + 创新功能两项（个性化、情景模拟）可验；P1=其余创新/检查点指标；P2=可砍；判定原则写进 02 开头。
- 涉及的文档/模块：02-功能规划、01-检查点。

#### Q2｜M4 答辩时「最小可演示闭环」是什么？
- 为什么重要/矛盾点：M4 只有「优化 + 演示数据 + 材料」，没定义哪条路径算「演示成功」，也没有兜底路径。
- 候选答案 A/B/C：A 口语闭环（注册→入学→场景对话→录音→评分→建议→报告）；B 唱歌闭环；C 两者都要，推荐/报表/社区后置；D 只演示口语。
- 推荐答案：C 的「演示级」（都可走通一次）+ 推荐/埋点作为屏录补充；给出一条 **5 分钟可复现**的演示脚本，落进 04 的 M4。
- 涉及的文档/模块：01-检查点、04-M4。

#### Q3｜唱歌与推荐都要在 M3，且都压到「算法人/全栈」头上，砍哪个？
- 为什么重要/矛盾点：唱歌=算法人（但算法人还要同窗做 wav2vec2），推荐=全栈(Python)；真正的冲突是**人力**而非模块。唱歌是产品名卖点（README 标题），推荐是案例创新功能，demo 都能演示，但时间只够一个做深。
- 候选答案 A/B/C：A 唱歌做深、推荐用模拟数据做浅；B 推荐做深、唱歌单曲演示；C 都做浅。
- 推荐答案：A——唱歌是差异化卖点与「自研亮点」候选；推荐用预置模拟行为矩阵演示「生效」，不做真实在线协同过滤。
- 涉及的文档/模块：02、04、01。

#### Q4｜三个「报告/报表」面到底谁给谁看？（单次口语报告 / 可视化报表 / 评价看板）
- 为什么重要/矛盾点：02 模块8「可视化报表」(用户)、03 的 LLM `generate_report`(单次)、02 模块13「评价看板」(管理员) 三者职责重叠且无边界，容易各写一套。
- 候选答案 A/B/C：A 用户看「单次报告+趋势报表」、管理员看「看板」；B 三者合并；C 砍看板。
- 推荐答案：A，三者各自独立接口与页面，但共享同一份「评分核心」数据模型；看板为 P2 可砍。
- 涉及的文档/模块：02、03。

#### Q5｜「工单管理」是案例明确要 Java 做的，但 02 的 Java 最小范围里没有它。做不做？
- 为什么重要/矛盾点：案例原文明确「Java（系统架构、工单管理）」；砍掉工单，「按案例要求用 Java」的答辩理由弱一半；但「工单对口语 App 是什么业务」没人定义。
- 候选答案 A/B/C：A 不做，答辩说明「本期无用户报障入口，工单未触发」；B 极简做：用户提交反馈/纠误→管理员处理→状态流转；C 用 GitHub Issue 承接。
- 推荐答案：B（提交+列表+状态+备注），作为 Java 端「案例要求」的合规支柱；若走 A 必须书面说明与案例偏差。
- 涉及的文档/模块：00、02、03。

#### Q6｜wav2vec2 微调是「自研加分项」，但它与唱歌评分在同一时段抢同一算法人，且「加分」是否真加分？
- 为什么重要/矛盾点：一个没打通的半成品模型在「成熟技术框架」评审下是**减分项**；且 wav2vec2 只是把发音评分换个引擎，demo 观感无提升。
- 候选答案 A/B/C：A 砍掉、纯讯飞基线（答辩说明「基线保底，自研延后」）；B 坚持做，但划为 M3 后置、失败即回退；C 用轻量替代（小样本微调小模型）。
- 推荐答案：A，除非有真实收益（讯飞免费额度耗尽 or 需离线演示）。把「wav2vec2 是否做」设为 M3 开工前的**硬门槛决策**，否则届时再谈必炸。
- 涉及的文档/模块：01、03、04。

#### Q7｜案例「移动端 App（Kotlin/Objective-C）」彻底不做还是留接口？
- 为什么重要/矛盾点：02 说「保留不砍不实现」，但若评审对照案例技术栈发现「从未出现任何移动端痕迹」会被指出。
- 候选答案 A/B/C：A 不做 App，移动端用 PWA/响应式覆盖；B 做一个最小 Android WebView 壳；C 完全不提。
- 推荐答案：A（PWA + 响应式），答辩话术「移动端以 Web/PWA 优先，原生 App 列为扩展」，避免硬伤。
- 涉及的文档/模块：00、02。

#### Q8｜案例基础功能「海量学习资源整合」（电影/剧/新闻/有声书）如何交代？
- 为什么重要/矛盾点：这是案例**基础功能第 1 条**，但 02 的内容只有「场景模板 + 歌曲库」，没有「听说素材库」，属于基础功能缺失。
- 候选答案 A/B/C：A 用「场景模板+歌曲库」作为可扩展的内容库模型，把「海量」解释为架构能力；B 加 1~2 个新闻/影视听力素材示例（含字幕）；C 承认不做并说明。
- 推荐答案：A + 1 个听力素材示例（含 ASR 字幕），证明「内容整合」的架构能力；不承诺真海量。
- 涉及的文档/模块：00、02。

### 维度 2 · 指标口径（重点）

#### Q9｜这四个指标的量是「三项」还是「四项」？（01 与 00 内部矛盾）
- 为什么重要/矛盾点：01 写「**三项**指标：点击率、完成率、互动率、跳出率」，但数出来是 4 个；00 原文是 4 个。到底是 3 还是 4，决定看板字段与砍项。
- 候选答案 A/B/C：A 4 项（以 00 为准，01 的「三项」为笔误）；B 3 项（删一个）；C 4 项但合并某项。
- 推荐答案：A，4 项独立；并在 01 更正「三项」→「四项」。
- 涉及的文档/模块：00、01。

#### Q10｜点击率（CTR）的分子/分母、事件与时间窗？
- 为什么重要/矛盾点：「点击」指对什么内容的点击？若无分母（曝光）则 CTR 无意义。
- 候选答案 A/B/C：A CTR=推荐内容被点击次数/推荐内容曝光次数（仅推荐位，展示后 30min 内）；B 全站点击/全站曝光；C 仅统计场景/歌曲卡片点击。
- 推荐答案：A——分母=推荐流曝光（impression），分子=这些曝光中发生点击（click）的去重会话数，窗口=曝光后 30min。埋点事件 `recommend_impression`、`recommend_click`。
- 涉及的文档/模块：01、02、03。

#### Q11｜「完成率」的「完成」指什么？分子分母、时长阈值？
- 为什么重要/矛盾点：完成率口径直接决定「是否算完成」，若不清，练一半就被算未完成。
- 候选答案 A/B/C：A 完成一次「场景对话」=答满 N 轮(如 5 轮)或达目标时长(如 2min)；B 完成一首歌=唱完所有句；C 完成「每日任务」。
- 推荐答案：分场景统一定义「成功结束的练习单元」：口语=单次对话达 **5 轮或 2 分钟**以上；唱歌=整首逐句评分结束。完成率=完成的练习单元数/发起的练习单元数（会话级去重）。
- 涉及的文档/模块：01、02。

#### Q12｜「互动率」的「互动」与分母？
- 为什么重要/矛盾点：口语 App 的「互动」极易被理解为「对话轮数」，也可理解为「用户主动操作」（点纠错/示范/收藏），口径不同数值天差地别。
- 候选答案 A/B/C：A 互动=用户发送的有效消息数/总轮数；B 互动=主动操作次数（重听/示范/纠错/换场景）；C 互动=触达数字人的次数。
- 推荐答案：两个层面并行——会话内互动率=用户主动发消息的轮数/该会话分配的轮数；另单列「功能互动」（点示范/点纠错/二次录制）作为可交互质量补充。
- 涉及的文档/模块：01、02。

#### Q13｜「跳出率」的「跳出」与停留阈值？
- 为什么重要/矛盾点：页面跳出率与「语音练习」的「跳出」不同，30s 的练习算不算跳出需要定义。
- 候选答案 A/B/C：A 进入场景/歌曲页后 30s 内无任何录音或点击即离开；B 开始录音后未完成一次评分即离开；C 会话级跳出（无有效交互即离开）。
- 推荐答案：A——进入场景或歌曲详情页后 **30 秒**内无任何有效事件（录音开始/播放/点击）即记 1 跳；跳出率=跳出会话数/进入会话数。
- 涉及的文档/模块：01、02。

#### Q14｜四指标需要哪些维度与埋点事件？是否上报服务端去重？
- 为什么重要/矛盾点：若只看一个裸数字无法归因；埋点不带维度（年龄/水平/场景/歌曲/设备），后续无法定位问题。
- 候选答案 A/B/C：A 维度=年龄组、水平档、场景、歌曲、渠道、时间(日/周)；B 仅年龄+水平档；C 仅场景+歌曲。
- 推荐答案：A（服务端落库 + 会话去重 + UTC 时间窗）。至少埋 `page_view / scene_start / recording_start / recording_complete / score_event / recommend_impression / recommend_click / practice_complete / fun_action(重听/示范/纠错)`；去重键=会话 id。
- 涉及的文档/模块：01、02、03。

#### Q15｜「推荐生效」如何验证？给出可验收判定。
- 为什么重要/矛盾点：01 说「不同水平/兴趣用户得到不同练习内容（用模拟行为数据验证）」，但「不同」不等于「对」。
- 候选答案 A/B/C：A 用 3 个预置画像（高/中/低水平 × 不同兴趣）请求推荐接口，断言 top-N 互异 + 命中兴趣标签 ≥X%；B 用用户点击反馈作为在线指标；C 仅展示推荐位不管合理性。
- 推荐答案：A——3 画像用户，断言(1) 推荐 top-3 各不相同；(2) 内容命中兴趣标签比例 ≥60%；(3) 内容类别分布 Jaccard 距离 > 阈值。用「模拟行为矩阵」驱动，明确标注为 **demo 验证**而非真实在线学习。
- 涉及的文档/模块：01、02、03。

#### Q16｜入学测试成绩与水平分级刻度。
- 为什么重要/矛盾点：现在只有「发音评分给出分数」，但「水平等级」无档位、无分数→档位映射；这是场景难度、推荐、水平预测的共同输入。
- 候选答案 A/B/C：A 3 档；B 5 档；C CEFR(A1~C2,6 档)。
- 推荐答案：**4 档**（L1 入门/L2 基础/L3 进阶/L4 高级），映射写入配置：综合分 S=0.4发音+0.3语法+0.3流利度，**S≥85→L4、70~84→L3、55~69→L2、<55→L1**；档位决定场景难度、推荐内容、默认目标语速。
- 涉及的文档/模块：01、02、03。

#### Q17｜入学测试到底测什么？（内容来源与判定方式）
- 为什么重要/矛盾点：若只测发音则「口语水平」定义过窄；题目来源决定一致性与可复现。
- 候选答案 A/B/C：A 测发音+流利度（朗读 5 句设计句）；B 只测发音；C 测发音+语法(LLM 判转写)+1 轮简单 QA（评应答相关度）。
- 推荐答案：C 但收敛为 **5 条固定朗读句 + 1 轮 QA**，全部来自 admin 题库；判定=综合分公式；保证 demo 可复现、口径一致。
- 涉及的文档/模块：01、02、03。

#### Q18｜「水平预测模型」是真的训练/用起来，还是演示道具？
- 为什么重要/矛盾点：demo 没有足量带标签数据，真训练一个可用水平预测模型不现实；且它预测的目标变量（水平档）又已由入学测试决定，形成循环。
- 候选答案 A/B/C：A 用评分映射代替（不做预测）；B 用 Scikit-learn 在「模拟行为→等级」合成数据上训练小模型并走接口，标注为 demo；C 砍掉。
- 推荐答案：B（合成数据 + 逻辑回归/GBDT），目标字段=水平档、特征=行为向量，体现「模型预测推荐」技术点；明确标注 demo 用合成数据。
- 涉及的文档/模块：01、02、03。

### 维度 3 · 用户与角色

#### Q19｜四类年龄人群在产品上到底体现在哪？还是只是注册标签？
- 为什么重要/矛盾点：案例强调「专业定制」，若只是 age 字段，答辩被问「儿童和青年在你系统里有什么不同」即崩。
- 候选答案 A/B/C：A 仅标签（注册时选，只用于报表/维度）；B 差异=语速(TTS rate)+难度档+内容分级；C 独立内容库（4 套×场景/歌曲）。
- 推荐答案：B——用 3 个参数化维度体现定制：默认 TTS 语速（儿童慢+活泼音色/老人更慢+低沉音色）、默认难度档、内容分级；内容库共用一个源，用难度/标签过滤。
- 涉及的文档/模块：00、01、02。

#### Q20｜年龄组与水平档是正交还是相关？内容矩阵会不会爆？
- 为什么重要/矛盾点：若 age×level 全正交（4×4=16 组合）并各配内容必爆，需决定谁是大维度谁过滤。
- 候选答案 A/B/C：A age 只影响语速/音色/文案，level 决定难度，两者正交但内容只按 level 分难度；B age 也参与内容过滤；C 只按 age 分。
- 推荐答案：A——内容只按「难度档」组织与过滤；age 只驱动 TTS 语速/音色与音色偏好；内容库复杂度=4 档而非 16 组合。
- 涉及的文档/模块：00、01、02。

#### Q21｜低龄（儿童/青少年）用户的合规与内容安全怎么交代？
- 为什么重要/矛盾点：案例明确含儿童；儿童语音/账号属未成年人个人信息，公开仓库绝不能出现真实用户数据；demo 若全用成人模拟账号则「服务儿童」承诺无落点。
- 候选答案 A/B/C：A 不做儿童真实 onboarding，demo 用成人模拟账号，文档声明含未成年人场景需监护人同意、本期不采真实儿童数据；B 做监护人同意流程；C 删除儿童/青少年人群。
- 推荐答案：A——产品范围写「面向成年学习者演示；儿童/青少年为目标人群，未成年人需监护人同意，本期不采集真实数据」，既保留人群定位又不踩红线。
- 涉及的文档/模块：00、05。

### 维度 4 · 场景扮演

### 维度 6 · 唱歌评分（自研扩展）

#### Q31｜音准/节奏/发音三个分数各自的定义与公式？
- 为什么重要/矛盾点：无公式，答辩必被问「音准 90 怎么算」。
- 候选答案 A/B/C：A 音准=逐句基频与参考旋律偏差(cent)映射；节奏=歌词时间戳与唱时戳的 DTW 偏差映射；发音=复用评分引擎；B 只用 pyin/crepe 看整体；C 只给档位不给分。
- 推荐答案：A，参考默认映射——音准：逐音高平均绝对偏差 ≤50cent→90~100、≤100→70~90、≤200→50~65、>300→<40；节奏：平均时间偏移 ≤150ms→90+、≤300→75~90、≤600→55~75、>1000→<50；综合=0.5音准+0.2节奏+0.3发音。

#### Q32｜不同原唱 tempo 如何对齐？（快/慢/变速演唱）

- 候选答案 A/B/C：A DTW 时间维对齐；B 先按整体倍率归一（检测平均 BPM 比例再缩放）；C 不规整（必须按原速）。
- 推荐答案：B+A——先用整体节拍倍率粗对齐（平均 BPM 比例），再对残差用 DTW 精对齐；若偏难，退化为「仅按原速+提示」（C），并在 demo 中规避变速演唱场景。

#### Q33｜唱歌评分的参考基准是什么？（原唱音轨/旋律线/MIDI）
- 为什么重要/矛盾点：「音准」需要参考音高序列；用原唱人声（带伴奏噪音）、旋律线还是 MIDI 影响很大。
- 候选答案 A/B/C：A 用歌曲旋律主音高序列（离线预提取）；B 用原唱人声；C 用 MIDI 乐谱。

#### Q34｜人工抽检标准是什么？（自研算法需 ground truth）

- 候选答案 A/B/C：A 抽 5 首×每首 5 句，2 名成员人工打 0-100，与算法相关 r≥0.7；B 抽 3 首×3 句；C 不做抽检。

#### Q59｜LLM 是否参与「会话内容相关度」评分？

## 第三部分 · 建议立即敲定并写入架构成品文档的决策条目（38 条 ADR）

1. **四项指标独立统计**；01 中「三项指标」更正为「四项指标」。
2. **评分总分 = 0.4·发音 + 0.3·语法 + 0.3·流利度**；发音/流利度取讯飞，语法由 LLM 基于转写判定(0-100)。
3. **若最终不引入语法项**，则全文档「发音、语法、流利度」统一改为「发音、流利度、完整度」，删除「语法」承诺。
4. **水平等级分 4 档(L1~L4)**；映射：综合分≥85→L4、70~84→L3、55~69→L2、<55→L1；写入配置。
5. **入学测试 = 5 条预置朗读句 + 1 轮 QA**，来自 admin 题库；判定=综合分公式，保证可复现。
6. **年龄组仅驱动 TTS 语速×音色×默认难度档与内容过滤**，不另开 4 套内容库。
7. **内容只按「难度档」组织**（4 档），而非 age×level 全正交。
8. **场景至少 3 类(生活/工作/学习)各 1 个，建议 4~5 个**，均可切难度。
9. **多轮会话默认 5~8 轮、目标 2~3 分钟**，超 8 轮 LLM 自动收尾。
10. **「交互数字人」= 2D 形象 + 语音播放(轻动/简单口型贴图) + 实时语音交互**；明确放弃 3D/口型驱动(SadTalker/Wav2Lip)。
11. **错误定位默认单词级**，重难点词给音素级提示 + 正确示范(TTS)。
12. **wav2vec2 微调设为 M3 开工前 Gate**：验证集相关 r≥0.8 且 MAE 达标才切换，否则回退讯飞基线，答辩降级为「探索性说明」。
13. **唱歌评分 = 音准(频率偏差映射) + 节奏(DTW 偏差映射) + 发音(复用评分引擎)**，综合=0.5/0.2/0.3；允许按整体 BPM 倍率粗对齐 + DTW 精对齐。
14. **唱歌评分基准 = 离线预提取的「参考旋律音高序列」+ LRC 时间戳**，不与原唱人声直接比对。
15. **自研唱歌算法人工抽检**：5 首×每首 5 句，2 人人工评分与算法相关 r≥0.7，出具验证报告。
16. **唱歌发音模块复用口语发音评分模块**。
17. **推荐 item 候选池 = 场景 + 歌曲 + 听力素材**(均带难度/类型/兴趣标签)；冷启动=入学测试档+兴趣标签+内容相似；在线协同过滤用种子/模拟矩阵。
18. **推荐「生效」验收**：3 画像用户 top-3 互异 + 命中兴趣标签≥60% + 类别分布 Jaccard 距离>阈值(模拟行为数据驱动)。
19. **水平预测模型用「练习行为特征+近期综合分」预测「预估/未来水平」**，目标≠入学测试档(避免循环)，用于进步趋势展示。
20. **埋点在 M3 独立实现**(前端真实事件→服务端落库+去重)，不依赖「真实行为积累」；事件含维度(年龄/水平/场景/歌曲/渠道/时间)。
21. **社交最小版 = 打卡(单日≥1 次口语练习) + 成绩卡片(canvas 图片下载/Web Share) + 只读打卡动态流 + 点赞**；不含双人实时对练。
22. **答辩口径：社交定位「分享+激励」**；「互相练习口语」解释为分享与互相督促，双人实时对练明确列为后续扩展。
23. **Java 管理端最小集 = 用户管理 + 场景/歌曲库 CRUD + 工单**；砍评价看板/admin 报表/精细权限。
24. **工单 = 用户提交反馈/报错/纠误 → 状态流转(新建/处理中/已解决/关闭)**，作为 Java 端「案例要求」落点。
25. **服务边界：前端只调 Java(业务 REST)；Java 内部调 Python(语音/LLM/推荐)**；密钥只在 Python 侧；用户/场景/歌曲/评分/工单主数据由 Java 写入 PG。
26. **Redis 在 compose 固定必含**；Python 提供内存级 fallback(启动参数)，确保「省 Redis 也能起」。
27. **ASR 主用 faster-whisper small(本地无网)**；TTS 用 Edge-TTS + 常用台词预合成 failover；讯飞/在线 API 监控余量，断网/配额满返回缓存或明确提示(演示主路径不崩)。
28. **数据合规：只存评分/转写/元数据**，原始音频默认 24h 清理(仅临时/内存)；demo 不采集真实用户数据。
29. **未成年人合规**：产品范围声明「面向成年学习者演示；儿童/青少年为目标人群，含未成年场景需监护人同意，本期不采集真实未成年人数据」。
30. **公开仓库红线扩充**：API Key、数据库密码、真实用户数据、训练集原始文件、模型权重、原始音频、商用音乐均禁提交；PR 模板加「敏感数据检查项」。
31. **模型权重/歌曲/LRC 用 setup 脚本下载(授权源) + 内置公有领域歌曲部署**，不入 .gitignore 目录，保证可复现。
32. **歌曲版权：demo 用公有领域/自创曲目(童谣/民歌)**，流行曲目仅在答辩说明思路，不入库。
33. **服务拓扑统一：前端→Java→Python**；避免两服务直接共享写同一 PG 表。
34. **性能基线(M4)**：常用接口 p95≤2s、ASR+LLM+TTS 全链路≤5s。
35. **演示脚本 5 分钟无人工救场**，预置 3 个画像账号(成年中级-场景、青少年初级-歌曲、老年高级-新闻/慢速)直接登录。
36. **「成熟技术框架」定义**：M1 落地 CI(GitHub Actions：前端 lint/build、python pytest、java build)+ 核心模块单测≥50% + docker compose 一键起 + 每里程碑补 ADR。
37. **流式录音：MVP 先「录完上传再处理」**，「流式」作为可选/加分优化，避免 M2 卡死。
38. **场景内容相关度不作量化分**；LLM 只负责引导与润色反馈，量化总分=发音/语法/流利度。

---

**一句话总结**：计划目前最需要的是「**在开工前把 #2(语法实现载体)、#3(指标口径)、#5(入学测试分级刻度)、#8(场景数量) 四件事做成一次二选一/数字决策**」，因为它们决定了架构、推荐、水平预测、社交、Demo 脚本等一整个链条——而这些恰恰是案例检查点与「成熟技术框架」评审最可能被打分的地方。
