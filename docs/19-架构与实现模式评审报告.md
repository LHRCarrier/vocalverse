### 1.2 一次对话回合的真实时序（`orchestrator._dialog_turn`，L122–400）

**结论先行**：这条时序里，DB 连接被独占 6–10 秒、事件循环被 ffmpeg 阻塞、首个音频块出现在"LLM 全文完成之后"，而所有落库动作发生在**所有 SSE 事件已经发出去之后**。三个 P0 的根都在这一张图里。

## 2. 致命缺陷 P0

### P0-1 会话状态机与会话锁是**进程内字典**，ADR 承诺的 Redis 一行没写

- **证据**：`app/practice/state.py` L38-87 —— `class StateStore` 的 `_data: dict[int, tuple[SessionState, float]]`、`_locks: dict[int, tuple[str, float]]`，`get_state_store()`（L83-87）是模块级单例。文件头 docstring L1 写"Redis session:{id} TTL 30min + 进程内降级"，L39 注释自认"M2 先落地内存，接口稳定后切 Redis"。`app/core/redis_client.py` 只被 `ratelimit.py` L44 引用，**全仓没有任何代码把会话写进 Redis**。
- **后果**：
  1. `docs/06 §10` 的"Redis：会话 `session:{id}` TTL 30min"是空头支票；`docs/16 C1` 拍板的"Redis SETNX 会话锁"未落地，锁只在**单进程内**有效——只要 `uvicorn --workers 2` 或起第二个副本，双开/重复提交立即打穿 `scenario_messages (session_id, seq)` 唯一约束（`models/content.py` 的唯一键），返回 500 而不是 409。
  2. 任何一次 `--reload`、发版、OOM 重启 → 全部在途会话蒸发。前端拿到的是 404「session not found or expired」（`practice.py` L144），用户正在说的话直接丢弃。
  3. `store.get()` 返回的是**共享可变对象引用**（L46-54 直接返回 `state`），`_dialog_turn` 在 L311/L346 `state.next_seq += 1`、L366 `state.current_turn = turn_index` 都是**就地改内存**，而 `db.commit()` 在 L376。若 commit 抛异常（唯一键冲突/连接断），内存状态已经推进，DB 没有对应行 → 会话进入"服务端认为第 3 轮、库里只有第 2 轮"的分叉态，且**没有任何补偿逻辑**。
- **建议方案**：把 `StateStore` 换成 Redis 后端（`SET session:{id} <json> EX 1800` + `SET lock:{id} nonce NX EX 60` + Lua 脚本释放），保留内存实现只作单测桩；`state` 改为**读时反序列化的副本**，回合结束"先 DB commit、后 state put"，把 `next_seq` 的权威改成 DB 侧 `SELECT max(seq)+1 FOR UPDATE` 或直接依赖唯一约束重试。
- **引入成本**：Redis 版 StateStore ≈ 120 行 + 6 个单测；改"先 commit 后 put"约 30 行。**0.5–1 人天**，且接口已经抽象好（`get_state_store()` 是唯一入口），是本报告里性价比最高的一条。

### P0-2 SSE 回合在 async 生成器里持有**同步 DB 连接 + 阻塞调用**，事件循环与连接池双杀

- **证据**：
  - `orchestrator._dialog_turn` L124 `db = _db()`（`get_session_factory()()`，`app/db/__init__.py` L38-42 是**同步** `sessionmaker`，驱动 `postgresql+psycopg`），`finally: db.close()` 在 L400 —— 连接横跨 L141 的 ASR、L220 的 LLM 流、L278 的逐句 TTS，**整整一个回合 6–10 秒**。
  - `app/db/__init__.py` L27 `kwargs = {"pool_pre_ping": True}`，**没有 `pool_size` / `max_overflow`** → SQLAlchemy 默认 5 + 10 = **15 条连接封顶**。
  - `app/audio/asr.py` L64-68 `subprocess.run([ffmpeg...], check=True, capture_output=True)` —— 在 `async def transcribe` 里**同步阻塞**，且**没有 timeout**。只有 whisper 那一步进了 `asyncio.to_thread`（L69）。这直接违反 `docs/06 §8`「>10ms 的 CPU 工作必须进 `anyio.to_thread`」，也让 `docs/09 §3.2-1` 点名的"SSE 心跳都发不出"成为现实。
  - `service.complete_session`（L118-188）是**同步函数**，却在 `orchestrator` L167/L384/L496 直接调用（不在线程池里），内部做 3 次查询 + 1 次 commit。
- **后果**：
  1. 15 个并发回合就把连接池抽干，第 16 个请求在 `get_session_factory()()` 处静默等待 30s 后抛 `TimeoutError`——而它已经被 `except Exception` 吞成一条 `error` SSE 事件（`practice.py` L163-165），前端只看到"管线提示：internal"。
  2. ffmpeg 阻塞期间（15s 音频转码 ~0.2–0.8s，但一旦 ffmpeg 卡住就是**永久**）整个进程不响应任何请求，包括 `/healthz`——compose 健康检查（`docker-compose.yml` L58-63）会判定容器 unhealthy 并连累 `java-api` 的 `depends_on: service_healthy`。
  3. `--workers 1`（Dockerfile L23，符合 ADR）意味着**没有第二个进程兜底**：一个坏音频文件可以让整个服务停摆。
- **建议方案**：① `subprocess.run` → `await asyncio.create_subprocess_exec(...)` + `wait_for(timeout=15)`；② DB 访问全部收进 `await asyncio.to_thread(...)` 的短事务函数，**回合中途不持连接**（把"写 3 行 + 提交"做成一个 `to_thread` 调用）；③ `create_engine(..., pool_size=20, max_overflow=10, pool_timeout=5)` 显式声明；④ 中长期换 `asyncpg + AsyncSession`。
- **引入成本**：①③ 各 10 行，**0.5 人天**；② 需要重构 `_dialog_turn` 的事务边界（约 80 行）+ 补 2 个并发测试，**1–1.5 人天**。不做②，第 3 条瓶颈（见 §5）在 15 并发就触发。

### P0-3 三处越权（IDOR）：`user_id` 传了但没用 / 报告与收尾无归属校验

- **证据**：
  - `orchestrator.run_turn(session_id, user_id, ...)`（L80-116）签名收了 `user_id`，**函数体内一次都没有使用**（grep 全文，唯一出现是 L337 `user_id=session.user_id`，取自 DB 而非请求）。`_dialog_turn`/`_defense_turn` 同样不校验 `session.user_id == 请求者`。
  - `practice.get_report`（L198-219）：`db.get(Report, report_id)` 后直接返回，**无任何归属过滤**。而 `complete_session` 往 `reports.metrics` 里塞了 `attempts[].transcript`（`service.py` L168-181）——即**别人的语音转写原文**。
  - `practice.complete`（L171-179）：拿到 `session_id` 直接 `complete_session()`，不校验归属，可以替任意用户关会话并生成报告。
  - 对比之下 `defense.py` L111/L137/L157 是**做了**归属校验的（`profile.user_id != user_id → 404`），说明团队知道该怎么写，只是练习域漏了。
- **后果**：任一登录用户遍历 `report_id`（BIGINT IDENTITY，连续可枚举）即可拖走全站转写文本；`docs/06 §9.7`「只存评分/转写/元数据」的合规声明连自己的门槛都没守住。演示现场只要有人打开 DevTools 改一个数字，就是答辩事故。
- **建议方案**：`reports` 增加 `owner_user_id`（或按 `scope='session'` 关联 `sessions.user_id` 做 JOIN 过滤）；`run_turn` 第一件事就是 `if session.user_id != user_id: 403`；`complete` 同理。顺带给 `Report` 加 `Index("ix_reports_owner")`。
- **引入成本**：3 处各 3–5 行 + 1 个迁移（若加列）+ 3 个越权测试，**0.5 人天**。

### P0-4 语音/LLM 裸接口**完全无鉴权、无限流**，成本与滥用敞口

- **证据**：`app/api/routes/audio.py` 全文 80 行，`/api/v1/asr`(L39)、`/api/v1/score`(L51)、`/api/v1/tts`(L63)、`/api/v1/llm/chat`(L74) **四个端点没有一个 `Depends(get_current_user_id)`，也没有一个限流依赖**。而 `practice.py` L107-128 明明已经写好了 `_rl_asr/_rl_ise/_rl_llm` 三个桶。`apps/web/nginx.conf` L27 把整个 `/api/v1/` 直接暴露到 8088。
  另：`defense.create_profile`（`defense.py` L75-100）会触发一次 **8000 字输入的 LLM 调用**（`service.generate_bank` L315，`max_tokens=4000`），同样**不消费任何限流桶**。
- **后果**：任何人拿到 URL 就有一个免费的 DeepSeek 代理 + 免费 TTS + 免费 ASR。`docs/06 §7` 的"LLM/评分 30 次/用户/时"在这四个端点上等于不存在。校园网内网演示无所谓，一旦按 README 的方式暴露 8088，账单和额度（`docs/06 §15` 的"讯飞免费额度耗尽"风险行）由这条路先耗光。
- **建议方案**：给 `audio.py` 四个端点统一加 `Depends(get_current_user_id)` + 对应桶；`defense` 的生成走 `llm` 桶并按"每 profile 每小时 3 次"单独计数；`/tts` 的 hex 返回（L71，`docs/09 P1-#9` 已点名 2 倍膨胀）改为直接返回 `audio/mpeg` 流。
- **引入成本**：**0.5 人天**（依赖已写好，粘贴即可），外加更新 `python-openapi.json` 快照重跑 `pnpm gen:api`。

### P0-5 "流式"只流字幕：首声延迟落回 docs/16 判定的**超预算方案**

- **证据**：`orchestrator._dialog_turn` 的 LLM 循环 L220-248 结束（即 `full_text` 已完整）之后，L278 才开始
  ```python
  for line in tts_sentences(reply):
      url = await _tts_url_from_bytes(tts, line, ...)   # 串行 await
      yield ev.AudioChunk(url=url)
  ```
  是**串行**的（尽管 L276 的注释写着"并发"）。`app/audio/tts.py` L39-46 写了 `synthesize_concurrent()`，**全仓无人调用**（grep 仅此一处定义）。
- **量化**：按 `docs/06 §8` 已实测的数字（edge-tts 单句 mean **1.34s**、whisper RTF **0.328**）：
  首声 = 上传 0.3 + ASR(15s×0.33) 2.0 + LLM 全文 2.5–4.0 + 首句 TTS 1.34 ≈ **6.1–7.6s**。
  这正是 `docs/16 §C4 结论①`「非流式 JSON → 5~8.5s，**超预算**，演示话术不成立」的那一档。也就是说：docs/16 花了整节论证要走"方案 A（流式 reply + 逐句 TTS 边生成边合成）"，`docs/17/18` 拍板走 A，**代码实现的是 C**。README L40 仍在承诺"SSE 流式（音频为时间轴权威）"。
- **后果**：答辩现场按下录音到听见 AI 说话约 7 秒，中间只有字幕在跳——而"音频为时间轴权威、文本降级为字幕"（`docs/06 §8`）的产品叙事整个反过来了。
- **建议方案**：在 LLM 流循环内做**句边界切分**，遇到 `.!?` 立即把该句丢进 `asyncio.create_task(tts.synthesize(...))`，用一个 `asyncio.Queue` 保序发 `audio_chunk`；配合 `docs/06 §8` 已定的"开场/常用句预合成"。首声可压到 ASR + 首 token + 1 句 TTS ≈ **3.5–4.5s**。
- **引入成本**：`_dialog_turn` 内约 40 行（切分器 + 有序任务队列）+ 3 个单测（跨 chunk 切句、TTS 失败跳过、顺序保证）。**1 人天**，是"3~5 秒"话术能否成立的唯一开关。

### P0-6 唯一一条跨服务写链路**字段名对不上**，且失败被静默吞掉

- **证据**：
  - Python 侧 `placement._callback_level`（L165-180）：`json={"user_id": user_id, "level": level}`。
  - Java 侧 `InternalLevelController.LevelRequest`（L20）：`record LevelRequest(@NotNull Long userId, @NotNull String level)`；`services/java/src/main/resources/application.yml` **没有任何 `property-naming-strategy` 配置**（全仓 grep `SNAKE_CASE` 无匹配）→ Jackson 只认 `userId`。
  - 结果：`userId == null` → `@Valid` 失败 → **400**。而 Python 侧 `httpx` 默认不对 4xx 抛异常，`await client.post(...)` 的返回值**根本没被检查**，外层 `except Exception: return`（L179-180）连日志都不打。
- **后果**：`user_profiles.cefr_level` **永远停留在注册时写死的 "L1"**（`AuthController.register` L95）。这意味着：
  - `docs/10 §3.2-1` 精心设计的"入学测试档位回写"链路 100% 不通，而且**没有任何告警**；
  - 顺带查证：Python 侧**从不 SELECT `user_profiles`**（grep 全仓，只有模型定义与注释），TTS 音色/语速取自全局配置 `config.py` L46-47 而非用户档案 → `docs/06 §9.2`「年龄组驱动 TTS 语速/音色/默认难度」**零实现**；
  - `events` 表的 `age_group` / `level` 维度列（`models/analytics.py` L64-65）在 `routes/events.py` L42-51 的 `Event(...)` 构造里**从不赋值**，全为 NULL → `docs/06 §9.1` 的"六维聚合"和 8 个相关索引（`analytics.py` L100-104）是**为空数据建的索引**。
- **这条最能回答"三语言架构的代价"**：整个 Java 服务对业务的唯一贡献是"发 JWT"，它与 Python 之间**唯一的数据交换**因为一个下划线而断了三周没人发现，因为①跨语言契约测试只覆盖各自的 OpenAPI 快照（`ContractSnapshotTest`），不覆盖内部 REST；②失败被 `except Exception: return` 吞掉；③没有任何一条集成测试跨两个进程。
- **建议方案**：立刻改 `json={"userId": ...}`（1 行），同时 ① `resp.raise_for_status()` + `logger.error`；② 给 `/internal/level` 写一条 Java 侧 `@SpringBootTest` + 一条 Python 侧契约测试（用 `respx` 断言请求体键名）；③ 长期把内部 REST 的请求体也纳入 `docs/api/` 契约真源。
- **引入成本**：修复 **10 分钟**；契约测试 **0.5 人天**。

### P0-7 "写方唯一性"在代码层已破，且没有任何机制守护

- **证据**：
  - `docs/10 §3.1` 声明 `scenarios / songs / lrc / listening_materials / placement_questions / tickets` 由 **Java 独占写**。`services/java` 全量 Java 文件共 12 个业务类（glob 结果），**没有任何一个** `ScenarioEntity` / `SongEntity` / `TicketEntity` 或对应 Controller/Repository。
  - `services/python/app/db/seed.py` L71-84 `seed_scenarios()` 直接 `session.add(Scenario(**item))`，L87-101 `seed_placement_questions()` 直接写 `placement_questions`——**两张 Java 拥有的表被 Python 写入**，且这个脚本被 `docker-compose.yml` L72 的 `migrate` 服务在每次 `compose up` 时执行。
  - 守护机制：`docs/10 §1 P8` 写"一张表一个 DB 写方"，但落地手段只有**文档**。两个服务用**同一个 DB 账号**（compose L45 与 L90-94 都是 `POSTGRES_USER`），没有按表授权，没有 CI 探针，没有触发器。
- **后果**：单写方在本项目里是一个**荣誉制约定**。当前风险不高（Java 侧还没写这些表的代码），但它意味着：
  1. `docs/16 B5` 讨论了半天的"seed 单写豁免"实际上已经被代码单方面执行；
  2. 一旦 M3 Java 真做了场景 CRUD，`scenarios.title` 幂等键（seed.py L78 用 title 查重）与 Java 的编辑动作会互相覆盖（管理员改了标题 → seed 认为不存在 → 再插一条重复场景）；
  3. `docs/10 §5.1` 的"更新必须维护 updated_at"约定在 Python seed 里也没执行。
- **建议方案**：最小成本方案是**用 DB 权限把约定变成约束**：建 `vv_python` / `vv_java` 两个角色，按 `docs/10 §3.1` 矩阵 `GRANT INSERT,UPDATE`；seed 用第三个 `vv_seed` 角色并只在初始化时执行。次选：CI 加一条静态探针（grep Python 代码中对 Java 拥有表的 `add()/update()`）。
- **引入成本**：DB 角色方案 = 1 个迁移 + compose 改两行连接串，**0.5 人天**；静态探针 ≈ 30 行脚本，**2 小时**。

### P0-8 `reports` 的唯一约束会让"再收尾一次"变成 500

- **证据**：`models/analytics.py` L131-139 `UniqueConstraint("report_type","scope","scope_id","period_start","period_end")`；`service.complete_session` L154-184 每次都是 `db.add(Report(...))` + `db.commit()`，`report_type="session_report"`、`scope="session"`、`scope_id=session.id`、`period_*` 都取 `started_at.date()` —— **同一会话第二次收尾必然唯一键冲突**。而 `docs/10 §4.4` 白纸黑字写"重复计算＝整行覆盖（**upsert**）"。

- **引入成本**：约 20 行 + 1 个"重复收尾幂等"测试，**2 小时**。

### P0-9 默认密钥进仓库，且 `/internal/**` 经网关**对外可达**

- **证据**：`services/java/src/main/resources/application.yml` L24 `secret: ${JWT_SECRET:vocalverse-dev-jwt-secret-0123456789abcdef}`、L26 `service-token: ${SERVICE_TOKEN:change-me-internal-service-token}`；`services/python/app/core/config.py` L31/L33 是**同样两个默认值**。`docker-compose.yml` 的 `python-api`(L37-63) 与 `java-api`(L82-107) **都没有显式注入这两个变量**，只有 `env_file: {path: .env, required: false}`——按 README L57「不填也能起」的路径，整套系统就跑在公开仓库里写死的密钥上。

- **引入成本**：**2 小时**，纯配置。

## 3. 重要问题 P1

### P1-1 音频回放的鉴权方案与 `<audio>` 标签**物理不兼容**

- **证据**：`practice.get_audio`（L225-264）要求 `Depends(get_current_user_id)`，即 `Authorization: Bearer`；前端 `PracticeView.vue` L124-131 `playChunk(url)` 用的是 `new Audio(url)`——浏览器发起的媒体请求**不可能带自定义头**。L130 `audio.play().catch(() => undefined)` 把 401 静默吞掉。
- **后果**：对话音频在真实鉴权下**全程无声**，"降级为字幕"看起来像是设计，其实是 401。（`DefenseView.vue` L127 走的是另一条路：`tts()` → `/api/v1/tts` 无鉴权 hex → Blob URL，能响。同一个产品里两套 TTS 交付方式，一套能响一套不能。）
- **建议**：`audio_chunk` 改发**短时签名 URL**（`?exp=&sig=HMAC(name|user_id|exp)`，服务端校验签名而非 JWT），或前端用 `fetch(url, {headers})` → `URL.createObjectURL(blob)`。前者更省，且天然解决枚举问题。
- **成本**：签名方案后端 25 行 + 前端 0 行；Blob 方案前端 15 行。**0.5 人天**。
- **附带 bug**：`playChunk` 的队列逻辑是错的——`audio.onended = () => audioQueue.shift()?.play()`（L127-129），`shift()` 弹出的是**刚播完的那一条自己**，第一句会被播两遍。零测试覆盖（`apps/web` 只有 `client.test.ts` 与 `sse.test.ts` 两个测试文件）。

### P1-2 音频文件只增不减 + 内容寻址导致跨用户误删

- **证据**：`practice.post_turn` L139 在**状态校验（L141-151）之前**就 `save_audio_bytes(data)` 落盘——409/404 的请求同样留下孤儿文件，而这些文件永远不会被任何 `attempts.audio_url` 引用。清理逻辑只有 `get_audio` L234-237 的惰性删除，触发条件是"有人带着合法归属来 GET 它" → **孤儿文件与无人回放的过期文件永不被删**。
  `save_audio_bytes`（`orchestrator.py` L63-74）用 `sha1(data)[:32]` 作文件名，`if not os.path.exists(path)` 才写 → **同一段音频跨用户共享一个文件**，而过期判定用 `path.stat().st_mtime`（首次创建时间）。用户 A 昨天的 TTS 与用户 B 今天的同句 TTS 复用同一文件，B 播放时按 A 的 mtime 判定过期 → 被删 + 410。
- **后果**：磁盘单调增长（见 §5 瓶颈 4）；合规上"24h 清理"（`docs/06 §9.7`）实际未生效；偶发的"音频已过期"无法复现。
- **建议**：① 落盘挪到状态校验之后；② 文件名改 `uuid4`（或 `sha1 + user_id` 分目录），放弃跨用户去重；③ 真做一个清理任务——`lifespan` 里起一个 `asyncio.create_task` 每小时扫一次，或干脆用 compose 加一个 `find -mmin +1440 -delete` 的 sidecar/cron。
- **成本**：**0.5 人天**。

### P1-3 外部依赖零弹性：无超时分层、无重试、无熔断、无连接复用

- **证据**：`audio/llm.py` L46 与 L70 每次调用都 `async with httpx.AsyncClient(timeout=90)`——**每轮对话新建一个连接池**，白扔一次 TCP+TLS 握手（对首 token 预算是 100–300ms 的净损失）；`timeout=90` 是一个数字包打天下（连接/读/写不分层）；没有 `Retry`、没有熔断器、没有降级缓存。`asr.py` L64 的 `subprocess.run` 无 timeout；`tts.py` L29-36 的 edge-tts 无超时（依赖库默认）。
- **后果**：DeepSeek 抖动一次 → 用户等 90 秒；whisper/ffmpeg 卡死 → 整个进程停摆（因 P0-2）。`docs/16 C8` 给了完整降级矩阵，但矩阵里的每一格都需要"**先能感知失败**"，而当前代码只能感知"抛异常"，感知不了"很慢"。
- **建议**：`httpx.AsyncClient` 提升为模块级单例（`lifespan` 管生命周期）+ `httpx.Timeout(connect=3, read=30, write=10, pool=5)`；LLM/TTS 各包一个极简熔断器（连续 5 次失败 → 60s 内直接走 `_fallback_reply`/静默字幕）；ffmpeg 加 15s 超时。
- **成本**：单例 + 分层超时 **2 小时**；60 行的极简熔断器 + 单测 **0.5 人天**。

### P1-4 ADR 明写的信号量（whisper 2 / ISE 2）**一个都没有**

- **证据**：全仓 grep `Semaphore` → **0 匹配**。`docs/06 §8` 的并发决策行「模型侧信号量（whisper 并发 2，与讯飞 ISE 一致），多请求排队不雪崩」、`docs/09 P1-#5` 的处置记录"✅ 已落地（文档）"——文档落地了，代码没有。
- **后果**：5 个人同时按录音 → 5 个 `asyncio.to_thread` 同时跑 whisper，faster-whisper 内部还各自开 C++ 线程池 → CPU 超卖、RTF 从 0.33 劣化到 1.5+，所有人一起变慢；`mem_limit: 2g`（compose L48）下多份特征张量并存有 OOM 风险。讯飞 ISE 侧则是直接超并发被拒。
- **建议**：`app/audio/base.py` 里加两个模块级 `asyncio.Semaphore(settings.asr_concurrency)` / `(2)`，在 `FasterWhisperClient.transcribe` 与 `ISEClient.score` 内 `async with`。
- **成本**：**1 小时**。这是 ROI 最高的 P1。

### P1-5 限流桶漏了 TTS，且空动作照样扣费

- **证据**：`practice.post_turn` L126-128 消费 `asr / ise / llm` 三桶；一轮回合的 TTS 调用数 = 句数（`tts_sentences`，`service.py` L379-391），**完全不计数**，而 `config.py` L63 明明定义了 `tts_rate_per_hour = 60`。反向的问题：`action in ("hint","demo","abandon")` 的轻回合（`orchestrator` L180-201 直接 return）**不消耗任何 ASR/ISE/LLM**，却在路由层被扣了三个桶。
- **后果**：TTS（edge-tts 是被微软限流的免费服务，`docs/06 §15` 已列为风险）没有护栏，一个 8 轮 × 3 句的会话就是 24 次外呼；同时用户点几次"示范"就被误判 429。
- **建议**：把限流从"路由依赖"下沉到"客户端包装器"（在 `get_*_client()` 返回的对象里按实际调用计数），这样天然对齐"实际消耗"，也顺手解决 P0-4。
- **成本**：**0.5 人天**（装饰器模式，约 40 行）。

### P1-6 `/readyz` 恒真、Redis 可用性判断恒真——可观测性是假的

- **证据**：`routes/health.py` L18-27 直接 `return ok({"status": "ready", ...})`，注释 L20 还写着"M2 起接入真实探测"——M2 已经交付了。`core/redis_client.py` L16-35：`aioredis.from_url()` 是**惰性连接**，不会抛异常，所以 `redis_available()`（L38-39）**永远返回 True**，而 `_redis_consume`（`ratelimit.py` L43-62）每次调用都要等真实的连接失败异常再落回内存桶——每个请求白等一次 Redis 超时。
- **后果**：`docs/06 §10.2` 承诺的「`/readyz` 报 degraded 并附 `redis:false`」不存在；DB 挂了 `/readyz` 照样 200，K8s/compose 永远不会把坏实例摘掉。
- **建议**：`/readyz` 里 `SELECT 1` + `redis.ping()`（各 1s 超时），按 `docs/06 §10.2` 返回 `degraded`；`get_redis()` 首次调用时 `await client.ping()` 并缓存负结果 30s（代码里 `_last_fail` 的机制已经写好了，只是没人触发它）。
- **成本**：**2 小时**。

### P1-7 指标口径：`user_turn_count` 永远是 0，救援轮只从分子剔除

- **证据**：

### P1-9 答辩知识包生成是"裸 `create_task`"——最该用任务队列的地方用了最脆的写法

- **证据**：`defense.py` L35-72 `_generate_task()` 内 `asyncio.create_task(runner())`，**没有保存返回的 Task 引用**（Python 官方文档明确：事件循环只持弱引用，任务可能在执行中被 GC）；没有超时（内部 LLM `timeout=90`）；没有重试（`docs/14 §4.2` 要求"失败重试 1 次"，代码里没有）；进程重启后所有 `status='generating'` 的行**永久卡死**（没有任何扫描/补偿）；`runner()` 里用的还是同步 `Session`（L39/L52/L69），在事件循环里 commit。

- **成本**：最小方案 **0.5 人天**。

## 4. 改进建议 P2

### P2-1 数据库设计的四个规模化隐患

1. **`reports.metrics` 被当成文档库**：`service.complete_session` L168-181 把**整个 attempts 数组**（含 transcript、details 词级明细）塞进 JSONB。一个 8 轮会话的 metrics ≈ 10–30KB，10 万用户 × 3 会话/周 → 单表每周 ~9GB JSONB。而 `docs/10 §4.4` 设计的 `metrics` 是 `{ctr:{n,d,rate},...}` 这种**几百字节**的聚合。会话报告应该是 `session_reports` 独立表或直接从 `attempts` re-play，不该塞进指标表。成本：一个迁移 + 改 `complete_session`，1 人天。
2. **`attempts.audio_url` 无索引却是查询条件**：`practice.get_audio` L244 `where(Attempt.audio_url == url, ...)`，`models/practice.py` L150-153 的三个索引里没有它 → 每次音频回放一次全表扫。报告页 8 条录音 = 8 次 seq scan。成本：1 个索引（或改成路径里带 attempt_id）。
3. **`events` 无分区、无归档、8 个索引**（`analytics.py` L95-104）：只追加表 + 8 个索引 = 写放大 9 倍。10 万用户量级必须按 `occurred_at` 做**月度声明式分区** + 冷分区 `DETACH`。当前规模不做没问题，但**表一旦上百 GB 再分区就得停机**。成本：现在做 0.5 人天，将来做 3 人天 + 停机。
4. **`scores` 表建好了没人写**（全仓 grep 无 `Score(` 构造）、`sing_attempts`/`song_pitch_refs`/`listening_materials`/`post_likes`/`tickets` 同理——19 张表里有 **7 张是纯占位**。这本身不算错（M3 计划内），但 `docs/10` 把它们描述成"已落地"会误导评审：建议在 §2 表清单里加一列"当前是否有写方代码"。

### P2-2 时区与方言泄漏到业务代码

`service.complete_session` L138-143 手工给 `started_at` 补 `tzinfo=UTC`，注释写"SQLite 返回 naive、PG timestamptz 是 aware"。这是**测试用 SQLite、生产用 PG** 这个决策（`conftest.py` L9 `sqlite+pysqlite:///:memory:`）泄漏到业务逻辑的直接证据。同类泄漏还会出现在 `Numeric`（SQLite 返回 float，PG 返回 Decimal）、JSONB 查询（SQLite 不支持 `->>`）。建议：`docs/06 §6` 承诺的 **Testcontainers 集成测试**必须真做（见 §6），否则每一个 PG 特性都要在业务层写一次兼容代码。

### P2-3 覆盖度指标可以被"复读机"刷满

`practice/corpus.py` L61-78 `match_rule` 是**归一化后子串匹配**。用户只要把提示卡上的句子照读一遍（`PracticeView.vue` L100 的 `hintText` 直接显示 `target_corpus` 第一条），就 100% 命中。而 `_grammar_ok`（`orchestrator.py` L601-604）在 LLM 没给 grammar 时**默认返回 True** → 状态 `ok`。于是"语言点覆盖度"这个 M2 的差异化卖点，用复读就能刷满。另：`corpus.py` L16 定义的 `_STRIP_LEADING` 正则**从未被使用**（死代码）。建议至少加"与提示卡展示时间间隔 <3s 的命中降权"或"同一 phrase 只在非 hint 轮计一次"。

### P2-4 前端/服务端双状态机没有恢复路径

`PracticeView.vue` L205 客户端自增 `currentTurn`，L162 用它发 `expected_turn`；服务端在 `orchestrator` L99-100 严格比对，不等就 409。任何一次 SSE 中断（切后台、断网、`turn_end` 丢包）都会让两边永久错位，而**没有 `GET /sessions/{id}` 恢复端点**（`practice.py` 里没有这个路由，`docs/16 A3/G2` 提过"刷新恢复 P2 延后"）。建议：`turn_end` 里回带服务端权威 `next_expected_turn`，前端无条件采纳（服务端是唯一真源），成本 30 分钟，直接消灭一整类现场事故。

## 5. 扩展性瓶颈排序（10 人 → 10 万人，按崩溃先后）

| # | 瓶颈 | 触发量级 | 崩溃形态 | 根因（文件/行） |
|---|---|---|---|---|
| **1** | **进程内会话状态 + 进程内锁** | **第 2 个副本 / 第 1 次发版重启**（并发无关） | 横向扩容后同一会话被路由到不同实例 → 404「session not found」或 seq 唯一键 500；重启即全量会话丢失 | `practice/state.py` L38-87 |
| **2** | **事件循环阻塞 + 15 条连接池** | **并发回合 ≈10–15**（约 300–500 DAU 的午间峰值） | 连接池耗尽 → 请求挂 30s 后 500；ffmpeg 卡死 → 整进程无响应，`/healthz` 超时被摘除 | `orchestrator.py` L124/L400、`db/__init__.py` L27、`asr.py` L64 |
| **3** | **whisper CPU（无信号量、单 worker）** | **并发 ASR ≈3–5**（10 人同时按录音） | RTF 从 0.33 劣化到 >1，首声从 4s 变 15s+，`mem_limit 2g` 下 OOM 风险 | 全仓无 `Semaphore`；`Dockerfile` L23 `--workers 1` |
| **4** | **本地卷音频 + 清理不生效** | **累计 ~3 万条录音（≈10GB）**；10 万用户按日活 5%、人均 3 段计 ≈ **9GB/日** | 磁盘写满 → 落盘失败 → 整条回合 500；且本地卷无法在多副本间共享，扩容即"音频找不到" | `orchestrator.py` L63-74、`practice.py` L139/L234 |
| **5** | **`events` 单表 + 每事件一次 commit + 8 索引** | **~300 万行/日**（10 万用户 × 30 事件） | 写入延迟抬升（每条埋点一个事务）、指标 re-play 全表扫、单表数百 GB 后无法在线分区 | `routes/events.py` L40-58、`analytics.py` L95-104 |

## 8. 三语言架构的真实成本核算

**Java 端当前实际承担的职责**（`services/java` 全部业务代码 ≈ 500 行）：
1. BCrypt 密码存储与校验（`AuthController` L83/L114）；
2. HS256 access token 签发（`JwtService` L30-38）；
3. `refresh_tokens` 表的 rotation（`AuthController` L120-135）；
4. 3 个演示账号 seed（`DemoSeeder`）；
5. `/internal/level` 回写（**当前是坏的**，见 P0-6）。

**不可替代性评估**：
- 技术上 = **0**。`app/core/auth.py` 已经手写了完整的 HS256 验签（L41-54）与签发（L30-38，注释写"仅供测试"），Python 侧 30 行就能接管 JWT 签发；BCrypt 用 `passlib` 一行；refresh rotation 是一张表两个 UPDATE。
- 课程/答辩上 = **100%**。`docs/09 §1` 明确"双语言后端不是自由选型而是作业条件"，`docs/12 §1` 也把它列为不可动的结构性前提。

**合并进 Python 会失去什么 / 得到什么**：

| 失去 | 得到 |
|---|---|
| 课程合规（选题要求 Python + Java），答辩"技术栈完整性"叙事 | 消灭 P0-6 一整类 bug：跨语言字段命名/序列化/时区/Decimal 的**四类边界**全部消失 |
| Spring Security / JPA 的成熟度背书 | 事务边界统一：登录后建 profile 与 placements 写入可以在**同一个事务**里（现在跨进程，靠"静默降级"兜底） |
| "两个后端"这个可以写进答辩 PPT 的架构图 | 少一个 400–600MB JVM（`docs/09 P2-#11` 已点名"价值密度"），compose 启动少一个 `service_healthy` 依赖链（现在 `web` 等 `java-api` 等 `python-api`，任一环慢就全链路慢） |
| — | 少一套构建工具链（Maven + spotless + JDK 21 版本坑，README FAQ 里为 JAVA_HOME/编码/端口占用写了 4 条），团队认知负荷从"三门语言的调试方式"降到两门 |

**结论**：这套架构的三语言成本不是"多写了 500 行 Java"，而是**多了一条没有测试、没有类型检查、没有契约保护的跨进程数据通路**——而这条通路上唯一的一个写操作，已经坏了。真实成本 = P0-6 + P0-7 + 那条永远为 NULL 的 `events.age_group` 维度。

保留 Java（课程强制）的前提下，**把它做成真正的边界服务**而不是半个数据面：① Java 只负责认证与用户资料，`user_profiles` 的**读**也应该走 Java 的 `/internal/profiles/{id}`（而不是 Python 直连 PG 读 Java 的表，虽然当前 Python 压根没读）；② 或者反过来，承认"共享数据库集成"这个反模式，把 `user_profiles` 的写方也划给 Python，Java 退化为纯 Auth 服务。**两者选一，别停在中间**——现在的状态是"契约上是委托、实现上是断的、事实上没人读"，最差的一种。

## 9. 一句话结论

**能撑到项目交付，撑不到真实上线**：单机单进程、逐个演示、Fake 兜底的条件下这套代码可以跑完一次完整答辩（且文档质量在学生项目里是顶级的）；但会话状态在进程内存里、事件循环被同步 IO 阻塞、报告与回合存在越权、语音裸接口无鉴权、跨服务唯一的写链路字段名对不上——这五条里的任意一条在真实上线的第一天都会出事，而它们合起来意味着**这套系统目前无法被复制成第二个副本**，也就谈不上"上线"。

**修复优先级（把"能上线"变成可能的最小集，合计约 5–6 人天）**：
