**特别表扬（架构成熟度的标志）：**

1. **热路径直连 Python、Java 只做管理端**——比 03 文档原始的「前端→Java→Python 三层中继」高明：少一跳、少一次 JSON 序列化，且以 ADR 修订覆盖旧文档，体现决策闭环；
2. **「明确不做」清单**（Java 不做 DDL、不上消息队列、不做 WebSocket、不做 3D/口型、不引 TensorFlow、不引 crepe）——砍需求的能力比堆技术更能体现架构判断力；
3. **Fake 依赖注入 + CI 零真实密钥**——4 个 `Client` 抽象接口（`app/audio/base.py`）让 M1 就能跑通全链路，这是未来 6 周不被密钥/网络卡住的根基；
4. **版本矩阵钉死 + 锁文件冻结**（pnpm-lock / uv.lock + CI `--frozen`）。

## 3. 性能评估（重点审计，附量化依据）

### 3.1 端到端预算逐段审计（docs/06 第 8 章：7~10s）

| 环节 | 文档预算 | 评审评估 | 结论 |
|---|---|---|---|
| 上传 2~4s | 2~4s | 60s opus ≈1~3MB，网络正常即达 | ✅ 乐观但合理 |
| **ASR ≈2s** | 2s | **严重乐观**：faster-whisper small int8 在 4~8 vCPU 上 RTF 实测约 0.3~0.8，即 **60s 有效语音 ≈ 18~48s**，超预算一个数量级 | ❌ **头号风险** |
| 评分 ≈1s | 1s | 讯飞 ISE 整句批量 + 并发 2，1~3s | ✅ 基本合理 |
| LLM 首 token 1~2s | 1~2s | DeepSeek 实测 0.5~2s | ✅ 合理 |
| TTS 1~2s | 1~2s | edge-tts 单句 0.5~1.5s；**句级流式推送（音频为时间轴权威）是好设计**，避免了「等全部合成完才说话」的 10s+ 空窗 | ✅ 合理 |

> **M4 有 p95 达标红线（README 里程碑 4），而预算表第一环就是虚的——这是当前最大的性能风险。**

### 3.2 四个必须提前定死的执行问题

1. **CPU 密集任务 vs 事件循环**：torch / librosa / pyin 是同步 CPU 密集型。若直接放在 async 处理器里，会阻塞整个事件循环（SSE 心跳都发不出）。M2 落地前需成文规则：*任何 >10ms 的 CPU 工作进 `anyio.to_thread` / 线程池，模型单例 + 信号量限流*。当前 ADR 未覆盖此点（P1）。
2. **进程与并发模型**：uvicorn 默认单 worker，这其实是对的（whisper 内部是 C++ 线程池，多 worker 只会让每进程各载一份 ~500MB 模型）；但需要显式声明：`--workers 1` + 线程池 + 容器内存 ≥2GB + 模型侧信号量（文档只给讯飞设了并发 2，模型侧没有，多请求会排队雪崩）。
3. **唱歌 pyin 必须异步化**：180s 音频 pyin RTF>1，同步处理要 1~3 分钟。文档已规划「Redis 任务状态轮询」——**这是对的设计，但 M3 必须真做，不能退化成同步等待**。另建议用户演唱段分句并行提 F0（天然并行），或对比 yin（快一个数量级）作为降级。
4. **sklearn 模型不能每次请求重训**：docs/06 9.5 提到「用 sklearn 合成数据训练」，务必训练一次 → `joblib.dump` → 启动时加载，否则推荐接口每请求数秒延迟。

### 3.3 前端与传输

- SSE 中音频块用 base64（或 hex）有 33%~100% 膨胀——逐句音频块小（~100KB 量级），影响有限，**可接受**；但 `tts` 接口现在返回 **hex（2 倍膨胀）**，建议改 base64（P1）。
- Vue3 性能无压力；唯一提醒：当前 `package.json` 无 vue-router / Pinia，M2 引入时需在 ADR 补版本钉死，避免三人各引各的（P1）。

## 4. 可维护性评估

### 4.1 亮点

- **文档体系 A+**：ADR 唯一权威 + 两份 60+ 问拷问报告 + 错误码契约 + 修订说明 + 红线清单。这是本项目最大的无形资产，超过绝大多数企业项目。
- **工程化完备**：三端 CI + secret-scan + dependabot + pre-commit（只用纯 Python 钩子，Windows 兼容考虑周到）+ Conventional Commits + 分支保护。
- **代码质量高**：文件 20~91 行、类型标注齐全、接口抽象清晰、依赖注入规范，无「上帝类」。

### 4.2 文档与代码的一致性缺口（需修正）

| 问题 | 证据 | 级别 |
|---|---|---|
| `alembic check || true` 吞掉失败——ADR 声称的「CI 一致性探针」实际**永不失败** | `python-ci.yml` L42 | P0 |
| CI 无 `uv lock` 同步校验，而 Dockerfile 用 `uv sync --frozen --no-dev || uv sync --no-dev` 回退分支，lock 失配会被静默掩盖 | `services/python/Dockerfile` L17 | P1 |
| `infra/` 目录在 README / ADR 中被引用但**实际不存在**（无 nginx 配置 / seed / `.wslconfig`） | 目录实查 | P2 |
| 版本矩阵「钉死」但 pyproject 全是 `>=` 区间——靠 uv.lock 兜底可复现，但无升级纪律 | `services/python/pyproject.toml` | P2（约定如「季度 `uv lock --upgrade`」即可，勿过度工程） |

### 4.3 可维护性最大结构性风险：双 ORM 共享 PG

Java（JPA / `ddl-auto=none`）与 Python（SQLAlchemy / Alembic）映射同一 schema，这是**课程约束下的必然**，但要注意：

- 约束 / FK / 索引只应建在 Alembic（JPA 只做纯映射），否则漂移无解；
- **SQLite 单测 vs PG JSONB 的兼容问题**：M2 建表时若用 `JSONB` 特化类型，SQLite 测试会炸，需 `JSON().with_variant(JSONB, "postgresql")` 方案，现在就定；
- M2 把「核心纯逻辑」（评分公式、CTR / 完成率 / 跳出率指标、推荐、水平预测）作为**单测第一优先级**——纯函数、成本低、直接兑现 50% 覆盖红线；UI / E2E 对 3 人 6 周是奢侈品，Playwright 1 条冒烟足矣（已定）。

## 6. 分项评分与最终结论

| 维度 | 得分 | 评语 |
|---|---|---|
| 架构合理性 | **9/10** | 拓扑、职责边界、「不做」清单都正确；扣分在双 ORM 共享 PG 的结构性复杂度（课程约束，非过失） |

| 可维护性 | **9.5/10** | 文档 + 工程化 + 代码质量全面优秀；扣分在文档与实现的几处漂移 |

### 9.2 修正（评审意见与本项目 ADR 冲突或口径需细化处）

1. **P0-#2 ASR 延迟预算**：评审按 60s 上限测算（RTF 0.3~0.8 → 18~48s），论证成立；但预算表主要用于**对话短轮次**（5~15s 语音，RTF 0.3~0.8 → 2~12s），单看 60s 会过度悲观。**修正**：docs/06 §8 改为分层口径（短轮次 3~5s / ≤30s 演示 5~8s / 全程 7~10s），并保留评审建议的「M2 第 1 周 ASR 基准试验（15s/60s 实测 RTF 入 ADR）」行动项——这部分完全采纳。
2. **P1-#7 Redis 降级**：评审建议「无 Redis 拒绝启动」与 docs/06 既有 ADR（内存 fallback，保证「省 Redis 也能起」）冲突。**修正**：不拒绝启动，改为「内存 fallback + 限流宽松 + `/readyz` 报 degraded 且附 `redis:false`」的成文行为（demo 弹性目标优先）。
3. **P2-#13 schema drift 探针**：评审引用「空转的 `alembic check`」——P0-#4 修复后探针已非空转；JPA 实体 vs 迁移漂移检查成本高，列为 M2 有余力再做（不为追求探针完整性过度工程）。

### 9.3 汇总

- 评审总体判断（框架合适、不主张替换技术栈、A-）**接受**；除上述 3 处修正外，其余问题与修法全部采纳。
- 评审结论「当前最该做的是修 4 个 P0 + 一次 ASR 基准试验」与 docs/06 §16 一致，M2 第 1 周任务已含基准试验。
