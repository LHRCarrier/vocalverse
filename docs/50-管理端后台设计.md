## 2. 为什么独立 SPA（含 ADR 修订申请）

### 2.1 反方论证（先写清楚，避免"为了独立而独立"）

现有 ADR `docs/06 §2.1-4` 明确：「管理端 UI = `apps/web` 内 `/admin` 路由 + admin 角色，不建独立 SPA」。
该决策的前提是 **「管理端最小集仅 3 能力」**（`docs/06 §9.6`：用户管理 + 场景/歌曲 CRUD + 工单）。反对独立的理由充分：

1. 单前端复用已有 naive-ui 实例与 `themeOverrides`，零重复配置；
2. nginx/vite 网关已存在，`/admin` 路由开箱即用；
3. 少一个构建产物、少一条 CI、少一份 lockfile；
4. 管理端与 App 共用登录态（`vv_token`），无需第二套会话。

### 2.2 支持独立的理由（本轮需求变化后的重新评估）

用户本轮要求把管理端从「3 能力」扩到**权限控制台 + 三域业务面**，前提已变：

1. **职责分离是安全要求，不是偏好**：审核账号能登录 App 并发帖，等于审核员可以自审自帖；
   运维账号持有 trace 读取权（含潜在 prompt 内容）却能用同一身份在社区发言。
   共用一个 `users` 行 + 一个 JWT，无法在**领域层**隔离这两种身份。
2. **`users.role` 的 CHECK 是用户域资产**：扩词表需改 `0001` 建立的用户域约束，
   而 App 的所有鉴权、种子、测试都挂在该列上——改动风险外溢到不需要改的地方。
   （反方：可以加 CHECK 值；但这仍让"管理端角色"成为"用户角色"的一个子集语义。）
3. **构建/部署独立性**：控制台要独立域名或 `/console/` 前缀、独立 CSP、独立发布节奏；
   塞进 `apps/web` 意味着每次改管理台都要重跑用户端 `check-bundle.mjs`
   （该脚本断言 dist 中 `echarts` **零残留**、`/preview/i` 零残留——管理台必然要用 ECharts，直接冲突）。
4. **独立 SPA 命中 §2.1-5 的既有触发条件**：ADR 自己写了再评估条件
   ——「仅当出现**需要独立构建/独立域名的第二前端消费者**时，才考虑…独立网关」。
   本控制台正是第二个前端消费者。
5. 与用户本轮**显式指令**一致：「独立 web 端…模块化的隔离，不与现有的其余业务代码耦合」。

## 3. 模块设计（隔离边界）

### 3.1 三端隔离矩阵

| 层 | 新模块 | 允许依赖 | **禁止** |
|---|---|---|---|
| 前端 | `apps/admin/**` | 自身源码；npm 公共包；`docs/50 §11` token 表（**复制**，不 import） | import `apps/web/src/**`；`~@/` 别名指向 web |
| Java | `com.vocalverse.console.**` | `common/dto`（Envelope/PageView）、`common/trace`、`config`（JwtService/filter）、既有领域 Repository（只读+必要写） | **反向依赖**：任何模块 import `com.vocalverse.console.*` |
| Python | `app/console/**`（运维+trace+书籍） | `app/core/**`、`app/models/**`、`app/db/**` | 改动 `app/practice`、`app/agent/runtime`、`app/reading` 的业务语义；对既有路由做非兼容修改 |

**单向依赖规则（可 CI 校验）**：`console` 是**终端模块**——它可以依赖领域模块，领域模块不得依赖它。
落地方式：`services/java` 加一个 ArchUnit 式断言测试（或退化为脚本正则检查）：
`grep -r "com.vocalverse.console" src/main/java --include=*.java` 的结果必须**全部落在 `com/vocalverse/console/` 目录内**。
同理 Python：`app/console` 之外不得出现 `from app.console` / `import app.console`。

### 3.2 后端归属：按**数据归属方**分服务，不按界面分

控制台一个界面跨两个后端，是刻意的：**每个服务只暴露自己拥有（写）的数据**，控制台 SPA 是组合层。
这避免了「Java 读 Python 的表」——`docs/06 §19` 已就同类问题定过调（跨服务读表破坏 §10 写方矩阵）。

| 域 | 服务 | 拥有表 | 网关 |
|---|---|---|---|
| 身份 / RBAC / 审计 / 审核 / 运营（场景·歌曲·听力·题库·工单） | **Java** | `admin_*`(7) + `moderation_*`(2) | `/manage/api/v1/console/**` |
| 运维（指标·预警）/ LLM trace / 运营（书籍·章节·媒体治理） | **Python** | `ops_*`(3) + `llm_*`(3) | `/api/v1/console/**`（复用既有 `/api/v1/` → python 路由，**nginx 零改动**） |

`/api/v1/console/**` 在两服务下**子路径不重叠**：
Java = `auth|admins|roles|permissions|audit-logs|moderation|content`，
Python = `ops|library`。前端用两个 client 实例（`api/console.ts` / `api/ops.ts`），互不串线。

## 4. 权限模型

### 4.1 身份

**独立管理端身份**，与 `users` 表无外键、无字段共享。管理端账号**不能**登录 App，App 账号**不能**登录控制台。

- 口令：BCrypt（cost 10），长度 10–64，禁止与用户名相同；
- 登录失败锁定：同账号 5 次 / 15 分钟 → `locked_until = now()+15min`（`admin_login_attempts` 计数，Redis 不参与，保证审计可追溯）；
- 同 IP 限流 20 次 / 5 分钟（`admin_login_attempts` 窗口计数，无需 Redis）；
- 令牌：access JWT **HS256 / 15 min**，refresh **不透明随机串（32 字节 hex）** 存 `admin_sessions.refresh_token_hash`（sha256），TTL 12h，**一次性轮换**（refresh 即吊销旧行）；
- JWT claims：`sub`(adminUserId) / `aud`(`vocalverse-console`) / `iss`(`vocalverse-java`) / `role`(roleCode) / `perms`(权限码数组) / `typ`(`console-access`) / `jti` / `iat` / `exp`；
- **`aud` 是硬闸**：既有 `JwtAuthFilter` 与 Python 侧验签必须校验 `aud`，
  防止 App token 被拿去访问控制台、控制台 token 被拿去访问 App API。
  **实现口径（架构拷问 C-4，重要）**：App 侧过滤器**只拒绝"携带外来 `aud`"的令牌**——
  既有 App 令牌**没有** `aud` claim，因此该改动对在线用户**零影响**；
  **严禁**给新签发的 App 令牌补 `aud`：`AuthController.java:224` 复用同一个 access token 作 refresh
  （30 天 TTL，按 sha256 查库），补 `aud` 会让**全体在线用户强制登出**。

#### 4.1.1 首个超级管理员从哪来（v1 漏写，架构拷问 C-3）

没有引导，空库上的控制台**完全不可用**，CI 与联调也没有账号可登录。机制照仓库既有 seeder 体例：

| 项 | 做法 |
|---|---|
| RBAC 目录 | `@Order` 的 **Seeder**（不是迁移）：`admin_roles` 4 个内置角色 + `admin_permissions` 权限目录，按**自然键**（`code`）幂等 upsert。⚠️ **绝不写显式 id**（仓库 seeder 铁律），**绝不放在 Alembic 迁移里**（迁移纯 DDL + 单写方，见 `docs/51` B-11） |
| 首个超管 | **env 驱动的一次性 bootstrap**：`VOICEVERSE_CONSOLE_BOOTSTRAP_USERNAME` / `_PASSWORD`；**仅当 `admin_users` 为空**时创建 `super`；口令为空/过弱则**拒绝启动并给出原因**（不允许"默认口令"这种后门）；日志打印"已创建引导账号 <username>"但**永不打印口令** |
| 测试 | 独立 fixture 账号（测试 Profile 下由 seeder 建），**不复用**生产引导路径 |
| 上线后 | 引导变量应清空；账号由 `console:admin:write` 管理（本控制台**不提供自助注册**） |

> **为什么 perms 进 JWT（而不是每请求查库）**：控制台接口 QPS 低，但角色变更需要即时生效。
> 折中：`perms` 进 JWT 换读取性能，**代价 = 最长 15 分钟权限滞后**（与既有 admin 降权问题同口径，`docs/06 §7` 原定 15min access）。
> 补偿：
> ① access TTL 从既有实现口径（3600s）**收紧到 900s**，只对控制台令牌生效；
> ② 改角色/停用账号时**同时吊销该账号全部 `admin_sessions` 并 bump `admin_users.token_epoch`**；
> ③ Java 侧每请求只读一次 `admin_users.status + token_epoch`（走主键，微秒级），不读权限表。
> `token_epoch` 在 JWT 中作为 `epo` claim——因此**停用/降权在下一个请求即生效，无需等 TTL**。
> Python 侧无法读该表，故 Python 端点接受 ≤15 分钟的滞后（已登记为已知缺口，见 §15）。

### 5.2 通用约定（沿用 `docs/10` / `docs/11`，不得偏离）

- 表名/列名 `snake_case`；主键 `bigint_pk()`（`BIGINT IDENTITY`，SQLite 变体 `Integer`）；
- 时间戳用 `TimestampMixin`（`created_at` / `updated_at` `timestamptz NOT NULL server_default now()`），
  **`updated_at` 由写入方维护，无 DB 触发器**（Java 侧必须显式 `setUpdatedAt(Instant.now())`）；
- 枚举 = `VARCHAR + 显式命名 CHECK`（**绝不使用 PG ENUM**），命名 `ck_<table>_<col>`；
- JSON 用 `jsonb()`（`sa.JSON().with_variant(postgresql.JSONB,"postgresql")`，兼容 SQLite 单测）；
- **软删除一律用 `status` 字符串**，仓库全域无 `deleted_at`——本设计沿用；
- 新表必须注册 5 处：模型文件、`app/models/__init__.py`（import + `__all__`）、
  迁移 `0013_<语义>.py`（`down_revision="0012"`）、`tests/test_models.py EXPECTED_TABLES`、
  Java 写的表进 `scripts/check_single_writer.py:JAVA_WRITTEN_MODELS`。

## 6. 业务逻辑与既有功能联动

### 6.1 运营：上架 / 下架

**语义拍板**（统一 4 个内容域）：

| 动作 | `status` 迁移 | 用户侧可见性 | 审计 |
|---|---|---|---|
| 草稿 | `draft` | 不可见 | `content.<domain>.publish` detail `{prev,next:'draft'}` |
| 上架 | `draft|archived → published` | 可见 | 同上 |
| 下架 | `published → archived` | **不可见，但保留行**（不做物理删除） | 同上 |
| 归档即软删 | —— | 既有 `DELETE /api/v1/admin/...` 语义 = archive，**控制台不再提供物理删除** | 同上 |

**上架前置校验（`PublishService`）**——这是"应该做什么"里最容易漏的一条：

1. **歌曲**：必须有 `lrc` 行（≥1 段）且 `audio_url`/`ref_melody` 至少一个非空，否则 `46011`（上架校验失败）；
2. **听力素材**：必须有 `audio_url` + `transcript` 非空；
3. **场景**：必须有 `opening_line` + 目标语料（语言点）≥ 3 条；
4. **书籍**：`book_chapters` 至少 1 章且每章 `status='published'`；书本身 `status` 才有意义；
5. **媒体**：`status='ready'` 才允许被引用。

> 校验放在**服务层**而非 controller，且**返回字段级错误列表**（`46011` + `data.violations[]`），
> 让运营一次看到"缺什么"而不是逐个试。

**联动回路（重要）**：`songs` / `listening_materials` 虽已有 admin CRUD，但**Python 侧从不按 status 过滤**
（侦察结论：唱吧与听力推荐池尚未实现）。因此：
- 本期**只做** `status` 的正确写入 + 在控制台明确标注「该内容域用户侧消费方尚未实现，下架暂无用户可见效果」；
- **不伪造**"下架立即生效"的效果；登记为已知缺口（§15 G-2），待唱歌/听力模块落地时统一加 `status='published'` 谓词。

### 6.2 审核：工单状态机与处置动作

```
                 ┌──────────── escalate ────────────┐
                 ▼                                  │
 pending ──assign──> pending(assignee) ──decide──> approved  (内容保留，单关闭)
    │                                    ├──────> rejected  (内容保留 + 举报驳回)
    │                                    └──────> withdrawn (举报人撤回/自动关闭)
    └── decide(hide/delete) ──> approved，且 target.status := hidden | deleted
```

**处置动作 → 目标表写入（同一事务）**：

| 决定 | `moderation_cases.status` | 对目标 | 幂等保护 |
|---|---|---|---|
| `approve`（通过，内容保留） | `approved` | 不动 | 已是终态 → `46010` |
| `hide`（隐藏） | `approved` | `posts.status='hidden'` / `post_comments.status='hidden'` / `media_assets.status='hidden'` | 目标已 hidden → 幂等成功 |
| `delete`（删除，软删） | `approved` | `status='deleted'` | 同上 |
| `reject`（驳回举报） | `rejected` | 不动 | 同上 |
| `escalate`（升级） | `escalated`（+priority=1） | 不动 | 保持队列中 |

**联动硬点**：
1. **隐藏必须真正生效**——`PostRepository` 的 8 处硬编码 `status='visible'` 谓词（`:40,68,89,95,102,108,113,118`）
   必须收紧为 `status NOT IN ('hidden','deleted')`（或 `status='visible'` 保持不变 + 隐藏时直接写 `deleted`）。
   **本设计选前者**（新增 `hidden` 语义可见性），并**配套测试**：隐藏后帖子不出现在 feed/详情/评论列表。
2. **计数一致**：隐藏不改 `like_count`/`comment_count`（隐藏≠删除，恢复后计数不漂移）。
3. **作者可见性**：`hidden` 对作者也隐藏（与 `docs/38 §统一可见谓词` 一致），
   作者在「我的帖子」看到 `hidden` 状态与未通过原因（`decision_note` 经**公开面白名单**下发，不含审核员身份）。
4. **自动送审**（`source='auto'`）本期**不接**关键词引擎（敏感词库为 P1），
   但**建单入口预留给 `POST /api/v1/console/moderation/cases`**，未来接引擎时不改表。

### 6.3 运维：指标 → 预警 → 处置

```
Python collector(60s) ──写──> ops_metric_samples
```

**预警规则内置 6 条 seed**（`enabled` 默认 true，阈值可改）：

## 7. LLM Trace 设计（对齐 DSH GenAI span 树）

### 7.1 参考对象

参考 DeepSeek Harness 的开源观测插件 **`loongsuite/dsh-plugin`**（Apache-2.0，
OpenTelemetry GenAI 语义约定）。其核心数据模型：

```text
一次 turn = 一个 trace
ENTRY
└── AGENT
    └── STEP
        ├── LLM      ← 每次真实 LLM 尝试一个 span（重试在同一 STEP 下可见）
        └── TOOL     ← 按 call id 与结果关联
```

移植的五条设计原则（**逐条映射到本项目**）：

| DSH 原则 | 本项目落地 |
|---|---|
| 一次 turn = 一个 trace | `llm_traces`：`kind` 区分 turn/free_chat/defense/summary/conclude… |
| 每次 LLM 尝试独立 span，重试同 STEP 下可见 | `llm_spans.retry_index` + 同 `parent_span_id` |
| 工具调用与结果按 call id 关联 | `llm_spans.tool_name` + `attrs.call_id`；结果作为 output span 的子节点 |
| 错误/中断/未完成流**关闭活动 span 并标 error**，不留悬挂 span | `status ∈ (ok,error,aborted,incomplete)`；**收尾钩子**保证异常路径也 close（§7.3） |
| **内容捕获默认关**，结构元数据与 token 仍导出 | `llm_span_contents` **独立表**，`content_captured=false` 时不写行；`APP_LLM_TRACE_CONTENT_CAPTURE` 默认 `false` |

另外借鉴其**导出器参数**：批量 512 / 队列 2048 / 导出间隔 5s —— 本项目等价物见 §8.3 的写入队列。

### 7.2 本项目 span 树（Python 侧）

一次「场景对话回合」：

```text
ENTRY                      (POST /api/v1/practice/turns，attrs: http.method/path/request_id)
├── ASR                    (client，attrs: engine=whisper|fake, audio_ms, text_chars)
├── AGENT                  (attrs: persona, turn_index, scene_code)
│   ├── RETRIEVE           (internal，学习者画像/语料检索，attrs: hits, cache=hit|miss)
│   ├── STEP               (attrs: step_index=0)
│   │   └── LLM            (client，model, prompt/completion tokens, ttft_ms, finish_reason, retry_index=0)
│   ├── STEP               (step_index=1，meta 补偿)
│   │   ├── LLM            (retry_index=0 → error: 429)
│   │   └── LLM            (retry_index=1 → ok)   ← 重试可见
│   └── TOOL               (internal，tool_name=usage_log，attrs: call_id)
└── TTS                    (client，attrs: provider=edge|kitten, chars, cached=true|false)
```

一次「自由说」：`ENTRY → LLM(stream) → TTS`（流式下 TTFT 有意义，`finish_reason` 记录）。

### 7.3 采集实现（**最小耦合**）

侦察给定三个候选注入点，按"改动半径"排序采用：

| 优先 | 注入点 | 做法 | 理由 |
|---|---|---|---|
| **P0** | `app/console/trace/recorder.py` 提供**装饰器/上下文管理器** `span(name, **attrs)` | 在既有 4 个 LLM 调用点（`practice/orchestrator.py:430`、`agent/runtime/meta_executor.py:123`、`agent/domains/summarizer.py:170`、`practice/orchestrator.py:1019`）**各加一行** `with span("LLM", ...)` | 改动 ≤10 行、语义显式、不需要包装 LLM client 的全部方法 |
| P1 | 包装 `get_llm_client()` 返回对象 | 透明代理 chat/chat_with_usage/stream/stream_rich | 一次覆盖所有调用，但对 `getattr(...,"stream_rich",None)` 的鸭子类型有隐性耦合 |
| **不做** | 改 `usage_log` 表 | —— | 见 §7.4 |

**ContextVar 贯通**（照抄既有 `app/core/trace.py:17` 的 `_request_id` 模式）：

```python
# app/console/trace/context.py
_current_trace: ContextVar[TraceContext | None]  # trace_id, kind, session_id, user_id, request_id
_current_span:  ContextVar[SpanContext  | None]  # span_id, name  → 自动做 parent
```

`ENTRY` span 由**中间件**开（已能复用 `get_request_id()`），
`AGENT/STEP` 由 orchestrator 开，`LLM/TOOL` 由装饰器开 —— 全链路无需改函数签名。

**收尾保证**（DSH 原则 4 的硬落地）：

```python
try:
    ...
except BaseException as exc:            # 含 CancelledError / 超时
    ctx.close(status="aborted" if isinstance(exc, asyncio.CancelledError) else "error",
              error_code=..., error_message=str(exc)[:500])
    raise
else:
    ctx.close(status="ok")
finally:
    sink.flush(ctx)                      # 无论如何都把已完成的 span 落盘
```

**绝不**：在热路径 `await` 数据库写入；**绝不**：让采集异常冒泡到业务
（`recorder` 全部内部 `try/except` 吞掉并计数 `trace_dropped_total`）。

### 7.4 与既有 `usage_log` 的关系（**双轨，不合并**）

- `usage_log` **保留不动**：它是"计费/配额"口径（`source/model/prompt_tokens/completion_tokens/meta`），
  已有 4 个调用点与测试；
- `llm_traces/spans` 是"观测/调优"口径（延迟、TTFT、重试、finish_reason、状态）；
- 两者**不互相写**，通过 `(trace_id ≈ request_id, started_at)` 弱关联。
- **不合并的理由**：合并需要改 `usage_log` 的写入点与所有断言它的测试（侦察：`tests` 有依赖），
  且两种口径的保留期不同（配额需长期、trace 只需短期）。
- **登记为已知缺口**：`usage_log` 目前**遗漏** free_chat / defense / `POST /llm/chat` 三处用量
  （侦察结论）——**本设计不修**（属业务口径问题，另立工单），但 trace 层会**完整覆盖**这三处调用，
  因此控制台能看出"用量统计与 trace 计数不一致"，正是调优线索。

### 7.5 内容捕获的隐私设计

| 项 | 取值 |
|---|---|
| 默认 | `APP_LLM_TRACE_CONTENT_CAPTURE=false` → `llm_span_contents` **零行**，`content_captured=false` |
| 单条上限 | `content_max_chars = 128000`（对齐 DSH 默认），超出截断并置 `truncated=true` |
| 脱敏 | 写入前过 `redact()`：邮箱/手机号/`sk-*`/`Bearer *`/长数字串 → `***`，命中置 `redacted=true` |
| 权限 | 读取内容需 `ops:trace:content:read`（独立权限码） |
| TTL | 内容默认 **72h** 清理；trace/span 默认 **30 天** |
| 审计 | 每次内容读取写 `admin_audit_logs(action='ops.trace.content.read')` —— **看别人的 prompt 是留痕行为** |
| 界面 | trace 详情页顶部常驻提示条：「内容捕获：开启（本环境）/ 关闭」，关闭时内容页显示"未捕获"而非空表 |

## 8. 并发性能设计

### 8.1 预算（本地单机，作为验收口径）

| 场景 | 目标 | 保障手段 |
|---|---|---|
| 控制台登录 | p95 < 400ms | BCrypt cost 10 + 单条主键查询 |
| 列表页（page_size=20） | p95 < 300ms | 覆盖索引 + 投影查询（只取列表列） |
| trace 列表（含 30 天过滤） | p95 < 350ms | `ix_llm_traces_kind_started` / `_started` |
| trace 详情（≤200 span） | p95 < 400ms | 一次 `(trace_id, seq)` 覆盖索引取全树，内存组树 |
| 指标查询（7 天 × 6 指标，step=600s） | p95 < 800ms | **服务端按 step 二次聚合**（`date_trunc`/`floor`）而非回传原始 60s 桶 |
| 审核队列 | p95 < 250ms | `ix_moderation_cases_queue (status, priority, created_at)` |
| 采集对业务的影响 | **< 1% 额外延迟** | 见 §8.3：完全异步 + 有界队列 |

### 8.2 数据库并发

- **Python 连接池**：既有 `pool_size=20 / max_overflow=10 / pool_timeout=5`（`db/__init__.py:40`）**不改**；
  trace 写入使用**独立短事务**并限制并发写入协程数 `_TRACE_WRITE_CONCURRENCY = 2`（防止 trace 写入抢占业务连接）。
- **Java 连接池**：控制台查询走只读事务（`@Transactional(readOnly=true)`），
  Hikari `maximum-pool-size` 保持默认，但**控制台模块的连接使用不超过 4**（用独立 `@Qualifier` 数据源会过重，改为信号量 `Semaphore(4)` 包住控制台 repository 调用）。
- **锁顺序**：审核决定的事务顺序固定 `moderation_cases → 目标表`，禁止反向，避免与未来"目标表触发审单"形成死锁环。
- **隔离级别**：保持 READ COMMITTED。审核决定的并发安全靠**条件 UPDATE**（`WHERE status='pending'`，`rowsAffected=0` → `46010`），不靠 `SELECT … FOR UPDATE`（避免长事务）。

### 8.3 采集写入：有界队列 + 批量 + 丢弃计数

```python
# app/console/trace/sink.py
QUEUE_MAX      = 2048     # 对齐 DSH maxQueueSize
BATCH_MAX      = 512      # 对齐 DSH maxExportBatchSize
FLUSH_INTERVAL = 5.0      # 对齐 DSH traceExportIntervalMs
```

- `recorder` 只把**已结束**的 trace（含 span 列表）`put_nowait` 进 `asyncio.Queue`；
- 后台单任务 `flush_loop`：`get` → 攒到 `BATCH_MAX` 或 5s → **一次事务批量 INSERT**；
- 队列满 → `put_nowait` 抛 `QueueFull` → **丢最旧？不**：**丢当前**（`trace_dropped_total += 1`），
  理由：丢当前是 O(1) 且不破坏已在队列中的顺序；丢最旧需要 deque 语义且会让"迟到"的 trace 先入库。
- **可观测**：`trace_dropped_total` / `trace_written_total` 本身就是指标（§8.4），
  **采集自身的健康也在控制台上可见**（否则"trace 没了"会被误判为"没调用"）。
- 进程退出：`lifespan` 的 shutdown 阶段 `await sink.drain(timeout=5)`。

### 9.2 Request-Id 贯通（补两处断点）

现有贯通链路：nginx `$request_id` → 各 location 透传 → 响应头回写；
Python `trace.py` 中间件 ContextVar + 日志 filter；Java `RequestIdFilter` MDC。

**断点 1**：Java **出站不透传**——Java 无 HTTP 客户端，但 **Python 的 `internal_client.py` 调用 Java 内部接口时未带 `X-Request-Id`**（侦察确认）。
→ **本期修**：`app/core/internal_client.py` 统一注入 `X-Request-Id: get_request_id()`。
（一处改动，让"控制台操作 → Java → Python"整链路同 id 可查。）

**断点 2**：控制台审计日志此前无从拿到 request_id（因为没有审计日志）→ 本期由 `RequestIdFilter` 把 MDC 暴露给 `AuditService` 一起落库。

### 9.3 日志内容纪律（红线）

- **禁记**：口令（含哈希）、任何 token、refresh token、`llm_span_contents.content`（除非内容捕获开启且写入独立表）；
- `admin_audit_logs.detail` 走**字段白名单**（`FIELD_ALLOWLIST` 常量）：只允许
  `status/code/name/title/priority/severity/enabled/prevStatus/nextStatus/reasonCode/assigneeId/permissionCodes/…`；
  白名单外的键**静默丢弃并计数**（`audit_detail_dropped_total`）。
- 审计日志**与业务写同事务**：`@Audited` 注解由 AOP 在**同一 `@Transactional`** 内插入，
  保证"改了但没留痕"不可能发生；若审计插入失败 → 整个业务事务回滚（宁可写不成功，不可无痕写成功）。
- 保留期：`admin_audit_logs` **365 天**（合规最低），`admin_login_attempts` 90 天，`ops_metric_samples` 7 天，
  `llm_traces/spans` 30 天，`llm_span_contents` 72h。

## 10. API 契约

### 10.1 约定

- Envelope：`{code:int, message:string, data:object|null}`，成功 `code=0`，错误 `data` 恒 `null`；
- 分页：`PageView{items,total,page,page_size}`，`page` 从 1 起，`page_size ≤ 100` 默认 20；
  **请求参数命名统一 `page` / `page_size`**（既有 users 用 `pageSize` 是历史分叉，控制台**不跟随**，新契约一律 snake_case）；
- 时间：请求/响应一律 **ISO-8601 with offset**（`2026-09-10T12:00:00+08:00`）；
- 幂等：所有"决定/处置"类 POST 支持 `Idempotency-Key` 头（可选），命中重复返回原结果；
- 契约快照：Java 侧改动必须 `CONTRACT_SNAPSHOT_GENERATE=1` 重生成 `java-openapi.json`；
  Python 侧必须跑 `scripts/refresh-openapi.ps1`。**两侧快照都要刷新**，否则 CI 红。
  ⚠️ 快照改了**必须同时**跑 `apps/web` 的 `pnpm gen:api`——否则 `frontend-ci.yml` 的
  `git diff --exit-code -- src/api/generated/` 这一步会红（已实际踩到一次，`docs/51 §7.3`）。

### 10.1.1 契约纪律（**本轮最贵的一课，写死在这里**）

> **本文档的端点清单只承诺「路径 + 方法 + 权限码 + 语义」；字段形状以实现为准。**

原因是真实发生过的：控制台的 DTO 是**照本文档写、在实现之前写**的，于是成批出现"看着合理、后端没有"
的字段与**根本不存在的端点**（`PATCH /auth/me`、`POST /auth/password`、`GET /admins/{id}/sessions`），
以及发错字段名的请求体（`{newPassword}` vs `{password}` → 恒 46007）。页面不会因此报错——
它会**静默显示空白**，比崩溃更难发现。完整清单见 `docs/51 §7.3`。

因此三条硬性纪律：

1. **DTO 必须在实现之后对着源码核一遍**——不是"照文档写然后祈祷"。核对对象是
   Controller 的 `record`（Java）与 route 的返回字典（Python），**不是**本文档。
2. **每个域的 DTO 必须由契约测试钉住**：控制台现有 `api/__tests__/console.contract.test.ts` +
   `ops.contract.test.ts`（16 例）**桩掉 `fetch`、断言真实 URL/方法/请求体**。
   这类测试在修复前必红——这才是证据；"两边我都看过"不是证据。
3. **后端不提供的字段，不许在前端编**：删掉该显示项并给出"后端未提供"的说明，
   或者**回头扩后端**（例：`/ops/traces/stats` 缺 `trend`/`by_model` → 已回派扩接口，
   而不是让"调用量趋势"这张图消失）。**"删掉一个功能"和"加一个后端聚合"是两种完全不同的处置**，
   前者要在文档里登记为缺口，后者才叫闭环。

## 11. 前端 UI/UX 设计与布局统一

### 11.1 设计系统选择（本轮最重要的 UI 决策）

侦察结论：仓库有**三套并存的设计系统**（`u-*` 纸墨 = 20 个 `/m/*` 页在用的真形态；
`s-*` Clean = 仅 `LoginView` 用；legacy `tokens.ts` 杜邦绿 = 唯一 naive-ui themeOverrides 来源）。

**决策：新建第四套？不。** —— 采用**「派生 + 降级」**策略，避免第四套设计系统：

| 维度 | 取值 | 来源 |
|---|---|---|
| 色彩 | **完全继承 `u-*` 纸墨**（paper/ink/sub/weak/track/accent） | `mobile-uic.css:14-61`（用户实际看到的形态） |
| 圆角 | **降级到控制台尺度**：卡片 16 / 控件 8 / 胶囊 999 | 依 `docs/13:27`「组件 8px / 卡片 12px / 胶囊 999px」的控制台精神 |
| 字体 | 系统栈 `'Segoe UI','Microsoft YaHei UI','Microsoft YaHei',sans-serif` | 仓库**没有可复用的 Web 字体基线**：唯一真实加载的是 `apps/web/src/styles/mobile-soft.css:11` 的 Google Fonts（Plus Jakarta Sans），而该 CSS **只被 `LoginView.vue` 引入** → 只在 `/login` 生效，成不了全局基线；`Nunito` 被 `tokens.ts`/`global.css` 引用但**无 `@font-face`、无字体链接**（实测恒回退）。**不引 CDN 字体**（内网/离线可用）。代价见 §12.4 偏离 #1 |
| 图标 | **Tabler only**，`unplugin-icons` 编译期内联 | `docs/35:27` 硬规则；`docs/32` 选型 |
| 组件库 | naive-ui，**单一注入点** `themeOverrides`，`primaryColor = #2f6bff` | `docs/32:53-54`「Naive UI 保留给 Web 管理端」；**不用退役绿 `#16A34A`** |
| 图表 | **lieflat Mono 单一色彩系统** | §12 |
| 动效 | 仅 `transform/opacity/box-shadow`，60/150/220ms，`prefers-reduced-motion` 降级 | `docs/33`/`docs/35` |

**为什么继承 `u-*` 而不是 `tokens.ts`**：`tokens.ts` 的杜邦绿是**已退役**的品牌色
（移动端已改 `#2f6bff`/`#2d79f3`），拿它做控制台会让控制台比 App 更"旧"；
而 `u-*` 的 `ink = #1c1c1a` 与 lieflat Mono 的 `INK = #1C1C1A` **完全相同**、
`paper = #f5f4f1` 与 Mono `PAPER = #F0EFEB` 同族 —— **纸墨体系天然让"控制台 UI 与图表"视觉统一**，
这是本轮能同时满足"布局统一"和"图表设计参考 lieflat"的关键。

## 12. 图表设计（lieflat-charts 全量候选审计）

### 12.1 色彩系统与引擎

- **色彩系统：锁 Mono**（纸灰 `#F0EFEB` + 炭黑 `#1C1C1A` + 7 级灰阶）。
  理由：① lieflat 硬规则「同一交付只用一种色彩系统」；② Mono 与产品 `u-*` 纸墨同族（§11.1）；
  ③ 控制台图表是**有序单序列/排名/构成**为主，符合 Mono「明度即数据」的契约；
  ④ 无彩色 → 无「类目 >6 还要彩色」的容量问题。
- **引擎：手写 SVG 为主 + ECharts 为辅**（`echarts/core` 按需 + `useECharts` 模式 **copy 自 `apps/web/src/composables/useECharts.ts`，不 import**）。
  lieflat 的 Lupi/Basics 两组本身就是手写 SVG（发丝线 0.5–0.7px，ECharts 默认线宽做不到）；
  ECharts 只用于 F13 矩形树图与 G17 实时流。
  **首屏体积**：apps/admin 独立构建，不受 `apps/web` 的「echarts 零残留」断言约束（这正是独立 SPA 的收益之一）。
- **硬规则继承**（违反即返工）：柱状图不断轴；面积用 `Math.sqrt`；动画 `quarticOut` 快进快停；
  点阵 stagger 8–15ms、条形 80–130ms；`prefers-reduced-motion` 降级；
  演示/兜底数据用确定性 `rnd(i,k)` **禁用 `Math.random()`**；卡片四件套（结论式标题 + 副标题 + 图 + 来源行全大写）。

### 12.3 库外图型：Trace 瀑布的翻译流程（SKILL §6）

1. **先回答本体**：这张图编码什么？——每个视觉通道对应哪个数据维度？
   - 横轴位置 = 绝对时间（trace 起点起算的 ms）；
   - 条形**长度** = span 耗时（`duration_ms`）→ **长度∝时间，比例必须诚实**（不断轴）；
   - 条形**纵向位置/嵌套缩进** = span 树层级（`parent_span_id`，深度 × 14px）；
   - **明度** = 状态（`ok` = ladder[0]，`error` = 最深 + 端头标记，`aborted` = ladder[4]）；
   - 旁注引线 = `ttft_ms`（首 token 延迟，画成 span 内部的细分隔线）。
2. **找最近的亲戚**（⚠️ v1 在此**结论错误**，UI 拷问 P0-1 已用 gallery 源码证伪）：

### 15.4 回退剧本（**v1 的"可干净回退"是错的**，拷问 C-13 修正）

> v1 声称"迁移只新增表 + 一个加列，可干净回退；不含数据迁移"。逐条核对后**三处不成立**：
> ① `media_assets`/`direct_messages` 的 CHECK 扩张：表内一旦存在 `hidden` 行，`downgrade` 还原 CHECK **会直接报错**（真 PG 实测到了这个失败）；
> ② `book_chapters.status` 的 `downgrade` 会**丢列**，已下架章节的信息**不可逆丢失**；
> ③ 迁移内**没有**数据 upsert（这是对的！），但 v1 曾计划把权限码/预警规则塞进迁移 —— 那部分改为 Java/Python 侧 seeder，因此**种子数据不在回退范围内**（也不需要回退，seeder 幂等）。

```text
回退步骤（必须按序，且第 1 步不可跳）：

1) 【归一化，不可跳】把隐藏态归零，否则第 2 步的 CHECK 还原必然失败：
   UPDATE media_assets    SET status = CASE WHEN status='hidden' THEN 'ready'   ELSE status END;
   UPDATE direct_messages SET status = CASE WHEN status='hidden' THEN 'visible' ELSE status END;
   -- ⚠️ 这会**丢失"曾被隐藏"的事实**。执行前先记录影响行数与人审：
   SELECT count(*) FROM media_assets WHERE status='hidden';
   SELECT count(*) FROM direct_messages WHERE status='hidden';
   -- 若需要保留该事实，先归档：把结果导出到 admin_audit_logs.detail 或离线留档。

2) uv run alembic downgrade 0012
   → 删 15 张新表；还原两处 CHECK（旧名）；4 条 RENAME 反向还原；DROP book_chapters.status
   → ⚠️ 不可逆点：book_chapters 的 draft/archived 状态永久丢失（列被删）

3) uv run alembic upgrade head    # 前滚验证：回退后必须能再升上来且零 diff
4) uv run alembic check           # 零 diff 门禁
```

**回退前必须确认**：`admin_users` 里的账号会随 `admin_audit_logs` 一起消失（表被删）——
审计日志**没有独立备份**，回退等于**丢失全部管理端操作留痕**。
因此**生产环境不要用 downgrade 回退控制台上线**；正确做法是**前滚**（再发一个迁移修问题）。
