## 0. 关键结论（一句话）

**唱歌模块是「schema 就绪、实现空白」**：数据表（`songs`/`lrc`/`song_pitch_refs`/`sing_attempts`）与评分口径（ADR §9.4）都已定稿并迁移，但**没有评分器、没有参考旋律提取器、没有唱歌端点、没有 `create_session` 的 sing 分支**。集成风险集中在 4 处：**① 参考旋律从哪来（`audio_url` 是 URL、无人声分离依赖）；② 逐帧音高曲线无存储（前端 D3 唱歌图拿不到数据源）；③ 参考旋律缺失/逐句表达（`ref_seq`/`no_ref` 未落地）；④ 音频 24h 清理无调度（合规高险）**。

## 1. 调研基线（已核实，作为拷问事实底座）

**三端**：`apps/web` Vue3.5+TS strict+Vite6+naive-ui+UnoCSS+Pinia；`services/python` FastAPI（ASR/TTS/发音评分/唱歌评分/LLM/推荐/埋点，无管理端 CRUD、不做 JWT 签发）；`services/java` Spring Boot（仅管理端 CRUD + JWT 签发）。单写者（docs/10 §3）：Python 写 `scenario_messages/song_pitch_refs/sing_attempts/attempts/scores/events/reports` 等；Java 写 `songs/lrc/scenarios/listening_materials/placement_questions/users/tickets` 等。

**评分口径（docs/06 §9.4，M3 做深）**：
- 音准=逐句基频 vs **离线预提取参考旋律音高序列**偏差(cent)映射：≤50→90+/≤100→70~90/≤200→50~65/>300→<40；
- 节奏=onset/beat 与 LRC 时间戳**相对** DTW 偏差映射：≤150ms→90+/≤300→75~90/≤600→55~75/>1000→<50；
- 发音=**复用口语评分引擎（讯飞 ISE）**；综合=`0.5·音准+0.2·节奏+0.3·发音`。
- 对齐：整体 BPM 倍率粗对齐 → Sakoe-Chiba window(≤10%)+斜率约束子序列 DTW 精对齐；音高轮廓先归一化。F0 用 **librosa pyin**（说话 75~300Hz、唱歌 65~800Hz；frame 2048/hop 512；清浊门限滤静音）；**不引 crepe/TensorFlow**。人工抽检 5 首×5 句、2 人 0-100、相关 r≥0.7。

**已落地 schema**（`app/models/content.py` + `practice.py` + `alembic/versions/0001_initial_schema.py`，SQLite 单测兼容 `tests/test_models.py:38`）：
- `songs`（level 1-4, source∈public_domain/original/demo_only, bpm, musical_key, audio_url, lrc_url, `pitch_ref_status`∈missing/building/ready/invalid）；
- `lrc`（song_id, seq, offset_ms, end_offset_ms?, line_text, source）；
- `song_pitch_refs`（lrc_id UNIQUE CASCADE, start_ms, end_ms, pitch_ref jsonb{f0s,notes}, extractor='pyin', version）；
- `sing_attempts`=SingAttempt（id, user_id, session_id SET NULL, song_id RESTRICT NOT NULL, lrc_id SET NULL, audio_url, duration_s, overall/pitch/rhythm/pron_score Numeric(5,2) 可 NULL, is_complete, expected_lines, `lines` jsonb[{seq,start_ms,end_ms,pitch_score,rhythm_score,pron_score,synced,skipped}], `alignment` jsonb{bpm_ratio,offset_ms,method,version}, created_at(不可变行)）；索引 user_created/song_id/lrc_id，**无 (user_id,song_id) 组合**；
- `sessions`（kind∈dialog/sing/defense, song_id→songs SET NULL, user_turn_count, assigned_turns, duration_s）。

**实现现状（缺失/未接线，重点）**：
- `app/audio` 只有 ISE（口语发音评分）；**无 SingScorer、无参考旋律提取器、无唱歌路由**。
- `create_session`（`app/practice/service.py:43`）只认 `dialog`/`defense`，`sing` 抛 "unsupported kind"；`SessionCreate`（`routes/practice.py:42`）**无 song_id 字段**。
- docs/21 §2.1 的 20 个 Python operation **无任何唱歌端点**。
- Java `ContentAdminController`：`SongUpsert.audioUrl` 是**管理端传入的 URL 字符串**（无文件上传实现）；`replaceLrc`（L328）只把 `pitch_ref_status` 从 ready→missing，**不通知 Python**（doc/20 §5 写到 Python 靠「离线检测重提取」）；**无「手动重提取/看提取状态」端点**；`SongUpsert` 允许 admin 直接写 `pitchRefStatus`（与「Python 翻转状态」写归属潜在冲突）。

**依赖**：`pyproject.toml` 已有 `librosa/soundfile/numpy/torch-cpu/scikit-learn`（可做 pyin/onset/beat）；**无 Demucs/UVR 人声分离依赖**。

**关键架构约束（docs/06 §6 / docs/20）**：uvicorn `--workers 1`；>10ms CPU 必进 `anyio.to_thread`；模型信号量（whisper 2）；内存≥2GB；唱歌/长音频评分走 **Redis 任务状态轮询（设计承诺 P0-1）**，**本期不引入 Celery/RQ/arq**；Redis 不可用→内存 fallback+degraded；音频≤20MB、唱歌≤180s、口语≤60s；原始音频 24h TTL（41001）。

**前端（docs/13 + `apps/web` 独立核实）**：D3 ^7 **仅**用于「唱歌评分逐句音准/对齐图」深度定制（M3）；ECharts ^6 用于报表；P5 仅品牌动效；Three.js 不引入；`/sing` 路由为占位（未实现），**无现成 D3 唱歌图**。录音组件 `audio/recorder.ts` 的 `VoiceRecorder` 可复用（`audio/webm;codecs=opus`，`MAX_RECORD_MS=60s`，`MIN_RECORD_MS=800ms`（误触丢弃），`MAX_BYTES=20MB`，`start(maxMs)` 按场景传——唱歌传 `maxMs=180000`）。`components/LieflatChart.vue` 与唱歌无关（sandbox iframe 渲染 HTML 报告）。
**对标 nightingale**（github.com/rzru/nightingale）：UVR Karaoke/Demucs 人声分离→WhisperX 逐词对齐→播放时实时麦克风音高→对参考旋律打分→星级+榜单；分析结果 blake3 哈希缓存，源文件变/手动重算才重算。

## 2. 评分算法与参考旋律（A 轴，完整采纳）

**已定**：pyin 提取（说话 75~300Hz、唱歌 65~800Hz、frame 2048/hop 512、清浊门限滤静音，**不引 crepe/TF**）；对齐=整体 BPM 倍率粗对齐 → Sakoe-Chiba window(≤10%)+斜率约束子序列 DTW 精对齐，音高轮廓先归一化；音准/节奏映射表；发音复用 ISE；综合权重公式。venv 已装 `librosa==1.0.0`（pyin/onset/beat/dtw 可用），**无 crepe/demucs**。docs/08 预期文件 `app/audio/pitch.py`/`sing.py`/`scorer.py` **均不存在**（只有 ise.py）。
**硬缺口 / 未决**：
- **A-G1（P0 最高，需拍板）参考旋律输入轨未定义**：`songs` 只有单条 `audio_url`（**本地路径字符串，非 HTTP URL**——`ContentAdminApiTest.java:90` 存 `/data/audio/twinkle.wav`，Python 按路径读共享卷、**不能下载**）；**无**独立人声/伴奏分离产物、**无 `vocal_ref_url` 字段**。若 `audio_url` 是纯伴奏 → pyin 提不出人声旋律；若是原唱混音 → 受伴奏/和声干扰。→ **建议拍板**：给 songs 增 `vocal_ref_url`（参考人声轨），或约定 demo 歌曲为「旋律主导/清唱版」，否则 `song_pitch_refs` 无可靠数据源。
- **A-G2（P0）monophonic 假设 vs 伴奏干扰**：pyin 单音高追踪对 KTV 和声/背景人声/和弦不鲁棒，docs 仅「清浊门限滤静音」，**无对伴奏干扰的处理**；节奏 onset/beat 取「用户人声」还是「伴奏/参考轨」也未言明（参考系混淆→相对 DTW 失真）。需含伴奏样本的基准来定标准。
- **A-G3（高）SingScorer 接口与 Fake 契约未定义**：现有抽象只有 ASR/TTS/Scorer(ISE)/LLM（`base.py`），**无 SingScorer/SingScoreResult/FakeSingScorer**；`librosa` 未在任何 app 代码 import。**建议**：新增 `SingScorer`（新 ABC，`score_song(...)->SingScoreResult`）或拆 `PitchExtractor`(pyin)+`SingingScorer`(DTW)+复用 `ScorerClient`(发音)；Fake 契约须与 `SingAttempt` 字段一致（含 `no_ref/synced/skipped`）。
- **A-G4（高）缺失降权/剔除规则未定义**：某句无音高/某路失败/整句失败时，`is_complete/expected_lines` 判定与「未评测」如何叠加、分项是否重分配（建议：某句无音高→该句不入综合平均，整首用「有效句均分」）——需拍板。
- **A-G5（中）发音=ISE on 唱音的风险**：ISE 按「语音评测」建模，唱音（音高/长音/颤音/连读吞音/节奏拉伸）会导致「完整性/流利度」失真、词级错误大量出现；且 `orchestrator.py:161` 把原始 webm 直接传 `ISE`（未转 16k wav，`audit V2.0 R-13`），唱歌**必须先转 16k mono**（复用 asr.py 的 ffmpeg 模式）。逐句调 ISE 还会放大免费额度（见 B-3）。
- **A-G6（中）逐句窗口 vs 整首 DTW 数据流 & `notes[]` 编码**：实现时须明确「先整首 BPM 粗对齐+子序列 DTW 求时间偏置→再按 LRC 句窗口逐句比对 F0」；`pitch_ref.notes[]` 是 MIDI 编号还是 note 名、以哪条为准；`end_offset_ms`（可空）缺末句推断规则（按 duration_s 或 BPM 拍数兜底）。
- **A-G7（中）路径语义三义性**：`audio_dir` 在 dev 相对路径（`services/python/data/audio`）/ docker 容器（`/app/data/audio`）/ 宿主（`./data/audio`）三种解释，Python 按 `songs.audio_url` 读文件**需先归一化**，现无归一化代码。

## 3. Python API 与异步契约（B 轴，完整采纳）

**形态已定【事实】（非未决）**：唱歌是**整首跟唱**——一次上传整首歌 → 服务端异步逐句评分 → 逐句结果（证据链 docs/02:41「选歌→录音→基频提取→DTW对齐→逐句评分→报表」、docs/01:43、docs/10:182-184 一行=一首歌、docs/07:88 完成率语义）。**不是**口语式「逐句重录 / SSE 每轮上传」。端点应「建会话（复用 `POST /api/v1/sessions`，kind=sing）→ 上传整首录音 → 轮询任务 → 取逐句结果」，不做口语 `POST /sessions/{id}/turns` 的 SSE 形态。

**结构性断链（必须修才能前进）**：
- **B-1（最高，依赖轴线 A）离线参考旋律提取无实现**：`song_pitch_refs` 只有模型、无写方；`pitch_ref_status` 全站恒 `'missing'`（content.py:164-166）；Java 只把它从 ready→missing，**没有任何 Python 离线任务把 missing→building→ready**。→ 音准（0.5 权重）无米下锅，唱歌端点会是空壳。
- **B-2**：`create_session` 对 `SING` 走 `else→400`（service.py:65-66）；`SessionCreate` 无 `song_id`（routes/practice.py:42-47）。→ 现契约无法建唱歌会话。
- **B-3 隐藏炸弹：逐句 ISE 发音限流配额**：发音复用口语 ISE（`cmd:"ssb"` 单句评分），一首 3 分钟歌 ≈几十句（`expected_lines`），`config.py:65 ise_rate_per_hour=60`（R-16 又指 ADR 实为 30/h）→ **单首歌即可打穿整小时配额，连唱即 429**。需拍板：全句发音评分（独立 `sing` 桶放宽）还是抽样句；与 R-16 一并裁决。
- **B-4 任务状态存储层未建**：docs/06 §8⑤ 要求「Redis 任务状态轮询，禁同步等待」；但 `redis_client.py` 无 task store、`state.py` StateStore 是会话运行时用、`redis_required=False` 内存兜底有重启丢任务风险。→ 建议「结果持久到 `sing_attempts`（DB，Python 写）+ Redis/内存只存进度」，状态机 `queued→processing→done|failed`，CPU 密集（pyin/DTW/numpy）必进 `asyncio.to_thread`（`asr.py:69` 先例）。
- **B-5**：唱歌端点挂 `Security(get_current_user_id)`（避免 R-1 的 `Depends` 缺陷）+ 独立限流桶；`<audio>`/Bearer 不兼容（R-5）唱歌回放会复用，需签名 URL 或 fetch+Blob。
- **B-6**：需新错误码 `40904`（参考旋律未就绪/缺失）、`41302`（时长超限，可选）、`50002`（提取/算法失败，可选），**先登记 `docs/api/error-codes.md` 再用**。
- **B-7**：唱歌**不建议调 LLM**（综合分只含音准/节奏/发音，docs/06 §9.4），故不走 llm 桶；但 `ise` 桶承载发音（见 B-3）。
- **B-8**：`orchestrator.py:161` `_safe_score` 直接把原始 webm/opus 字节传 `scorer.score()`，ISE 内部不转 16k wav（`ise.py` 无转码）——**既存缺口，唱歌发音继承**；需评分算法侧统一 `asyncio.to_thread` 转 16k mono wav（`ise.py:43` 要求 `audio/L16;16k`）。
- **B-9 契约流程**：新增端点必须走 docs/21 §7——改代码→`refresh-openapi.ps1`→`pnpm gen:api`→同步 docs/21 §2.1 + docs/api + error-codes→CI 三关卡（python-ci 快照==`app.openapi()`、frontend-ci `pnpm gen:api` 后 `git diff` 空）。

## 4. 数据模型与存储（C 轴，完整采纳）

**前提纠正（重要）**：`sing_attempts` 已建模且已入首次迁移，**非未建模**。
**设计判定**：✅ 独立表不并 attempts、一行=整首、列存聚合分+`lines` JSONB 逐句、写归属 Python 独享；分数为真实列可 SQL 聚合/排序；song 下架不毁历史（`song_id` RESTRICT，docs/11 Q-A16）；`song_pitch_refs` 随 lrc CASCADE 重建。
**真实/低成本需补**：
- **C-P1**：`get_audio` 归属校验只查 Attempt/ScenarioMessage，**漏 SingAttempt**（`routes/practice.py:244-257`；docs/06 §9.7 L182、docs/21 L58 同）→ 跟唱回放误 403。修复=owned 判定补 SingAttempt。
- **C-合规高险**：24h 惰性清理**无定时任务**，未回放音频**永久驻留**（docs/19 合规风险拷问报告:285-286,415 已列 M-04）。应补 lifespan 周期扫描 + 启动扫描。
- **C-可追溯性矛盾**：`lrc_id` 选 SET NULL，LRC 整首重写后旧跟唱 lrc_id 变 NULL，`lines[].seq` 无法解析回具体歌词行 → 「可解释同曲分数变化」（Q-B10 初衷）落空。建议 lrc 加版本保留历史行，或 sing_attempts 加 `lrc_version`/`scoring_version` 快照列；旧分一律不作废。
- **C-榜单/逐句跨用户分析**：当前无 `(user_id,song_id)` 组合索引、无 GIN。是否做榜单本身未定（docs/07 L337 只要求逐句评分含对齐）。若 M3 做榜单：**实时聚合 sing_attempts + 补索引**即可，勿建冗余 scoreboard 表（评分对象=user，非 profile，sing_attempts 无 profile_id）。
- **C-埋点**：无需新增唱歌 EventType（复用 `practice_complete(kind=sing)`，完成率由 `is_complete` 直接计数、非事件推导），但 M3 需补唱歌埋点核对表。
**迁移/演进**：base 表已入 0001，无需新迁移；后续加字段按「先改 docs/10 §4.3 → 改 model → autogenerate 新迁移（一 PR 一迁移，禁改 0001）→ alembic check 零 diff → 连测」（base.py:3；docs/10 §7.1）。
**文档漂移**：docs/21 L54 `sessions.kind∈practice/defense/placement` 与模型 `SessionKinds(dialog/sing/defense)` 矛盾；docs/06 L187 `compare_server_default=False` 与 docs/10 §7.2 自定义比较器不一致 → 需修订。

- **D-G5**：无「手动重提取 + 提取状态」端点；**薄管理端最小增补** = 歌曲 CRUD（已有）+ `POST /songs/{id}/recompute-pitch-ref` + `GET /songs/{id}/pitch-ref-status` + 每首歌成绩/榜单只读（P2）。

## 6. Web 前端与移动端（E 轴）

**已定**：D3（唱歌音准/对齐图，M3）、`/sing` 路由、录音组件可复用（`maxMs=180s`）。
**硬缺口 / 未决**：
- **E-G1**：前端唱歌形态随 B-G1（整首 vs 逐句）。推荐整首跟唱 + 唱完展示。
- **E-G2 实时可视化**：唱时要否实时音高/波形（像 nightingale 麦克风监听：参考旋律线 + 实时用户音高游标）。浏览器实时 F0 检测可用 `pitchy`（ACF 自相关，纯 JS）或自研 autocorrelation，但**噪声鲁棒性/延迟**是风险；若只做「唱完展示」，则后端已算逐句分，前端只画**静态**参考 vs 用户曲线——但（见 A-G2）用户逐帧 F0 未存储，故画不出「用户曲线」，只能画逐句柱状 + 参考线。→ 这是 A-G2/E-G2 联动决策。
- **E-G3 可视化选型**：docs/13 已定 D3 用于唱歌对齐图；ECharts 用于报表。**结论**：音准/逐句对齐（多序列时间轴、参考+用户重叠、逐句标注）用 **D3 自绘**（已定案、贴合 docs/13）；波形用 wavesurfer.js 或 Web Audio AnalyserNode；逐句柱状/雷达可用 ECharts。**不建议混用 p5**（仅品牌动效，且非数据图场景）。
- **E-G4 任务轮询**：唱歌评分若走 Redis 轮询，前端 `GET /sing/sessions/{id}/status` 轮询间隔/退避/中止；或唱歌也走 SSE（与口语一致）。展示「提取中/缺词/未就绪」状态（`pitch_ref_status` 影响入口）。
- **E-G5 移动端坑（5-8 条）**：① iOS Safari `getUserMedia` 必须在用户手势内 + HTTPS/localhost；② 授权后 `AudioContext` 常 suspended，需先 `resume()`；③ iOS 增益不可调，WebAudio 后处理降噪/增益；④ 切后台/锁屏断录音，提示保持前台；⑤ Android 需 mic 权限 + 安全上下文（非 HTTPS 直接拒绝）；⑥ 无手势禁播 TTS/音频，先 resume；⑦ PWA 安装提示 + 避 iOS 通知/后台音频限制；⑧ 20MB/180s 上限，前端可先压缩（Opus -> 16k mono），或后端转。

## 7. 运维/测试/合规/并发（F 轴）

**硬缺口 / 未决**：
- **F-G1 CPU 热路径**：pyin/onset/beat 是重 CPU >10ms，必进 `anyio.to_thread`（docs/06 §6）。新增信号量（sing scorer 并发 2？与 whisper/ISE 独立还是共用）。**uvicorn --workers 1 + 重任务是否拖垮同进程 SSE 对话心跳？** 唱歌评分若在 `BackgroundTasks` 同步跑会阻塞事件循环→建议独立 asyncio 队列 + 任务态轮询（docs/20 P0-1），不给对话热路径添堵；**不引入 Celery/RQ**（docs/20 明确）。
- **F-G2 配置/门禁**：新增 `APP_*` 配置（如 `APP_SING_CONCURRENCY`、`APP_PITCH_EXTRACTOR=pyin`、`APP_AUDIO_STORAGE`、模型缓存路径）与 `.env.example` 占位、docker-compose 回退一致；模型/产物放 `models/`(gitignored)、`data/`。
- **F-G3 测试/打桩**：新增 `FakeSingScorer`/`FakePitchExtractor` 保证 CI 零真实 Key；评分公式单测覆盖 ≥50%（docs/06 §13 门禁）；参考 `scripts/poc/whisper_rtf.py` 做唱歌评分/提取基准脚本；契约变更走 docs/21 §7 + CI 三关卡。
- **F-G4 合规**：商用音乐严禁入库（source 仅 public_domain/original/demo_only）；原始音频 24h 清理（但 C 轴指出无调度→补定时任务）；LRC 逐句版权跟踪；提取产物/人声分离产物的版权与存储。
- **F-G5 交叉风险**：与 R-1..R-16 叠加——唱歌是长任务+限流桶冲突（B-G4）+音频回放 Bearer 头不兼容 + 越权访问他人 sing_attempts（C-P1 归属校验）+ 错误码是否覆盖。唱歌模块要新增的合规/安全/性能风险清单需在实施 PR 里逐条勾。

## 9. 结论与建议下一步

**整体成熟度**：数据与口径**高度成熟**（schema/公式/对齐算法/前端栈都已拍板），**实现层从 0 开始**。风险不在「怎么算」，而在**「喂给算法的素材（参考旋律）与给用户的呈现（逐帧曲线）」两块数据断流**，以及 **4 条仅 schema 层面未考虑的生命周期/归属问题**（C-P1、24h 清理、参考缺失句、lrc 版本锚点）。

**建议实施顺序**（对齐 M3）：
1. **拍板 P0**（A-G1 参考来源、B-G1 形态、A-G2 是否存逐帧）——这三项锁死设计面；
2. 补 `create_session` sing 分支 + `SessionCreate.song_id` + 校验（published + ready），建 sing 会话 + 端点骨架（B 轴）；
3. 实现 SingScorer（pyin + DTW + ISE 复用）+ Fake 打桩 + 评分公式单测（A/F 轴）；
4. 补 C-P1 归属校验、24h 清理调度、参考缺失句表达、lrc 版本锚点；
5. Java 薄管理端最小增补（重提取触发 + 状态 + 榜单只读），移除 SongUpsert.pitchRefStatus 写；
6. 前端 `/sing` 整首跟唱页 + D3 逐句音准图 + 状态轮询 + 移动端录音手势/AudioContext 处理。

> **后续**：六轴（A/B/C/D/E/F）系统集成拷问**全部完成**；主轴结论见上文，逐轴细目与逐问 Q/A 详见对应附录（**A/B/C/E/F** → `docs/singing/22-英文歌打分系统集成拷问报告-轴线X.md`；**D** → `docs/singing/英文歌打分-系统集成拷问-轴线D-离线参考旋律提取与Java薄管理端边界.md`，逐轴全文已落库）。建议先按下表「P0 六项」拍板，再进入 M3 实现。
