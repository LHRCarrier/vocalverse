# 英文歌打分 · 系统集成拷问报告（轴线 A：评分算法与参考旋律）

> 完整逐问 Q/A，主报告见 `docs/singing/22-英文歌打分系统集成拷问报告.md`。

## 0. 拷问目标
判定「英文歌打分」在算法可行性与系统集成上是否闭环、缺口在哪。结论：建模与口径拍板已相当完整，但「参考旋律从哪首歌哪条轨提取 / 无独立人声分离产物 / 唱歌评分器/抽象/路由/异步化零代码 / 无歌唱基准脚本」四处是硬缺口——**有模型无算法、有口径无数据源**。

## 1. 问题清单
Q1 参考旋律从哪来（有无独立人声/分离产物；audio_url 指向什么）｜Q2 离线提取算法/粒度/monophonic｜Q3 音准怎么打分（逐句切窗 vs 整首 DTW；cent/量化）｜Q4 节奏怎么打分（onset/beat；end_offset 缺省）｜Q5 发音复用 ISE（唱音适不适合；16k mono）｜Q6 综合分/取整/缺失降权｜Q7 CI Fake 接口形状（SingScorer 子类还是新抽象）｜Q8 基准/校准脚本｜Q9 pyin RTF 与 yin 降级｜Q10 落库一致性（同事务；error）｜Q11 端点与异步化现状。

## 2. 逐问结论
- **Q1【未决，最高】**：`songs` 只有单条 `audio_url`（NOT NULL），**无** `vocal_url`/`accompaniment_url`/`reference_vocal_url` 字段；`song_pitch_refs` 只有 `lrc_id` 外键、**不含「来自哪条轨道」**。`audio_url` 是**本地路径字符串**（`ContentAdminApiTest.java:90` `/data/audio/twinkle.wav`），Python **不能下载**、只能按路径读共享卷。无 UVR/Demucs（全仓 grep 无）。**建议拍板**：给 songs 增 `vocal_ref_url`（参考人声轨）或约定 demo 歌曲为「旋律主导/清唱版」，否则 `song_pitch_refs` 无可靠数据源。另：`audio_dir` 有 dev 相对路径 / docker 容器路径 / 宿主路径**三义性**，Python 读文件须先归一化（无归一化代码）。
- **Q2【事实，部分未决】**：已拍板 librosa **`pyin`**（唱歌 65~800Hz、说话 75~300Hz、frame 2048/hop 512、清浊门限滤静音；**不引 crepe/TF**）；venv 已装 `librosa==1.0.0`（pyin/onset/beat/dtw 可用），无 crepe/demucs。产物 = `song_pitch_refs.pitch_ref={f0s,notes}`（逐句 1:1）。**未决**：`notes[]` 编码语义（MIDI vs note 名）；**monophonic 假设对 KTV 和声/背景人声不鲁棒**（docs 仅清浊门限滤静音，无伴奏干扰处理）。
- **Q3【事实，部分未决】**：音准=逐句基频 vs 参考旋律偏差(cent)映射（≤50→90+/≤100→70~90/≤200→50~65/>300→<40）；综合=0.5音准+0.2节奏+0.3发音。对齐=整体 BPM 倍率粗对齐 → Sakoe-Chiba(≤10%)+斜率约束子序列 DTW 精对齐；音高轮廓归一化。**未决**：逐句切窗 vs 整首 DTW 的确切数据流；cent 映射取绝对；若先按 `notes[]` 量化到半音（100 cent）天然对齐。
- **Q4【事实，部分未决】**：节奏=onset/beat 与 LRC 时间戳**相对** DTW 偏差映射（≤150ms→90+/≤300→75~90/≤600→55~75/>1000→<50）。参考点=lrc.offset_ms（NOT NULL）+ end_offset_ms（**可空**，算法按下一句 offset 推断）。**未决**：节奏 onset/beat 取**用户人声**还是**伴奏/参考轨**（参考系混淆→失真）；末句 end 推断规则（按 duration_s/BPM 拍数）。
- **Q5【事实，风险】**：发音=复用 ISE（docs/06 §9.4）。ISE 契约 `auf=audio/L16;rate=16000`、单句 `cmd=ssb`；`ISEClient.score` **直接把传入 audio_bytes base64 上送、未转码**（R-13）→ 唱歌必须先 16k mono（复用 `asr.py:64-66` ffmpeg）。逐句 reference=`lrc.line_text`。**风险**：唱音有音高/长音/颤音/连读吞音/节奏拉伸 → ISE「完整性/流利度」可能失真、词级错误大量出现，发音子项可能系统性偏低/失真。逐句调 ISE 放大免费额度。
- **Q6【事实，未决】**：综合=`0.5音准+0.2节奏+0.3发音`（docs/06:153）；`Numeric(5,2)`。**未决**：① 展示取整规则；② **分项缺失重分配未定义**（某句无音高→该句仅 0.2/0.5 归一重算综合，或整句剔除？）；③ 某一路整句失败时 `is_complete/expected_lines` 与「未评测」如何叠加。建议：某句无音高→该句不入综合平均，整首用「有效句均分」。
- **Q7【未决】**：现有抽象只有 ASR/TTS/Scorer(ISE)/LLM 四 ABC + `get_*_client` 工厂（base.py:46-150）；**无唱歌评分器/抽象/工厂/路由**；`librosa` 未在任何 app 代码 import。docs/08 预期文件 `app/audio/pitch.py`(Q35)/`sing.py`(Q36)/`scorer.py`(Q30) 均不存在。**建议**：新增 `SingScorer`（新 ABC，`score_song(audio, song_id/lrc_id, ...)->SingScoreResult`）或拆 `PitchExtractor`(pyin)+`SingingScorer`(DTW)+复用 `ScorerClient`(发音)。`FakeSingScorer` 应返回与 `SingAttempt` 字段一致（含 `no_ref/synced/skipped`），接口与模型对齐。
- **Q8【事实，无】**：`scripts/poc/` 有 `whisper_rtf.py`(POC-3 ASR RTF) 等，**无任何唱歌/音准/节奏/pyin 基准脚本**。docs/06 §9.4:156「5 首×5 句、2 人 0-100、r≥0.7 验证报告」**无对应脚本/报告**——这是评分「可信」的唯一硬证据，缺了答辩会被质疑。
- **Q9【事实】**：docs/09 §3.2-3：180s 音频 pyin RTF>1，同步 1~3 分钟 → 必须异步化；docs/16:498：pyin transient ≈100~300MB。docs 建议**或对比 yin（快一数量级）作为降级**（librosa.yin 可用）。**未决**：pyin 在 demo 歌曲上的实际 RTF 实测值（ASR 有 POC-3，唱歌无对等实验）。
- **Q10【事实】**：docs/10 §4.3：明细与总分同一事务写入；单条流水线失败写 `error` 快照后不写分数行（分数 NULL）。**`sing_attempts` 无 `error` 列**（对比 attempts 有），失败靠 `lines[].skipped/no_ref` + 分数字段 NULL 表达。
- **Q11【事实，无】**：`app/api/routes` 无任何唱歌评分端点；defense.py:72 用裸 `asyncio.create_task`（无 Redis 任务状态轮询机制、无 poll 端点）。唱歌评分异步化 **零实现**，违反 M3 硬约束「不许退化为同步等待」。

## 4. 结论
口径拍板过半、实现为零。已闭环：公式/映射/pyin 参数/DTW/发音复用/schema 都已定稿落库，`SingAttempt(lines[]+alignment)`/`sessions.kind=sing` 已建模。未落地：算法与集成全空。主要风险排序：① 数据源未定（最致命）；② 伴奏/和声对 monophonic 的破坏（且无基准佐证）；③ **用户逐帧 F0 无落库**（D3 画不出用户曲线，锁死评分器输出契约）；④ 异步化零实现；⑤ 无 Fake/无接口形状 + `ref_seq/no_ref` 未落地；⑥ 缺降权口径与基准。**一句话**：设计与口径足够支撑落地，但「参考旋律数据源」这一项可卡死整条链路；M3 启动前先把 Q1（输入轨）、Q12（逐帧 F0）、Q7（接口/Fake）、Q11（异步化）、Q8（基准脚本）定死。

## 5. A 完整报告补充：synced/skipped / alignment 字段语义 & Q12 决策
- **`skipped`**=该句无有效用户人声（静音/没唱/超范围）→ 不算、不进入完成 count；**`synced`**=该句用户音频是否成功与参考完成时间对齐（有人声但没对上=跑调/节奏极乱/参考缺失）→ `synced=false` 该句分数标 NULL/近似并前端提示「未对齐」；二者正交。
- **`alignment`**：`bpm_ratio`=用户平均 BPM/参考 BPM（粗对齐）；`offset_ms`=去倍率后全局时间偏置（子序列 DTW 中位漂移）；`method`=算法标识（如 `sakoe-chiba-subseq-dtw-v1`）；`version`=随评分算法升级递增（与 `song_pitch_refs.version` 一致，保证可解释）。`bpm_ratio/offset_ms` 整首一个；逐句窗口差异由逐句 `start_ms/end_ms` 承载。
- **Q12（P0 决策）用户逐帧 F0**：`lines` 只存逐句聚合分、不含用户逐帧 F0；只有参考旋律 F0 在 `song_pitch_refs`。若要画「用户音高曲线（参考线+用户线重叠，x=offset_ms/y=Hz·cent）」：**方案 a（推荐，M3 DoD 含逐帧可视化时）**评分器把该句用户逐帧 F0 写回 `lines[i].f0`（hop 512，与参考 f0s 同粒度）或整首 `user_f0` jsonb——唯一可复现的持久数据源（原始录音 24h 清理后 F0 是唯一痕迹），直接支撑 D3 重叠绘；**方案 b（仅作唱时即时反馈）**浏览器端 `pitchy`/自研 autocorrelation 实时算，不作评分依据、不持久化。`synced=true` 是「该句 f0 有效可存」的门禁。
