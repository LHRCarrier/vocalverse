## 2. 逐问 Q/A

### Q1 唱歌前端交互形态

【事实】ADR 口径：唱歌完成率 = **整首逐句评分结束**（`docs/06-技术框架决策.md:131`）；评分走 **pyin**（对整段音频 65~800Hz，frame 2048/hop 512）与 **整体 BPM 倍率粗对齐 + Sakoe-Chiba 子序列 DTW 精对齐**（`docs/06:154-155`）。SingAttempt 是**一条记录存整首**：`lines` jsonb（逐句 seq/start_ms/end_ms/pitch_score/rhythm_score/pron_score/synced/skipped）+ `alignment` jsonb（bpm_ratio/offset_ms/method/version）+ `is_complete`/`expected_lines`（`services/python/app/models/practice.py:190-230`）。后端为**异步任务**（Redis 任务状态轮询，M3 必项，`docs/06:121`）。

【推断】→ **推荐整首跟唱（一次录完）为主形态**。理由：① 后端 pyin/DTW 是对**整段**做全局对齐，逐句录会丧失句间 BPM 连续性与 DTW 上下文；② 完成率定义 = 整首逐句评分结束，天然对应"一次上传 → 一次轮询 → 出全量 lines"的一发流程；③ 前端状态机最简单：`idle → recording(≤180s 自动停) → uploading → scoring(轮询) → report`，与 `DefenseView` 的 `setInterval` 轮询模式同构（`apps/web/src/views/DefenseView.vue:86-103`）；④ nightingale（`github.com/rzru/nightingale`）即"唱时监听 + 结束出整首分"，被验证过。
**风险与权衡**：一次 180s 无暂停无逐句重唱，录制终止（后台切换/误触）需整段重录；KTV 体验上更接近"整首伴奏"。**逐句录制**作为**延伸项**（每个 lrc 行一次录音+一次异步评分）适合"即时纠错/逐句重唱"，但状态机退化为 `PracticeView` 式**回合制**，且需新增"逐句评分"端点——M3 建议**做整首、不做逐句**，并把逐句版本列为答辩扩展。
**是否未决**：否（形态已推荐，范围（整首 vs 逐句）需组长拍板，见 §3 B1）。

### Q2 录音

【事实】现有 `VoiceRecorder`（`apps/web/src/audio/recorder.ts`）：
- `MAX_RECORD_MS = 60_000`、`MIN_RECORD_MS = 800`、`MAX_BYTES = 20MB`（`recorder.ts:7-11`）。
- `start(maxMs)` 已参数化；`recorder.ts:113` 自动停止计时器 `setTimeout(() => this.stop(), maxMs)`；`_mime` 自动回退 `webm;opus → webm → mp4`（`recorder.ts:43-49`）。
- **停止键/误触已修复**：`stop()` 幂等守 `MediaRecorder.state`（`recorder.ts:125-136`），`cancel()` 作废权限窗口内的 start（`recorder.ts:142-155`）；`onStop` 对 `durationMs < MIN_RECORD_MS` 由调用方丢弃不上传（`PracticeView.vue:162-170`、`DefenseView.vue:52-59`）。
- 后端 `min_upload_bytes=1024`（`app/core/config.py:57`）+ `validate_audio_bytes` 先行校验抛 **40002**（`app/audio/upload.py:17-27`），正是为挡住"~0ms 的 webm 容器（几百字节）"。**因此 40002 的下界问题在 dialog/defense 已由"前端 min 校验 + 后端 1024 下界"双保险覆盖**。

【事实】**转码在后端**：faster-whisper 用 `ffmpeg -y -i src -ar 16000 -ac 1 -f wav` 把 webm/opus 转 16k mono wav（`app/audio/asr.py:63-69`）；讯飞 ISE 同样以 `audio/L16;rate=16000` 消费（`app/audio/ise.py:43`）。ffmpeg 是服务端唯一硬依赖（`asr.py:5`）。
【推断】**唱歌也应**：前端**不转码**，直接上传原始 webm/opus blob（`form.append('audio', blob, 'sing.webm')`），由后端统一 ffmpeg→16k mono wav 后喂 pyin。理由：① 复用已有后端链路，避免前端引入 `AudioContext.decodeAudioData`+离线 PCM 编码的重管线（移动端耗性能、易内存峰值）；② 后端已装 ffmpeg（生产镜像），改造成本≈0；③ 上传体积无压力（见下）。**若唱歌评分器需要 16k mono wav**，在 sing 服务内复用 `ffmpeg` 即可。

【事实】**180s 体积估算**：webm/opus 按 MediaRecorder 默认码率（约 110~130 kbps 音频）约 **180s × 128kbps ÷ 8 ≈ 2.9 MB**；即便设 `audioBitsPerSecond: 32_000` 也仅 **≈0.72 MB**；**均远低于 20MB 上限**（且低于 `MIN_RECORD_MS` 触发误触的 1KB 下界 3 个数量级）。转换后 16k/16bit/mono wav = `16000×2×180 ≈ 5.76 MB`，仍 <20MB。
【事实】唱歌应传 `maxMs = 180_000`（`VoiceRecorder.start(180_000)`），复用同一 `VoiceRecorder`，**无需新建 recorder**，只需在录音区把 auto-stop 文案从"≤15s"改成"≤180s"，并给录音中间态一个"放弃重新唱"（对应 `cancel()`）。
**是否未决**：否（复用 recorder + 后端转码已定；180s 文案/长录音 UI 属实现细节）。

### Q3 实时音高/波形

【事实】可视化栈拍板：**P5 仅品牌动效（录音波纹已实现 `useP5Wave`）**；**D3 ^7 仅唱歌"逐句音准/对齐图"（M3）**；**ECharts ^6 仅 M3 报表**（`docs/13-前端设计系统.md:57-64`；`docs/06:71`）。仓库已引入 d3/echarts/p5，但**无 wavesurfer/pitchy/creek**（package.json）。
【事实】**用户逐帧 F0 未落库**：`SingAttempt.lines` 只存 `{seq,start_ms,end_ms,pitch_score,rhythm_score,pron_score,synced,skipped}`（`models/practice.py:190-230`），**不含用户 sung 的逐帧 F0 序列**；只有**参考**旋律 F0 在 `song_pitch_refs.pitch_ref = {f0s,notes}`（`models/content.py:235`）。→ **"唱完展示用户音高曲线"当前无数据源，除非：a) 唱歌评分器把每帧 F0 一并写回 `lines`（改 schema/加 jsonb 字段），或 b) 前端唱时实时检测、本地缓存。**（见 §3 B2）
【推断】**实时可视化（唱时**）推荐**做，但要降级为"轻量、可失败"**：
- **实时 F0**：浏览器端用 **pitchy**（autocorrelation 类，维护活跃、~几 KB、MIT）或自研 ~80 行 autocorrelation（`sen-ltd/pitch-detector`，sub-cent 精度、FFT 在低音失效处更稳）。唱歌 65~800Hz 用 autocorrelation 可行；**噪声鲁棒性**：清浊门限 + 帧中值平滑 + 目标音高约束（只报"预期旋律附近 ±300 cent"），能压住八度错和分谐波；**延迟**：hop 512@16k ≈ 32ms 帧距，加一帧缓冲 ≈ 50-100ms 可见延迟，可接受。**注意**：pitchy/creek 默认针对人声/低频，唱歌高频段（>600Hz）与强颤音(vibrato)下八度/半音错会变多，需调 clarity 阈值。
- **波形**：**不使用 wavesurfer.js**（那是播放/交互波形，且引入体积）；用 **Web Audio `AnalyserNode.getByteTimeDomainData`** 驱动一段自绘 canvas（或复用 p5 波纹），成本最低。
- **降级**：实时块全部 `try/catch`，失败静默回落为"只显示录音波纹 + 录音时长"，**评分正确性不依赖实时检测**（评分服务端 pyin，才权威）。
【推断】**离线"唱完展示"曲线**：因为用户 F0 没落库（见【事实】），前端只能画 **参考旋律曲线（来自 song_pitch_refs.f0s）+ 逐句分数条/热力**；**要画用户音高重叠**必须先把用户 F0 写回。**推荐**：M3 先做"参考旋律线 + 逐句分数（条/热力）+ 高亮问题句"，**把用户 F0 曲线作为加分项**，需在 sing 服务写 `lines[].f0`（或独立 `user_f0` jsonb）。实时检测仅在"唱时给用户即时反馈"作用，**不做评分依据**。
**是否未决**：部分（见 §3 B2：用户 F0 是否写回，需拍板）。

### Q4 评分展示与可视化

【事实】ADR 已拍板：**D3 ^7 专用于唱歌"逐句音准/对齐图"**（`docs/13:63`、`docs/06:71` "d3 ^7.9（仅唱歌细图）"）。ECharts 只做 M3 报表（趋势/雷达/四指标卡）。现有 `useECharts` 只注册 `Line/Pie/Bar + Grid/Tooltip/Legend/Title + Canvas`（`apps/web/src/composables/useECharts.ts:22-40`），**未注册 Radar/DataZoom/Graphic/MarkLine**。
【推断】**结论：音准/对齐图（多序列时间轴对齐）选 D3 自绘 SVG 划算**，理由：
- **多序列自定义时间轴对齐**（参考旋律线 + 用户音高线 + lrc 句边界标记，x=时间(由 offset_ms 派生)，y=音高(Hz 或 cent)）在 ECharts 需要 `xAxis: type 'value'` + 自定义 `markLine`/`graphic` 才能把 lrc 边界与两条曲线精确对齐，且 D3 里一个 `scale` + `line` generator 十行内搞定；ECharts 的 dataZoom 对该"把跨 180s 的时间轴+边界对齐"帮助有限，且需要额外注册 dataZoom/axisPointer。
- D3 无渲染层依赖、可控像素级，正好做"KTV/Kalaoke 音准线"这种**一图多轴**（用户曲线 vs 参考曲线 vs 音高网格 vs 句区间背景）。
- 对比表：ECharts（上手快、交互内置如 tooltip/legend，但"自定义多序列时间轴+区间标记"要绕自定义 series/组件）；D3（代码多、无内置交互，但**该类图零绑定成本**）；自绘 canvas/SVG（最轻，但坐标/缩放/交互全手写）。**结论：这张图 → D3 SVG；分数卡/总览 → naive-ui + 简单百分比条（复用 ReportView/PracticeView 的评分卡样式）。**
【事实】"评分"展示：总体 = `0.5·音准 + 0.2·节奏 + 0.3·发音`（`docs/06:153`）；逐句卡含音准/节奏/发音三分（SingAttempt.lines）。可复用 `ReportView.vue`/`PracticeView.vue` 的三维 NProgress 评分卡布局（`PracticeView.vue:316-344`），但**改四项**（发音/流利度/语法 → 音准/节奏/发音）。**结论：评分卡复用样式，可视化（音准/对齐图）新造 D3 组件。**
**是否未决**：否（D3 已拍板；数据源缺用户 F0 见 §3 B2）。

### Q5 任务状态轮询 vs SSE

【事实】**唱歌评分是异步任务**（`docs/06:121` "唱歌/长音频评分走 Redis 任务状态轮询异步化（M3 必项，不许退化为同步等待）"）。**后端尚无该端点/服务**——`main.py` 无 sing 路由，`python-openapi.json` 无 sing 端点（【事实】见 §0）。
【推断】**推荐轮询（非 SSE）**，且轮询形态=「上传即返回 session 状态 → 前端轮询状态直到终态」。理由：① ADR 明确"Redis 任务状态轮询"；② 唱歌是**后置重型计算**（pyin+DTW+发音），无逐字流式需求（与对话 SSE 的 turn 级流不同）；③ 前端**已有轮询范式**：`DefenseView.pollStatus` 用 `setInterval(fetch, 1500)`（`apps/web/src/views/DefenseView.vue:86-103`），可直接抽出复用；④ SSE 现有实现 `openSseFetch` **仅支持 POST multipart**（`apps/web/src/audio/sse.ts:44-87`），唱歌若要 SSE 得再造一条——收益低。
**轮询参数（推荐）**：间隔 **1.5s（前 30 次）→ 退避到 3s**，总超时 **60~120s**；`setTimeout`+`clearTimeout` 由 `useTurnTimers`/`onBeforeUnmount` 统一清理（防连接泄漏）；**终态即停**：`status in (complete/failed)` 停轮询；`retry`（指数退避，最多 3 次）仅用于 5xx/网络错误，**不重放录音**。
【事实】**错误码消费**（`docs/api/error-codes.md`）：
- **40002**（音频空/过短）→ 提示重录，**不消耗回合/限流**（`error-codes.md:9`）。前端 `MIN_RECORD_MS` 已前置拦截。
- **40401**（会话/报告/档案不存在）→ 提示 + 路由回退（`error-codes.md:12`）；对 `/sing/sessions/{id}` 被拒即该 id 过期/不存在。
- **40901/40902/40903**（锁/状态错/ stale）→ 前端"刷新状态/采纳服务端权威轮次"（`error-codes.md:14-16`）。唱歌无 turn 概念，主要防**重复提交/并发**。
- **41001**（音频 24h 过期）→ 提示重录（`error-codes.md:17`）；对**老 session 回放**即触发。
- **41301**（>20MB）→ 前端压缩或分段（`error-codes.md:18`）；唱歌 ≤3MB 不会触发，但**保底处理**。
- 前端统一在 `request()`/`ApiError`（`apps/web/src/api/client.ts:63-71`）捕获 `code`，已在 `PracticeView`/`DefenseView` 把 `(e as Error).message` 抛到 `errorMsg`。
【事实】**pitch_ref_status 状态**：`Song.pitch_ref_status ∈ missing/building/ready/invalid`（`models/content.py:164-166`、`models/base.py:137-141`）。**前端在进入跟唱前必须读歌曲状态**：`ready` 可唱；`building`→提示"参考旋律提取中，稍后再试"；`missing/invalid`→"缺参考旋律/不可用"，禁用进入并引导管理员重提取。
**是否未决**：是（轮询端点与整套 sing 后端未实现，前端实现的轮询 UI 依赖其契约；状态轮询字段名待契约冻结，见 §3 B1/B3）。

### Q6 移动端/PWA 硬约束

### Q7 路由与状态

【事实】路由（`apps/web/src/router/index.ts`）：`/sing` 现为 `PlaceholderView`（`router/index.ts:53-58`，M3）；计划新增 `/sing`（歌曲列表/入口）、`/sing/sessions/:id`（跟唱+轮询）、`/sing/sessions/:id/report`（逐句报告）三条。**现状无 Pinia practice 业务 store**：只有一个 `stores/auth.ts`；`PracticeView`/`DefenseView` 全部用**组件内 ref 状态**（`PracticeView.vue:30-48`、`DefenseView.vue:35-46`），无 `practiceStore`。
【推断】**推荐建 `singSession` store**（而非硬塞组件内），理由：① sing 流程跨**三个路由**（入口→跟唱→报告），状态需在路由跳转间存活，组件内 ref 会丢；② 轮询是**跨页面长生命周期**任务，放 store 便于组件卸载后仍能继续并在路由跳转后恢复；③ **与 `DefenseView` 的"生成中轮询"同构**，可把轮询逻辑抽成共享 composable（`usePolling`）。**复用度**：与现有 `practiceStore`（不存在）复用度低，但因没有 store 基础，可**新立**；把 `VoiceRecorder`、`openSseFetch`、`request`、`ApiError`、`micErrorMessage` 全部复用。
【事实】**管理端歌曲列表**：`AdminLayout` 下 `songs` 路由现为 `PlaceholderView`（`router/index.ts:95-99`）；Java 管理端已有歌曲 CRUD + LRC 整首重写（`docs/21:83`，`/manage/api/v1/admin/songs*`），**LRC 重写会置 `pitch_ref_status→missing`** 并触发离线重提取（`models/content.py:162-166,191`、`docs/21:83`）。
【推断】**管理端前端应加**：每首歌一个 **"参考旋律状态"徽章**（missing/building/ready/invalid）+ **"重提取"按钮**（`POST /manage/.../songs/{id}/pitch-ref/build` 之类，需 Java/Python 提供）——因为用户端依赖 `pitch_ref_status=ready` 才能唱，管理员需要能触发/查看重提取。**但 Java 管理端歌曲 API 目前无"重提取/状态"端点**（`docs/21:83` 只有 CRUD+LRC），是缺口 B3。
**是否未决**：部分（store/路由推荐明确；管理端"重提取"端点需后端补）。

### Q9 契约生成链路

【事实】前端类型由 `pnpm gen:api` 从 `python-openapi.json` / `java-openapi.json` 生成（`apps/web/package.json:18`；`apps/web/src/api/specs/*.json`）。**当前两个快照都无 sing 端点**（【事实】见 §0）。**SSE 事件类型是手写共享类型，不进 gen:api**（`docs/14:3`、`sse-types.ts:1`，因为 SSE 端点在 OpenAPI 无响应 schema，契约管线盲区，见 `docs/16 A6`）。
【推断】**对唱歌的影响**：① 用户态 sing 端点（创建 session/上传/状态轮询/report）必须在 Python 写路由 + OpenAPI 生成后，前端**跑 `gen:api` 刷新 `python-api.d.ts`**，typecheck 立即暴露断点（`client.ts:8-11` 已记录该纪律）；② 唱歌若走**轮询**则走 JSON envelope（走 gen:api，OK）；若走 SSE 则需**手写 sing 事件类型**并双端同步（`sse-types.ts` 注明"改动须双端同步"）。**推荐唱歌走轮询**（envelope 走契约生成，减少手写同步）。
**是否未决**：部分（取决于是否走 SSE；推荐走轮询）。

### Q10 音频回放鉴权（R-5）与媒体类型

【事实】`GET /api/v1/audio/{name}`：`name` 必须匹配 `^[0-9a-f]{32}\.mp3$`（`practice.py:39`）；`user_id = Depends(get_current_user_id)` 强制 **Bearer 鉴权**（`practice.py:234`）；校验归属（`Attempt`/`ScenarioMessage`）否则 40301（`practice.py:248-259`）；24h 惰性过期 → 41001（`practice.py:240-243`）；返回 `StreamingResponse(media_type="audio/mpeg")`（`practice.py:268-270`）。**R-5 结论**：`<audio src>`/`Audio(url)` 无法带 Bearer 头，与鉴权物理冲突。
【事实】**媒体类型隐患**：`save_audio_bytes` 把**用户录音（webm/opus）**写成 `{sha1[:32]}.mp3`（`orchestrator.py:63-74`），与 `.mp3`/`audio/mpeg` 命名不符；虽然浏览器按魔数嗅探容器通常能解码，但**内容与声明/扩展名不一致**是脆弱的（不同 Safari/WebView 对 content-type 嗅探行为不一），且**不适用于"参考旋律试听"**（参考歌曲音频是真 mp3，无问题；用户录音回放才有此问题）。
【推断】**绕行方案（推荐）**：唱歌逐句回放（用户录音/参考旋律）统一走 **`fetch(url, {headers: {Authorization}})` → `blob` → `URL.createObjectURL`**（新增一个 `fetchAudio` 到 `api/sing.ts`，复用 `authHeaders`），彻底绕开 `<audio>` 带不了 header 的问题；返回 `URL` 给 `<audio>`/`Audio` 播放。**此方案同样修复当前 `.mp3`/`audio/mpeg` 与 webm 内容不一致**（因为 fetch 取的是完整字节，不受媒体类型声明影响）。**若走"签名 URL"（后端临时签发带 token 的 URL）也可行**，但需后端改动；**推荐 fetch+Blob**（只动前端，后端零改动，且对 R-5 一并解决）。
**是否未决**：否（推荐 fetch+Blob；后端签名 URL 作为备选）。

### Q11 会话完成判定

【事实】`SingAttempt.is_complete`：`is_complete=true 且 scored 且 not skipped 的句数 == expected_lines`（`models/practice.py:219-222` 注释）。`expected_lines` = 评分时 lrc 行数快照；`lines` jsonb 每行带 `synced`/`skipped`。
【推断】**前端判定「整首逐句评分结束」**：调 `GET /sing/sessions/{id}`（或 report 接口）拿到 `is_complete` + `lines`。**终态判定**：① `status` 变 `complete`（服务端任务落库完成）且 `is_complete=true` → 跳 `/sing/sessions/{id}/report`；② 若 `lines.length` 有 `skipped` 行且 `is_complete=false`，前端提示"部分句未对齐（skipped=N），评分为近似值"并给重唱入口；③ 若 `pitch_ref_status` 在评分中变为 `invalid`（如 LRC 重写触发），任务应 fail 并提示"参考旋律已变更，请重试"。
**是否未决**：部分（依赖后端把 `is_complete`/`lines` 通过轮询/report 返回的字段名，见 §3 B3 契约）。

## 4. 结论

**四句话结论：**

1. **形态 = 整首跟唱（一次录完 180s → 异步评分 → 出整首逐句分）**。与后端 pyin+DTW 全局对齐、完成率「整首逐句评分结束」、Redis 异步任务三者自洽；逐句录制留作答辩扩展。状态机 `idle→recording(≤180s)→uploading→scoring(轮询)→report`，复用 `DefenseView` 的轮询范式。

2. **录音直接复用 `VoiceRecorder`（`start(180_000)`）**；`webm/opus→16k mono wav` **由后端 ffmpeg 统一转换**（现成链路），前端**不转码**、直接上传原始 blob（180s ≈ 0.7~3MB，远低于 20MB，无需前端压缩）。40002 下界在"前端 800ms 校验 + 后端 1024B 下界"已双保险。

3. **可视化**：评分卡复用现有三维 NProgress（改四项）；**逐句音准/对齐图用 D3 SVG**（ADR 已拍板，多序列时间轴对齐场景 D3 零绑定成本、ECharts 反而要绕自定义组件）。**用户音高曲线能否画取决于 B2（用户 F0 是否写回）**；**实时 F0 用 pitchy/自研 autocorrelation（仅反馈、不作评分依据），波形用 Web Audio AnalyserNode**。

4. **状态/轮询**：建议新建 `singSession` Pinia store（跨"入口→跟唱→报告"三路由存活）+ 共享轮询 composable；走**轮询**（非 SSE）以贴合"Redis 任务轮询"ADR 与现有前端范式；错误码沿用 `error-codes.md` 在 `ApiError` 统一处理。**音频回放**用 `fetch+Blob` 绕开 R-5 的 `<audio>` 鉴权冲突，同时修复 `.mp3`/`audio/mpeg` 与 webm 内容不一致。

**三条最优先待办**：① 冻结唱歌后端契约（B1/B3，否则前端无法开工）；② 拍板用户 F0 是否写回（B2，决定可视化深度与评分器输出）；③ 补 PWA 基建与 `pitch_ref_status` 状态门禁（B5/B4，移动端与可用性验收）。
