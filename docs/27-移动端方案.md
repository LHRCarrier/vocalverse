## 0. 目标与约束

| 项 | 内容 |
|---|---|
| 目标 | 把 VocalVerse 做成可上架的**手机 App**（真实产品化，非仅答辩演示） |
| 核心理由 | 口语/跟唱场景天然便携；录音、蓝牙耳麦、推送等移动侧价值大 |
| 节奏 | **1 个月**（4 周）内出可发布版本 |
| 首发 | **Android 先行上架，iOS 跟后（TestFlight 内测先行）** |
| 团队 | 3 人：Vue3/TS 前端、FastAPI Python、Spring Boot Java；**无移动端原生经验** |
| 现状 | M2 MVP 已落地（对话闭环）；M3（唱歌/推荐/报表）进行中；后端两服务 + nginx 同源反代 |

## 1. 结论摘要（TL;DR 决策清单）

| # | 决策 | 一句话理由 |
|---|---|---|
| D1 | 技术路线 = **Capacitor 8 套壳**（WebView 加载现有 Vue 应用），**远程 URL 型首发** | 复用 ≈100% 前端代码；零后端改动；1 个月窗口内唯一可行且能上架的路线 |
| D2 | 移动端范围 = **MVP 只做一个功能：口语对话闭环**（登录→录音→评分→报告） | 视频调研铁律「MVP 只做一个功能」；跟唱/报表/社区全部后置 |
| D3 | 先验证再投入：**W0 用手机端设计草图发小红书/B站收集反馈** | 视频调研法篇：需求未验证前不写代码 |
| D4 | 商业模式 = **Freemium**：免费限量 + 月/年/买断三档（12/38/68/128 带锚定） | 单人/小团队被动收入模型；Android 微信支付，iOS 后续 IAP |
| D5 | 不做原生重写（Flutter/RN/uni-app/原生双端） | 复用率 0 + 团队无相关经验 + 1 个月不可能；「用最熟的工具」 |
| D6 | 仅当 WebView 能力不达标时，才写**原生插件定点突破**（首发候选点：推送；次选：iOS 录音/蓝牙） | 避免框架级重写，插件级投入 |

## 2. 现状盘点（做方案的事实基座）

| 项 | 现状 | 对手机端的影响 |
|---|---|---|
| 前端 | Vue3.5 + TS + Vite6 + naive-ui + pinia（`apps/web`），录音/SSE/埋点已齐 | **可直接进壳**，无需移动端框架重写 |
| 后端 API | 同源反代 `apps/web/nginx.conf`（`/api/v1/`→Python、`/manage/`→Java）；**Python 无 CORSMiddleware** | 壳加载**线上同源域名** → 跨域问题不存在，后端零改动 |
| 鉴权 | `stores/auth.ts`：access/refresh token 存 **localStorage**；`POST /auth/refresh` body JSON | WebView 内 localStorage 按 origin 持久化，**无需 cookie/SameSite 适配** |
| SSE 热路径 | `audio/sse.ts` fetch 流式消费 | 标准 Web API，WebView 内可用 |
| 音频回放（R-5） | `fetch(url,{Authorization}) → blob → objectURL` | 同上，WebView 内可用 |
| PWA 基建 | **完全未建**（轴线E Q12/B5：无 manifest/SW） | 仍应补（低成本、Android 可安装、答辩加成），与壳并行 |
| 移动端硬约束 | 轴线E Q6 已审计 **8 条**（手势开麦/HTTPS/AudioContext/后台断录/自动播放等） | 真机实测表（§8）按此执行 |
| ADR 表述 | docs/06 §1「不做 App（PWA/响应式覆盖）§9.6「原生 App 列为扩展」 | 需按 §13 修订（本次方案即为修订依据） |

## 3. 技术路线对比与裁决

| 路线 | 复用率 | 1 个月内可上架？ | 关键风险 | 结论 |
|---|---|---|---|---|
| A. PWA 增强（`vite-plugin-pwa`） | 100% | 不可上架商店 | iOS 限制多、无推送/后台；无商店曝光 | 保留作**低成本加分项**（§2 已欠账 B5），不作主线 |
| B. **Capacitor 8 远程 URL 型**（壳加载线上域名） | ≈100% | ✅ Android | 纯套壳有审核风险（§11）；离线不可用 | **主线，首发** |
| C. Capacitor 8 本地打包型（Vue 构建产物入包） | ≈100% | ✅ | 需 CORS 或 CapacitorHttp；**SSE 在 CapacitorHttp 不流式**，仍需 WebView fetch + 后端 CORS；发布新包周期长 | 作为上线后的**优化项**（首屏秒开/弱网壳），不卡首发 |
| D. Flutter / RN / uni-app 重写 | 0 | ❌ | 团队零经验 + 页面全重做（docs/13 设计系统作废） | 否决（与视频「最熟工具」铁律一致） |
| E. 原生双端（Kotlin/Swift） | 0 | ❌ | 双代码库 + Mac/证书 + 无 iOS 经验 | 否决；仅「原生能力插件」层保留 |

**裁决：B 首发（D1）**。理由：① 后端同源反代架构让 WebView 加载域名即可，**全链路零改动**；② 产品是强在线应用（LLM/TTS/评分每轮都请求后端），本地打包壳的「离线」价值低；③ 1 个月窗口内 B 是唯一同时满足「复用 + 可上架 + 可回退」的路线；④ 后续从 B 切 C 只改 `server.url` 配置与发布通道，无架构重构。

> 审核风险备忘：Google Play / App Store 对「纯 WebView 套壳」有最低功能审查（4.2 条款）。首发即带**原生价值点**：① 原生推送（Firebase/极光）；② 崩溃上报（Sentry 类）；③ 后续原生登录/支付增值。若仍被拒，回退路径见 §11。

### 4.1 补充调研：ETOS LLM Studio（是否可作「现成架构改造」——结论：仅可借鉴思路，不可作为基础工程）

> 事实：原生 Swift/SwiftUI 工程（iOS + watchOS），单人学生项目，约 971 个 Swift 源文件 / 36 万行，GPL-3.0，[Eric-Terminal/ETOS-LLM-Studio](https://github.com/Eric-Terminal/ETOS-LLM-Studio)。定位 = **客户端重**的通用 LLM 聊天/Agent 客户端（多提供商、本地 GGUF/llama.cpp、MCP、Agent Skills、内嵌 Linux、本地 RAG、双端同步、系统 STT/TTS）。

**裁决：不采用为 VocalVerse 移动端基础工程**，理由：

| # | 冲突点 | 说明 |
|---|---|---|
| 1 | 仅 Apple 生态（iOS/watchOS） | 与本方案 **Android 首发** 直接冲突 |
| 2 | 36 万行 Swift，团队零 Swift 经验 | 违背「用最熟的工具」铁律（§4 视频调研）与 1 个月窗口 |
| 3 | 问题错配 | 它解决「通用 LLM 客户端」；VocalVerse 核心是**服务端语音管线**（ASR/评分/SSE 音频队列/跟唱），客户端是薄壳；且 docs/26 已明确不迁移工具/RAG 类能力 |
| 4 | GPL-3.0 传染性 | 拷贝代码/素材 → 整体衍生须 GPL-3.0，与课程公开仓库 + 商业会员红线冲突；**只读思路（clean-room），不拷代码** |

**可借鉴点（思路级，落到本项目具体模块）**：

| 借鉴点 | 本项目转化 |
|---|---|
| 多提供商抽象 + 模型动态管理 + 成本估算 | `LLMClient` 接口（docs/06 §6）演进：DeepSeek 主 + 备胎切换、按 token 计费（配合 §4 Freemium 定价） |
| 流式思考/工具时间线、单条回复重写 | SSE 字幕 + `score_delta` 迟到显示（docs/14 §3.2）的 UI 状态机设计参考 |
| 会话级并发请求 / 取消 / 后台完成通知 | M3 唱歌长任务轮询的移动端 UX 模式 |
| 系统 STT 流式回填（SFSpeechRecognizer） | iOS 端「快速转写预览」备选通道；**评分仍必须走服务端**（ISE 参考句评分，系统 STT 无参考分） |
| watch-first「每日脉冲」 | 远期概念储备（手表打卡提醒），不立项 |

### 4.2 补充调研：MobileGym（浏览器模拟手机 GUI Agent 平台——不可用，仅取一条理念）

> 事实：[Purewhiter/mobilegym](https://github.com/Purewhiter/mobilegym)（EMNLP 2026 论文工程，785★）。**不是安卓模拟器**：它是「手机 GUI Agent」的仿真训练/评测平台——React 实现的模拟安卓手机 + 28 个研究替身 App（微信/支付宝/B站/小红书等），全环境 JSON 可编程状态（单机 256 并行）、确定性程序化判分（亚毫秒、无 VLM 判卷）、每 App 一份声明式导航 FSM；Python+Playwright agent 运行时（AutoGLM-Phone-9B 等 9 模型跑分），Qwen3-VL-4B+GRPO 在线 RL 涨分 42.8、真机保留 95.1%。许可：**代码 Apache-2.0 / 数据 CC BY-NC 4.0（非商用）**，模拟内容涉第三方品牌（有独立免责声明）。

**裁决：不采用、不集成**。理由：① 它的 app 是 React 重写的替身（非 APK 运行时），装不进我们的 Capacitor/Vue 壳，模拟 VocalVerse = 重写一套假 UI，投入大产出低；② 不覆盖我们的验收痛点（录音/蓝牙/iOS 内核），§8 真机实测表仍不可省；③ 数据/内容非商用许可 + 第三方品牌替身，商用红线。

**可借鉴（一条）**：**「读结构化状态 + 确定性断言，不做像素/VLM 评判」**——其判分器直接读 JSON 状态（作者实测 VLM 判卷误判率 10.2%）。本项目同构理念已在仓库落地（契约快照零 diff、alembic check、CI 探针）；新增落地点 = **手机端/Web 端 E2E 冒烟采用结构化状态断言**（URL/响应/DOM 数据字段），不引入截图-VLM 判卷。

### 4.3 开源架构调研汇总（三路并行 × 22 候选 · 许可全部核实）

> 方法：三路并行调研（Capacitor 壳生态 / AI 对话客户端 / 语言学习+音频库），候选逐个用 GitHub API/raw 核实 `stars · 最近更新 · LICENSE 原文 · 技术栈`；等级定义 A=直接复用、B=架构借鉴（需翻译/改造）、C=仅启发。

**最重要的 3 个发现**

1. **唯一 A 级「同栈代码级借鉴」= chatgpt-web**（Vue3+TS+Pinia，MIT，2024 年停更）：Pinia chat store / `useChat` SSE hook / 消息流式增量渲染，可直接翻译进我们工程；但它是单供应商、无队列，多供应商部分需配 LibreChat 补。
2. **LibreChat（MIT）是流式与多供应商的最佳架构参照**：SSE 协议层（`queuedTurns` 队列化回合，天然解决并发乱序）+ 供应商目录化（`Endpoints/{provider}/{build,initialize,title}`）+ 会话/消息模型；React 栈，需译成 Vue3+Pinia。
3. **「音频为时间轴权威」在全部候选中无先例**——此专项仍为自研点（docs/06 §8 不变）；但武器库已备齐：wavesurfer.js（波形回放）、sherpa-onnx（离线 ASR 降级）、Capacitor `audio-recorder/audio-session`（iOS 录音+音频会话）、`purchases`（IAP）。

**对方案的实际影响**

1. **W1**：壳工程 + CI 不再从零设计——照 capawesome 的 CI job/镜像模式落地；§6.1 依赖清单以本表为准；
2. **W2**：iOS 蓝牙麦/后台专项的**插件清单已备齐**（`audio-recorder` + `audio-session` + `bluetooth-low-energy`），真机实测不过即按 §11 决策立项（不再是「未知可行性」，而已知有解、待实测）；
3. **P0 对话页**：流式状态机设计参照 chatgpt-web（A，同栈）+ LibreChat queuedTurns（B），全部翻译为 Vue3+Pinia；
4. **M3 唱歌**：wavesurfer.js + pitchy 锁定候选（全程零 GPL/LGPL 依赖）；离线 ASR 降级通道登记 P2；
5. 新增依赖（前端 npm 包 / Capacitor 插件 / 镜像）按仓库纪律统一登记进 docs/06 §3 版本表（§13 修订申请已涵盖）。

## 5. MVP 功能范围（D2 · 一刀切）

❌ 跟唱（M3 唱歌流程后端未冻结契约，BSSE 轮询未实现——**等 M3 后端 + Web 版验收后再评估**）

### 每周功能评审三问（照抄进每周例会）

1. 这个功能是**验证产品需求的前提**吗？不是 → 砍/延后。
2. 这技术我熟吗？**一小时内**能搞定吗？不是 → 找替代方案（不现学）。
3. 先做它会不会**影响听到用户声音**？会 → 先做核心闭环。

## 6. 技术方案与集成要点

### 6.1 目录与依赖

```
vocalverse/
├── apps/mobile/          # 新增：Capacitor 壳工程（Android 首发）
│   ├── capacitor.config.json   # server.url = 生产域名；本地打真机包=false
│   ├── android/                # @capacitor/android 生成工程
│   └── package.json
├── apps/web/             # 不变：壳加载的就是它的线上构建产物
```

- 依赖（登记进 docs/06 §3 版本表）：`@capacitor/core|cli|android` **8.x**（2026 当前主线，以 lockfile 为准）、`@capacitor/push-notifications`、可选 `@capacitor/app`/`@capacitor/status-bar`。
- **不建独立构建链**：壳不重跑 `apps/web` 构建（远程 URL 型加载线上产物）；`apps/web` 的 lint/typecheck/build 门禁照旧。

### 6.2 为什么认证/跨域零改动（重申）

- 壳 WebView 加载 `https://<生产域名>` → 与 nginx 同源 → 无 CORS、无 cookie、无 Origin 问题；
- localStorage（`vv_token`/`vv_refresh`）在 WebView 按 origin **持久化**（WKWebView/Android WebView 默认持久，配 `server.cleartext=false` 线上强制 HTTPS）；
- SSE、fetch+Blob 音频回放均为 WebView 内 fetch，同源直通；
- **风险点**：Android 上若用户清理「浏览器缓存」或系统自动回收 WebView 数据 → 掉登录，需提供「重新登录」兜底（P1 项）。

### 6.3 权限清单（AndroidManifest / iOS Info.plist）

| 权限 | 用途 | 备注 |
|---|---|---|
| RECORD_AUDIO | 录音/口语练习 | 壳启动弹窗，配「为什么需要」说明页 |
| INTERNET（Android 默认） | - | - |
| POST_NOTIFICATIONS（Android 13+） | 推送（P1） | 可后置 |
| 麦克风使用说明（iOS） | 同上 | iOS 阶段配 `NSMicrophoneUsageDescription` |

### 6.4 与 M3 唱歌的前后端边界

- 唱歌移动端**不在本方案范围**（§5）；若 W2 后 M3 契约冻结且 Web 版验收，另行追加评估（沿用轴线E 的轮询/`pitch_ref_status` 门禁与 fetch+Blob 播放方案）。
- 本方案不新增任何后端契约 → **OpenAPI 双快照零 diff**，pytest/Java CI 不受影响。
