## 0. 一页摘要

企业级社区对「帖子 + 图片 + 视频」的统一处理骨架：

1. **一张 Media 表承载全部媒体**（图片/视频/文件），带状态机 `UPLOADED → TRANSCODING → READY / FAILED`；多规格产物存 `variants` JSON；封面、宽高、时长、大小、mime、排序一个不少；
2. **上传两条链路**：图片 = 服务端收 multipart → 同一文件处理出多规格（original/thumb/list/detail）→ 全部写对象存储；视频 = **客户端分片**（init → chunk → merge）→ **异步转码**（本地直出模拟 / 云转码 + 回调验签）；「上传 ≠ 发布」——媒体可见性由绑定场景（帖子/会话）决定；
3. **发帖 = 内容行 + 批量绑定媒体**（mediaIds 归属校验 + 类型白名单）→ **先审后发**（auditStatus 状态机 PENDING/APPROVED/REJECTED）→ 可选定时发布（延迟队列 + SCHEDULED 状态）；
4. **读取 = 游标分页 + 多态视图**（列表封面卡 / 详情多图与播放器）+ **冗余计数字段** + **唯一约束防并发重复互动**；
5. **周边**：软删（deletedAt）+ 用户回收站/管理员强删分离；互动通知（队列 + `mergeKey` 聚合「张三 等 N 人赞了…」）；机审三级分流（BLOCK/REVIEW/PASS）+ 本地词库兜底 + 第三方驱动预留；按**动作维度**限流；搜索索引弱一致异步同步。

## 1. 帖子建模（题目 1）

### 1.1 核心表结构

```
post(id UUID, authorId, type: IMAGE_TEXT|VIDEO, title, content,
     categoryId /*必选分区*/, visibility: PUBLIC|PRIVATE,
     status: DRAFT|PUBLISHED|SCHEDULED|RECYCLED,          ← 生命周期
     auditStatus: PENDING|APPROVED|REJECTED, auditReason, ← 合规（先审后发）
     viewCount/likeCount/coinCount/favoriteCount/commentCount,  ← 冗余计数
     scheduledAt, publishedAt, createTime, updateTime, deletedAt)
post_tag(postId, tagId)             ← 话题标签（Tag.useCount 热度）
media(postId?)                      ← 0..n 媒体（1 对多）
comment / like / favorite / coin / follow   ← 互动表（见 §5）
```

### 1.2 关键设计点（对建模的启示）

- **status 与 auditStatus 正交**：一个管生命周期（草稿/发布/定时/回收站），一个管合规——两条状态机不混在一个字段里，避免「审核中」与「草稿」语义纠缠；
- **软删三态语义分层**：
  - 用户删除 → `status=RECYCLED`（回收站，可自助恢复）；恢复时**不冗余记录删除前状态**，按现有字段推导：已过审且写过 `publishedAt` → `PUBLISHED`；定时未到 → `SCHEDULED` 并**重新投递发布任务**；其余（含待审/驳回/定时已过期）→ `DRAFT`，由作者**重新送审发布（合规红线不绕过）**；
  - 管理员下架 → `deletedAt` 软删（用户不可恢复，与回收站区分）；
- **计数冗余 + 同事务原子自增**：`likeCount` 等持久化列，互动读写放同一事务（`increment/decrement`），不做读时 COUNT 聚合；
- **统一可见谓词**：对外可见 = `auditStatus=APPROVED + status=PUBLISHED + visibility=PUBLIC + publishedAt 非空`；feed/详情/搜索/关注流**共用同一谓词常量**，防止「某一处漏过滤」；
- **详情信息量区分**：待审内容对非作者显示「审核中」提示，已删显示 404——不是所有不可见都 404；
- **全站内容坐标系 = 分区（category 必选）**：与领域 Tab 同构（我们的 domain 三领域）。

## 2. 图片链路（题目 2）

### 2.1 流程与端点

```
POST /media/upload (multipart, 单文件)
  → EXIF 清理（隐私/畸形头）
  → 同文件生成多规格：original / thumb / list / detail（各自裁切压缩）
  → 逐规格上传对象存储，key = images/YYYYMM/{uuid}/{variant}.{ext}
  → media 行落库（type=IMAGE, status=READY, variants, width/height/size/mimeType, coverUrl=列表规格）
  → 返回带变体视图的 MediaItem（id 供发帖时 mediaIds 绑定）
```

### 2.2 关键纪律

- **存储层抽象**：`StorageService`（upload / getPublicUrl / delete / exists），驱动 = `local | aliyun-oss | tencent-cos` 按环境变量一键切换；开发本地磁盘、生产对象存储，**业务代码零改动**；
- **key 规范化**：按年-月分桶 + UUID 随机化（防枚举、防重名）；`sanitizeObjectKey` 拒绝 `.`/`..`/空段；**落盘名与展示名分离**——原名只存 `Media.filename`（群文件场景展示需要），文件扩展名白名单收口；
- **「上传 ≠ 发布」**：上传是自由动作，媒体对他人可见的唯一路径是绑定到发布场景（帖子/会话）；帖子只允许绑 `IMAGE/VIDEO`（`MediaType.FILE` 明确排除——否则等于绕开会话边界把文件公开，且前端渲染拿 FILE 会渲染出坏图）；
- **读取出口统一签名**：CDN 私有化时由服务端统一签名返回短效 URL（`signMediaItem`），前端过期后「重签 + 续播」兜底；
- 图片 `status=READY`（无转码态），状态机主要为视频服务。

## 3. 视频链路（题目 3）

### 3.1 分片上传

```
POST /media/video/init   {filename, size, chunkCount} → {uploadId, maxChunkSize}
POST /media/video/chunk  {uploadId, index} multipart   （逐片落临时目录）
POST /media/video/merge  {uploadId} → MediaItem(status=TRANSCODING)
```

- init 校验：扩展名白名单（.mp4/.mov/.webm/.m4v）、大小上限（500MB）、**分片数必须与 size 匹配**（防伪造/防参数错位）；
- 会话表：`Map<uploadId, session>`，TTL 6h（超时由下次 init 顺带清理）；单实例内存即可（分片上传要求同实例亲和；多实例改 Redis——项目注释明确写了）；
- merge：按序拼接 + **总大小二次校验**（不符 → 直接废会话，坏媒体不进转码）；随后写存储 → 落 `Media(status=TRANSCODING)` → 投递转码队列；
- 生产演进注释：大文件应「服务端签发临时凭证 + 客户端分片**直传**对象存储」，不经过应用服务器（课程演示不需要）。

### 3.2 异步转码与状态机

- **`Media.status` 是播放器可用性的权威**：`TRANSCODING` 期间前端展示「转码中」，`READY` 才可播放；
- 转码队列（BullMQ 类）双轨：
  - **本地模拟**：未配置云转码 → 直接把原片标 `READY`（`variants={original}`），开发/演示即刻可播；
  - **云转码**（阿里 MPS 类）：提交 360p/720p/1080p + HLS + 封面截图作业；完成后回调 `POST /media/transcode/callback`（HMAC 验签），与 MNS 消费**双入口共用同一状态机函数**；**成功幂等（重复应用结果相同）、已 READY 的媒体收到迟到的失败通知不回退**；失败回退 `UPLOADED` 可重试；
- `variants` 约定：`{ "hls": m3u8, "1080p": url, "720p": url, "360p": url, "original": url }`；
- **前端播放器**（对应我们 MobilePostMedia）：按 key 排序（hls 自动档 > 原画 > 数字档降序）；HLS 走 Safari 原生 / hls.js(MSE)；容错三件套——① CDN 签名过期（长视频必 403）→ 重新拉详情换 URL 并 seek 回原位；② hls.js 网络/媒体错误恢复（带次数上限防死循环）；③ 档位判死 → 自动降级次优档并提示，无档可用才整体失败（不给黑屏）。

### 3.3 列表卡与详情的渲染分工

- 列表卡只渲染**封面 + 时长 + 播放角标**（`coverUrl` + `duration` + `▶` + `loading="lazy"`），不加载播放器——流量与性能的关键一刀；
- 详情页才挂 `VideoPlayer`；多图按 media 行逐张渲染；帖子媒体渲染只认 IMAGE/VIDEO（与后端类型白名单同构）。

## 4. 发布与审核

- **发帖**：校验分区 → **机审分流**（`gateText`）：命中 BLOCK 词 → **整体拦截（内容不入库，仅留痕摘要给后台追溯）**；命中 REVIEW 词 → 入库 `PENDING` 转人工；PASS + `autoPassClean` → 自动过审；机审关闭/第三方失败 → 回退**本地敏感词库** + 全量人审；
- **`audit.autoApprove=true` 仅开发用**；**机审 BLOCK 拦截任何模式下都生效**（合规红线不因开发开关绕过）；
- **草稿不送审**；**定时发布** = 队列延迟任务（jobId=postId，天然幂等去重）+ `SCHEDULED` 状态；**到点必须已过审才发布**（未过审保持 SCHEDULED，由审核通过路径补发）；服务启动补扫存量 SCHEDULED 防停机漏投；
- 发布后异步同步搜索索引（弱一致，入队失败仅告警）；
- **限流按动作维度**（非接口维度）：发帖 `5/分 · 10/时 · 50/天`；点赞 `30/分 · 1000/天`；投币 `10/分 · 200/天`；
- **机审图片/视频是预留**：驱动接口统一 `scanImage(url)`（视频抽帧送审共用），当前生产只接了文本机审——说明媒体机审即使是企业项目也常分阶段落地，不是发布即全量。

## 5. 互动与通知（支撑「点赞/投币/评论」的工程细节）

| 互动 | 机制 | 要点 |
|---|---|---|
| 点赞 | 唯一约束 `(userId, targetType, targetId)` 防并发重复 | toggle 取消 = 软删 + 计数自减（同事务）；再赞 = **恢复软删记录**（避开唯一索引）而非新建；自赞不通知、取消不回撤 |
| 投币 | **不可取消**；一人一帖一次（唯一约束兜底并发） | 消耗本人积分账户 + 作者**等额入账**（强正反馈）；条件扣减防负余额；不能给自己投 |
| 收藏 | 可分类收藏夹 folderName | 软删 toggle，同点赞套路 |
| 关注 | 唯一 `(follower, following)` | 关注流 = 已关注作者新内容（游标分页） |
| 评论 | 先审后发；**根评论分页 + 楼内回复拉平二级**（`rootId` 拉平 + `parentId` 引用 + `replyToNickname`） | 「本人待审评论自己也可见（标记审核中），别人看不到」 |
| 通知 | 队列任务（失败不影响互动本身） | **`mergeKey` 聚合**：同帖多人点赞 → 摘要「张三 等 N 人赞了你的内容」；分型 SYSTEM/INTERACTION/ORDER/AUDIT |

## 6. 对我们（docs/37 S1）的直接启示

### 6.1 建议采纳（低门槛、课程演示尺度）

1. **Media 单表 + 状态机 + variants JSON**（见 §2/§3）：比 docs/37 现在的 `posts.media jsonb` 更可演进——字段集（type/status/url/coverUrl/variants/width/height/duration/size/mimeType/sort）与演示级简化（只做原片 + 封面 + `variants={original}`，转码本地模拟直出，MPS/MNS/HLS/多清晰度/签名全不做）兼容；
2. **「上传 ≠ 发布」的绑定边界**：S1 我们不实现上传（媒体 = 元数据占位/外部 URL），但**表结构按 media 表预热**（字段命名对齐），S2 做上传时再加 `media` 表与绑定校验，避免返工；
3. **status × 合规位正交 + 统一可见谓词**：我们 S1 `posts.status(visible/hidden/deleted)` + 统一谓词（visible + 未软删）；内容审核（机审/敏感词/举报）登记为 P1——公开仓库红线（不采真实用户数据）+ 前端纯文本渲染转义已覆盖演示安全面；
4. **计数冗余 + 唯一约束 + 软删恢复套路**：like/coin 计数列 + `(post_id, actor_id)` 唯一 + 幂等（我们 interactions 已设计唯一键，正确）；投币我们没有积分账户 → **免费计数器**（语义降级，表结构同款）；
5. **游标分页「多取一条判 hasMore」**：与 docs/37 keyset 设计一致，补上断言惯例；
6. **互动通知 mergeKey 聚合**：通知中心 S2 真实化的直接模板（「张三 等 N 人赞了…」）；
7. **限流按动作维度**：给出参考值（发帖 5/分、点赞 30/分、投币 10/分），登记为 docs/37 §4 的 P1 落地参数。

### 6.2 明确不做（避免过度设计，写入 docs/37 修订）

- 定时发布 / 草稿 / 回收站 / 多状态机（我们只有 visible/hidden/deleted 三态，S1 为 append-only 流）；
- 积分账户 / 收藏夹 / 举报 / 机审 / ES 搜索 / 召回-热度-重排推荐（「为你推荐」= 时间序，推荐引擎 M3 再接）；
- 云转码 / MNS / HLS 多清晰度 / CDN 签名（demo 500 DAU 不需要；docs/06 §8 的 AudioStore 抽象预留已够）；
- 视频分片上传（我们音频 ≤20MB 单次上传；视频 S1 只存元数据不传文件）。
